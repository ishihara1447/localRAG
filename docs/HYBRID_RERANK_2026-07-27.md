## 1. 何が壊れていたのか（再掲・コード実測）

`anything-llm/server/utils/vectorDbProviders/lance/index.js` の `performSimilaritySearch` は

```js
if (rerank) {                        // workspace.vectorSearchMode === "rerank" のときだけ真。既定 false
  result = await this.rerankedSimilarityResponse({...});   // cross-encoder あり。ただし dense のみ（BM25不使用）
} else if (this.hybridSearchEnabled) {                     // 製品はこちら（LANCE_HYBRID_SEARCH=true が既定）
  result = await this.hybridSimilarityResponse({...});     // cross-encoder 呼び出しが一切ない
}
```

という**排他分岐**である。したがって製品既定の経路では、同梱している
**bge-reranker-v2-m3（571MB）がチャンクの選抜に一度も使われていなかった**。
RRF は候補32件を作りながら `reciprocalRankFusion(..., {limit: topN})` で**順位だけで8件に切り捨てて**おり、
rank 9〜32 の正解チャンクはリランカーの入力にすら到達していなかった。

実際に稼働ワークスペースの本番設定は `vectorSearchMode = "default"` である（本作業中にAPIで実測）。
＝ `rerankedSimilarityResponse` は**この製品では一度も走っていない**。

## 2. 実装

変更ファイルは **`anything-llm/server/utils/vectorDbProviders/lance/index.js` の1本のみ**（+94/−3行）。
`rerankedSimilarityResponse`（dense-only 経路）と `sentenceCushion.js` は**未接触**。

### 2-1. 追加した3点

| # | 内容 |
|---|---|
| 1 | `get hybridRerankEnabled()` — `LANCE_HYBRID_RERANK` を読む gate。**既定 OFF** |
| 2 | `hybridCandidateLimit(topN)` に `LANCE_HYBRID_CANDIDATE_LIMIT` の上書きを追加。**未設定なら返り値は従来と1件も変わらない**（`Math.min(50, Math.max(20, topN*4))`。topN=8 → 32） |
| 3 | `rerankFusedCandidates({query, fused, topN})` — RRF融合済み候補を cross-encoder で再順位付けする新メソッド |

`hybridSimilarityResponse` 本体の差分は実質2行:

```js
const fused = reciprocalRankFusion(denseResults, ftsResults, {
  limit: this.hybridRerankEnabled ? candidateLimit : topN,   // ← OFF なら従来と同一
});
const ordered = this.hybridRerankEnabled
  ? await this.rerankFusedCandidates({ query, fused, topN })
  : fused;
ordered.slice(0, topN).forEach(({ item }) => { /* 以下は従来のまま */ });
```

### 2-2. 設計上の判断（意図的にこうした点）

- **リランカーは新規導入しない。** `rerankedSimilarityResponse` が使っているのと同じ
  `NativeEmbeddingReranker` を再利用する。モデルは静的シングルトンなので二重ロードは起きない
  （ログの `Reranker suite already fully initialized - reusing.` で実測確認）。
- **リランカーには `{text}` だけを渡す**（`__fusedIndex` で元要素に引き当てる）。
  `item` 全体を渡すと 1024次元の `vector` を候補数ぶんコピーすることになるため。
- **`score` の意味は変えていない。** 従来どおり dense の `_distance` 由来の類似度（BM25専用ヒットは `score` 無し）。
  変えると **P1（`queryReformulation.js` の `searchIsWeak`）の発火条件が同時に動いてしまい**、
  何が効いたのか切り分けられなくなるため。`rerank_score` も出力に混ぜていない。
- **失敗したら必ず RRF の順序をそのまま返す**（`try/catch`）。検索を落とさない。
- **順序を変えるだけで、集合の外へは出ない。** 融合プールは K 件のままで、K を超えて候補を掘りには行かない。

- ホスト↔コンテナ `sha256` 一致（`37a2b00e798e87be…`）。`docker cp` + `docker restart` のみ、`--force-recreate` 不使用

## 6. `sentenceCushion` との相互作用（実測して記録する）

**クッションはチャンクリランクの後段で走る。両方ONのときの挙動を実測した。**

処理順は `performSimilaritySearch` の中で

```
dense(K件) + BM25(K件) → RRF(K件) → 【新】chunk rerank → topN=8
                                   → 【既存】applySentenceCushion（文単位rerank）→ LLM
```

**同じ bge-reranker-v2-m3 が1クエリにつき2回、粒度を変えて呼ばれる。**

| 質問 | 条件 | chunk rerank | cushion のログ |
|---|---|---|---|
| Q02 | OFF | （走らない） | `chunks 8 -> 7, sentences kept 16/26`（26文入力・4.06秒） |
| Q02 | K=32 ON | `32 candidates -> top 8 in 9340ms` | `chunks 8 -> 7, sentences kept 13/19`（19文入力・2.06秒） |
| Q13 | OFF | （走らない） | `chunks 8 -> 8, sentences kept 19/31`（31文入力・3.92秒） |
| Q13 | K=32 ON | `32 candidates -> top 8 in 5002ms` | `chunks 8 -> 7, sentences kept 18/38`（38文入力・5.44秒） |

観測された事実:

1. **クッションの入力は常に topN=8 チャンクのままで、件数は増えない。** チャンクリランクは
   「どの8件が入るか」だけを変える。したがって **`SENTENCE_CUSHION_TOPK` を触る必要はない**
   （`docs/TOPN_CUSHION_EXPERIMENT_2026-07-26.md` で問題になった「topNを上げるとクッション予算が足りなくなる」
   現象は本施策では起きない）。
2. **最終的なチャンクの並びを決めるのはクッションのほう**である。クッションは
   「チャンク内ベスト文のスコア降順」で並べ直し、選ばれた文を1つも含まないチャンクを落とす。
   **チャンクリランクの順位はクッションの並べ替えで上書きされる。**
   ＝ 本施策の効き目は「順序」ではなく「**どのチャンクをクッションに見せるか**」にある。
3. **チャンクリランクは BM25専用ヒット（`score` が付かないチャンク）を topN に押し上げる。**
   Q13 の K=32 ON では rank2 と rank5 が `score=None`（＝dense に出てこなかった FTS 専用ヒット）だった。
   → **P1（`queryReformulation`）の `searchIsWeak` は「dense実スコアが1つも無いか / 最高スコアが閾値未満」で発火する**ため、
   将来 topN が全て FTS専用ヒットで埋まると P1 の発火頻度が変わりうる。
   本評価の範囲では最上位に dense スコアが残っていたため発火挙動の変化は観測されなかったが、
   **`score` の意味を変えなかったのはこの相互作用を動かさないためである**（§2-2）。
4. Q13 が K=16/50 で退行したのは、この (3) の副作用である。cross-encoder が押し上げた
   FTS専用チャンクが、`若年定年退職者給付金` を含むチャンクを topN から押し出した。

## 8. 判断と、やっていないこと

### 採否

**既定 OFF のまま据え置いた。** 理由:

- 検索層（主指標）の改善は**決定的で退行ゼロ**（K=32）。判定軸の主に照らせば採用側。
- しかし生成層は**事前固定の判定則で「差は誤差範囲」**であり、`hakusho-eval` も 29/30 で横ばい。
  **「エンドユーザーが受け取る回答が良くなった」という証拠は無い。**
- レイテンシが**約1.7倍**になる。品質の改善が証明できていない状態でこのコストを既定にするのは、
  顧客配布製品として妥当でない。
- したがって**ONにする判断はユーザーに委ねる**（依頼書の指示どおり）。

### 🔴 改善しなかった／悪化した点（はっきり書く）

1. **生成品質の改善は証明できていない。** 決定的要素 49/79 → 50/79（+1）は誤差。`hakusho-eval` は不変。
2. **K=50 は悪化する。** 検索層では最高（0.745）なのに `hakusho-eval` が **29/30 → 27/30**、
   決定的要素が **49/79 → 46/79** に落ちた。
   **「Drowning in Documents」（arXiv:2411.11767、bge-reranker-v2-m3 を含む4モデルで検証）が
   実証した「Kを増やしすぎると検索単独より悪化する」という現象が、本環境でも再現した**
   ——ただし本環境で悪化したのは**検索指標ではなく生成指標**である点が文献と異なる。
   検索は良くなったのに回答が悪くなった。
3. **(A) 検索失敗の3問（Q12・Q16・Q18）はどのKでも1ミリも動かない**（すべて `anchor@8 = 0.00` のまま）。
   これらは候補プールの中に正解が存在しない索引・チャンク分割の問題であり、
   **リランクでは原理的に解けない**。`anchor_coverage@32` も 0.00 のままであることが裏付け。
4. **Q13 は K=16 と K=50 で退行する**（1.00 → 0.75）。K=32 のみ無傷。
5. **レイテンシは明確に悪化する**（§7）。

### やっていないこと

- **`rerankedSimilarityResponse`（dense-only 経路）は1行も触っていない。**
  `vectorSearchMode === "rerank"` を選んだときの挙動は不変。
- 3run目は取っていない（依頼の要件は最低2run。各条件で2runが完全一致したため追加の情報量は乏しいと判断）。
  ただし `complex-eval.py --phase report` は「★最低3run必要」と警告を出すので、
  **製品判断として確定させるなら3run目を足すこと**。
- 評価フィクスチャ・採点ロジックは**一切変更していない**（退行が出たときに採点側を緩めるのは判定基準の後付け変更にあたるため）。
- `LANCE_HYBRID_CANDIDATE_LIMIT` を**gate OFF のまま単独で使う**組み合わせは評価していない
  （実装上は可能で、その場合 RRF の候補プールだけが変わる）。

## 10. 次に触るときのために

1. **K=32（＝env未設定）以外を選ぶ理由は、今のところ無い。** K=16 は検索が劣り Q13 を落とす。K=50 は生成が壊れる。
2. **効果を確定させたいなら、先に評価セットを 20 → 30〜40問に拡張すること**（`NEXT_PLAN_2026-07-27.md` A2）。
   n=20 では McNemar が b=2/c=3 のような小さな入れ替わりを検出できず、

3. **レイテンシを下げる余地**: リランカーは CPU 実行。ONNX Runtime の GPU EP か、

   ただし同§の期待「Hybrid+Rerank が単独最大の改善」は**生成層では再現しなかった**。
