# 評価プロトコル — 事前登録と「内容補正」の禁止

作成: 2026-07-27 / 担当: Claude Code
位置づけ: `docs/RESEARCH_EVAL_INDEPENDENCE_2026-07-27.md` §9 **手順2**（推奨度「必須」）の実装。
対になる実装: `scripts/test_scoring_mft.py`（同 §9 手順1。既知の採点事故の常設回帰テスト）

**この文書は運用ルールであり、次に評価を回すときに開いて上から順に使う。**
§7 の事前登録票をコピーして埋めるところから始めること。

## 0. なぜこのルールが要るのか（1分で読む用）

内部監査（`RAG_EVAL_INTERNAL_AUDIT_2026-07-16.md` §1-1）はこう書いている。

> 直近2回連続で「自動採点の生スコア → 手動で目視して補正したスコア」という運用になっている。
> **「生スコアが気に入らなければ人間が読んで正解にする」運用**は、
> 評価者のバイアス（施策を通したい/通したくない）が混入する余地を生む。

そして採点器の欠陥は**5例連続で発生し、うち4例は「評価が甘い方向」**だった。
これは leniency bias として実証されている既知現象で、LLM 判定者は
**TPR > 96% に対し TNR < 25%**（arXiv:2510.11822）。文字列一致の採点器も同じ方向に倒れる。

**HELM（arXiv:2211.09110）は raw prompt / completion を全公開し、第三者が事後に判定を覆せる
状態を作ることで妥当性を担保している。手動補正はこの原則と最も相性が悪い。**
補正した瞬間に「その数字がどう作られたか」を再現できなくなる。

事前登録（preregistration）は心理学・実験経済学の標準手法で、**コストがほぼゼロ**である。
実験前に「何を変え／何を期待し／どの指標で判定するか」を書き、実行後に採点基準を動かさない。
これだけで我々の最大の欠陥（手動補正の常態化）が消える。

## 1. 採点基準は実験前に凍結する

### 1-1. 凍結の対象（これが「採点基準」の定義）

| 対象 | 実体 |
|---|---|
| 設問と正解 | `fixtures/complex/hakusho-complex-qa.json` |
| 正規化層（Layer0） | `scripts/_eval_common.py` |
| 決定的判定（Layer0/1） | `scripts/complex-eval.py` の `judge_element()` および `not_preceded_by` の扱い |
| 不明応答判定 | `hakusho-eval.py` の `UNKNOWN` / `scale-eval.py`・`precision-eval.py` の `UNKNOWN_PATTERNS` |
| 既存3セットの設問と採点 | `hakusho-eval.py` の `CASES`、`ambiguous-eval.py` の `CASES`、`scale-eval.py` の `CASES` |
| LLM-as-judge | `scripts/_judge.py` の `PROMPT` / `PROMPTS`、`JUDGE_MODEL`、`JUDGE_SEED` |
| MFT 回帰 | `scripts/test_scoring_mft.py`（`KNOWN_INCLUSION_OFFENDERS` と `known_defect` を含む） |

### 1-2. 凍結の手順

測定を始める**前**に、事前登録票（§7）へ次を記録する。

```bash
cd repos/localRAG
sha256sum fixtures/complex/hakusho-complex-qa.json \
          scripts/_eval_common.py scripts/complex-eval.py scripts/_judge.py \
          scripts/hakusho-eval.py scripts/ambiguous-eval.py \
          scripts/scale-eval.py scripts/precision-eval.py \
          scripts/test_scoring_mft.py
git rev-parse HEAD 2>/dev/null; git status --porcelain
```

さらに **MFT を通してから測る**。採点器が壊れた状態で測ったデータは、後から採点し直しても
「どの条件で何が起きたか」の解釈が汚染される。

```bash
uv run scripts/test_scoring_mft.py          # 全件（KNOWN は許容）
uv run scripts/test_scoring_mft.py --strict # リリース判定・対外主張の前はこちら
```

### 1-3. 凍結の期間

**測定開始から、その測定にもとづく結論を書き終えるまで。**
A条件を測ったあとにB条件を測るなら、その間ずっと凍結されている。
凍結を解いてよいのは §2 の手順を踏んで**全条件を再実行するとき**だけ。

### 1-4. 凍結しなくてよいもの（＝これが「実験条件」）

`topN`・`chatModel`・プロンプト・`LANCE_SENTENCE_CUSHION`・chunk サイズ・rerank 設定など、
**製品側の設定**は当然変える。変えるからこそ測る。混同しないこと。

> 🔴 **同時に2つ以上の条件を変えない。** 変えたなら、どちらが効いたかは言えない。
> 2026-07-26 に `topN` と `SENTENCE_CUSHION_TOPK` を同時に上げて有意悪化（p=0.0003）した
> 事例がある（`NEXT_PLAN_2026-07-27.md` §0-a）。

## 2. 実行後の「内容補正」を禁止する

### 2-1. 禁止事項（例外なし）

- ❌ 自動採点の結果を目視して「これは実質正解だから」と点を足す／引く
- ❌ 「表記ゆれで誤NGだったので手動補正すると21/30」と書いて、その数字で判断する
- ❌ 採点器を直したあと、**改善側の条件だけ**再実行して旧ベースラインと比べる
- ❌ 実行後に alias / 正規表現 / 設問を追加して、追加後の点数を採用する
- ❌ 「3run のうち一番良かった run」を代表値にする

### 2-2. 採点が誤っていると分かったときの手順

```
  1. 止める。その測定の数字は使わない（消さずに残す。§2-4）
  2. 事故を `scripts/test_scoring_mft.py` に **先に** MFT として足す
     → その時点では FAIL するはず。FAIL しないなら再現できていない＝修正対象が違う
  3. 採点器を直す。MFT が PASS することを確認する
  4. `uv run scripts/test_scoring_mft.py --strict` で他の事故が再発していないことを確認
  5. **全条件を、同じ新しい採点器で再実行する**
     ・保存済み回答があるなら `--phase judge` を掛け直すだけでよい（生成し直さなくてよい）
     ・保存済み回答が無い条件があるなら、その条件は生成からやり直す
  6. 事前登録票に「逸脱」として記録する（§9）
```

**「片方だけ直して比較しない」が本項の核心である。**
採点器を直すと点数は両条件で動く。改善側だけに新しい採点器を当てれば、
その差分は施策の効果ではなく採点器の変更でしかない。

### 2-3. 再実行の工数が無いときの正しい振る舞い

**「測定できなかった」と書く。** 補正した数字で結論を書かない。
証拠のない主張を1つ残すほうが、工数を惜しんで作った数字1つより安い。

### 2-4. 生データは消さない・上書きしない（HELM 原則）

- `--phase generate` の出力 JSON（回答全文）は必ず保存し、条件名と run 番号がファイル名で分かるようにする
- 採点をやり直すときは `--phase judge` を**新しい出力ファイル**に書く。上書きしない
- こうしておけば、後日「採点器が間違っていた」と分かっても**生成をやり直さずに全条件を再採点できる**
  ＝ §2-2 の手順5 のコストが激減する。これが内容補正への最大の抑止力になる

## 3. 「改善した」と主張してよい条件（事前定義）

### 3-1. 判定則（S07。2026-07-26 に凍結済み・変更しない）

**次の3条件を*すべて*満たしたときにだけ「改善した」と書いてよい。**

| | 条件 |
|---|---|
| (a) | 95%信頼区間が重ならない（要素カバー率＝クラスタブートストラップCI、リサンプル単位は**設問**／完全正答率＝Wilson CI） |
| (b) | McNemar 検定で **p < 0.05**（ペア設計。同一設問集合なので対応ありで分散が下がる） |
| (c) | **3run すべてで改善方向が一致**している |

1つでも欠けたら **「差は誤差範囲」** と書く。「改善傾向が見られた」も禁止（(c) を満たさない
限り方向すら言えない）。

### 3-2. 悪化（退行）の判定

**退行は改善より緩い基準で拾う。** 少数拒否権の考え方（1体でもNGならNG, arXiv:2510.11822）と
同じで、見逃しのコストが非対称だからである。

- (a)(b)(c) を満たす悪化 → **不採用・巻き戻し**（例: 2026-07-26 の topN+cushion 同時増、p=0.0003）
- 3run すべてで悪化方向が一致 → **採用保留**。有意でなくても、改善の証拠が無いまま入れない

### 3-3. どの指標で判定するか（主・従）

2026-07-26 に決定済み。**変更するなら本文書を改訂してから測ること。**

| | 指標 | 理由 |
|---|---|---|
| **主** | retrieval 指標（`anchor_coverage@8`・`All-Hit@8`・nDCG@k） | LLM 非依存で決定的。条件を明確に分離できる |
| **従** | generation 指標（要素カバー率・完全正答率） | 退行監視に使う。n=20 では検出力が足りない（§4） |

`--phase failmode` は **anchor_coverage@8 が主・page_coverage は参考値**（A1, 2026-07-27）。
ページ方式には2度誤誘導された実績がある。

## 4. n=20〜40 で検出できるのは概ね15pt以上の差

### 4-1. 根拠

- **Voorhees & Buckley, SIGIR 2002**: TREC 50トピックを25/25に分割。**25トピックでは MAP の絶対差が8〜9%ないと、順位の入れ替わらない確率が95%に達しない**
- **Sakai, SIGIR 2016**: 十分な検出力にはトピック数**200程度**が必要
- **Miller (Anthropic), arXiv:2411.00640**: 標準誤差・信頼区間の報告、ペア分析、**事前の検出力設計**を推奨
- **我々の実測**: S07 で topN=8 vs 4 の**実差が存在する**（要素カバー率 0.608→0.536、C5 が 0.500→0.100、20問すべてで回答本文が変化）にもかかわらず、**McNemar p=0.18 で有意にならなかった**

### 4-2. 運用ルール

> **20〜40問の生成側評価で、15pt 未満の差は「差なし」として扱う。**
> §3-1 の判定則を満たさない限り、大小を論じない。

具体的に禁止される言い方（すべて実際に書かれたことがある形）:

| ❌ 書いてはいけない | ✅ 正しい書き方 |
|---|---|
| 「28/30 が 29/30 になったので改善した」 | 「28/30 → 29/30。1問差は n=30 の検出限界以下であり、差なしと扱う」 |
| 「hybrid 検索は 21→19 点なので改悪」 | 「21→19。差なし。retrieval 指標で判定する」 |
| 「要素カバー率が 0.582 → 0.608 に向上」 | 「0.582 → 0.608（+2.6pt）。CI が重なり McNemar p=0.xx。差なし」 |
| 「改善傾向が見られる」 | （そもそも書かない。3run方向一致すら無いなら方向も言えない） |

### 4-3. 小さい差をどうしても見たいとき

**問題数を増やすしかない。** 統計処理では解決しない。
評価セットの 20→30〜40 問拡張（`NEXT_PLAN_2026-07-27.md` Track A / A2）はこのための作業であり、
40問でも検出限界は 15pt 前後にしか下がらない。**100問以上が必要**（Sakai 2016）。

その代わり **retrieval 指標は決定的**なので、同じ n でも generation より遥かに小さい差を
確実に見られる。§3-3 で retrieval を主指標にしているのはこのためである。

## 5. カテゴリ別スコアを主指標とし、合計点を単一指標にしない

### 5-1. 根拠

**llm-jp-eval（ANLP 2024）は、NLI タスクを「正解ラベル分布の不均衡で評価が不安定になる」
として合計指標から除外した。** 性質の違うタスクを1つの数字に潰すと、
片方の不安定さがもう片方の実質的な改善を覆い隠す。

我々の (d) 不明応答カテゴリは同じ構造にある。**(d) は「ハルシネーションが出ないこと」という
安全性の主張を担っており、事実正答率とは意味が違う。**足して1つの数字にしてはならない。

### 5-2. 運用ルール

1. **必ずカテゴリ別に分解して報告する**
   - complex: `C1 集約・構成 / C2 マルチホップ / C3 比較 / C4 要約 / C5 推論・含意 / C6 unanswerable`
   - hakusho / scale: `(a) 事実 / (b) 数値 / (c) 定義 / (d) 不明応答 / (e) その他`
2. **合計点は「補助的に併記してよい」だけ。** 意思決定の主軸にしない
3. **異なるセットの点を足さない・混ぜない。** complex 20問と hakusho 30問は難易度が違う
   （`COMPLEX_QA_EVAL_SET_DESIGN_2026-07-26.md` §7-4）。合算した「50問中◯問」は作らない
4. **(d) / C6（不明応答・unanswerable）は必ず単独で報告する。**
   ここが下がったらハルシネーションが増えたということで、他がいくら上がっても採用しない
5. カテゴリ別に見ると n が 3〜5 まで落ちるので、**カテゴリ単体の差に統計的主張をしない**。
   カテゴリ別スコアは「どこが弱いか」の**診断**に使い、「良くなった」の**証明**には使わない

## 6. 絶対%を製品の性能主張に使わない

### 6-1. 根拠

- **Are We Done with MMLU?（NAACL 2025）**: MMLU 全体の **6.49% に誤り**、Virology サブセットでは **57%**。
  → **30〜40問なら 2〜3問に正解ラベルの誤りがある前提で扱うべき**
- **Voorhees 2000** が示したのは「**相対順位**は判定のブレに頑健」であって「絶対値が信頼できる」ではない
- **GSM1k（arXiv:2405.00332）**: 同難易度の新規問題に差し替えると一部モデルで**最大13pt低下**。
  設問を固定したまま改善サイクルを回すと、その設問に過剰適合する（Goodhart's law）。
  **我々の改善サイクル（topN・hybrid・cushion・rerank）はまさにこの構造**
- 調査の結論: **「29/30 = 97%」を製品の性能主張に使うのは、先行研究の全文に照らして支持できない**

### 6-2. 運用ルール

| ❌ 使ってはいけない | ✅ 使ってよい |
|---|---|
| 「正答率97%」「精度96.7%」（対外・社内問わず） | 「**同一の30問・同一条件**で、施策前後を比較して有意な退行が無いことを確認した」 |
| 「30問中29問正解の高精度」 | 「防衛白書30問の内製評価セットで、条件Aと条件Bの相対比較に用いている」 |
| 「ハルシネーション率 0%」 | 「(d) 5問で不明応答を返し、誤った断定は観測されなかった（n=5。ゼロの証明ではない）」 |
| 数字をグラフにして提案資料へ | 数字は `docs/` の測定記録に留め、**社外資料には相対比較の結論だけ**書く |

### 6-3. 過剰適合を抑える運用（推奨・未実施）

- 評価セットの一部を **held-out（封印）**し、日常の改善サイクルでは使わずリリース判定時のみ開封する
  （`RESEARCH_EVAL_INDEPENDENCE_2026-07-27.md` §9 手順6）
- 拡張時は**同一仕様の新規問題**を作って時々入れ替える

## 7. 測定前チェックリスト（事前登録票）

**測定を始める前にこれを埋め、`docs/` の作業記録に貼る。埋まっていない項目があるうちは測らない。**

```markdown
## 事前登録票 — <実験名> (<日付>)

### 1. 何を変えるか（1回に1つ）
- 変更点: 
- 変更しないもの（明示）: fixture / 採点器 / judge プロンプト / judge seed / 他の製品設定

### 2. 何を期待するか（測る前に書く）
- 仮説: 
- 予測される変化（指標と向き、できれば大きさ）: 
- **この仮説を支持する先行研究**（NEXT_PLAN §0-a 文献先行の原則）: 
- **既存の自社調査 `docs/RESEARCH_*.md` に答えが無いことを確認したか**: [ ]

### 3. どの指標で判定するか
- 主指標（retrieval）: anchor_coverage@8 / All-Hit@8 / その他（　　）
- 従指標（generation・退行監視）: 決定的要素カバー率 / 完全正答率 / カテゴリ別
- 判定則: S07（(a) CI非重複 かつ (b) McNemar p<0.05 かつ (c) 3run方向一致）
- **検出限界の確認**: n = ___ 問。generation 側で検出できるのは概ね15pt以上（§4）
- **予想される差が検出限界を下回るなら、測る前にそう書く**: 

### 4. 実験計画
- 条件: A = ______ / B = ______
- run 数: ___（最低3）
- ペア設計であること（同一設問集合・同一 run 番号で対応づける）: [ ]
- 生成出力の保存先（条件・run が分かるファイル名）: 
- 交互実行か（環境ドリフト対策）: [ ]

### 5. 凍結の証拠
- MFT: `uv run scripts/test_scoring_mft.py` → passed __ / failed __ / known __
- KNOWN の内訳と、それが本実験の判定に影響しない理由: 
- sha256（§1-2 のコマンド出力を貼る）:
- git HEAD / 未コミット差分: 

### 6. 事前に決めた撤退条件
- どうなったら不採用にするか: 
- どうなったら「差なし」と結論するか: 
```

## 8. 測定後チェックリスト

```markdown
## 測定後 — <実験名>

- [ ] 採点器を実行後に変更していない（変更したなら §9 に逸脱として記録し、全条件を再実行した）
- [ ] 手動での点数補正を一切していない
- [ ] 生成出力 JSON をすべて保存し、上書きしていない
- [ ] カテゴリ別に分解して報告した（合計点を単一指標にしていない）
- [ ] (d) / C6（不明応答）を単独で報告した
- [ ] 判定則 (a)(b)(c) の各条件について、満たしたか満たさないかを明記した
- [ ] 満たさない条件があるなら結論を「差なし」と書いた
- [ ] 絶対%を性能主張に使っていない
- [ ] 事前登録票の「期待」と実測がずれた場合、**ずれたことを消さずに書いた**
- [ ] MFT を測定後にもう一度回して PASS した（測定中に誰かが採点器を触っていないことの確認）
```

> **事前登録の価値は「予測が外れたことが記録に残る」ことにある。**
> 外れた予測を消して結果に合う説明を後付けすると（HARKing）、事前登録した意味が消える。

## 9. 逸脱（deviation）の記録

計画どおりにいかないことはある。**やってはいけないのは、逸脱を黙って埋めることだけ**である。

逸脱が起きたら、作業記録に次の形で残す。

```markdown
### 逸脱 <番号>
- 何が起きたか: 
- いつ気づいたか（測定前 / 測定中 / 結果を見た後）: 
- どう対処したか: 
- **結果を見た後の逸脱か**: はい / いいえ
  （はい の場合、その測定の結論は「参考値」に格下げし、主張に使わない）
- MFT に回帰テストを追加したか: [ ] → テスト名: 
```

**「結果を見た後に採点基準を触った」場合、その測定は原則として主張に使えない。**
使いたいなら §2-2 の手順で全条件を再実行すること。

## 付録A. 標準実行手順（コピペ用）

```bash
cd repos/localRAG
export HAKUSHO_SLUG=<slug>

# 0) 凍結の証拠を取る（§1-2）
uv run scripts/test_scoring_mft.py
sha256sum fixtures/complex/hakusho-complex-qa.json scripts/_eval_common.py \
          scripts/complex-eval.py scripts/_judge.py scripts/test_scoring_mft.py

# 1) 主指標: retrieval（LLM不使用・決定的）
uv run scripts/complex-eval.py --phase retrieval --out out/<cond>-retrieval.json

      --out out/<cond>-gen-run$r.json
done

# 3) 採点（生成をやり直さずに掛け直せる。ここが内容補正の代替手段）

      --out out/<cond>-judged-run$r.json
done

# 4) 判定（CI・McNemar・カテゴリ別）
uv run scripts/complex-eval.py --phase report out/<cond>-judged-run*.json
uv run scripts/complex-eval.py --phase report out/A-judged-run*.json \
    --compare out/B-judged-run*.json

# 5) 測定後にもう一度 MFT（測定中に採点器が動いていないことの確認）
uv run scripts/test_scoring_mft.py
```
