# OTE-RAG スパナメニュー互換性分析

調査日: 2026-07-25  
対象: `anything-llm/frontend/src/components/SettingsSidebar/index.jsx` と、対応するフロントエンド・サーバー実装  
想定製品: Windows 11 ネイティブ版、WSL/Docker不要、単一ユーザー、ローカルLLM、LanceDB、外部送信なし

## 1. 結論

現在のスパナメニューは、AnythingLLM上流版の設定画面を広く残した構成です。そのため、**画面とルートが存在することと、OTE-RAGで利用を保証できることは別**です。

現行製品の設計方針では、次の3層に分けるのが適切です。

| 判定 | 意味 |
|---|---|
| ◎ | 現行のWindowsネイティブ構成で利用を保証できる |
| ○ | 実装はあるが、追加設定・同梱確認・安全上の条件が必要 |
| △ | 技術的には実現可能だが、製品向けの追加実装・検証が必要 |
| × | 現在の「ローカル限定・Windows単体」方針とは両立しない。顧客画面には出さない |

### 推奨判断

- **残す**: ローカルLLM、埋め込み、LanceDB、チャンク設定、ワークスペース、既定プロンプト、UI/チャット設定、イベントログ、セキュリティ。
- **条件付きで残す**: ローカル音声認識・音声合成、APIキー、システムプロンプト変数、ワークスペース履歴、モデルルーター。
- **顧客向け画面から隠す**: Community Hub、Telegram、モバイル、ブラウザ拡張、外部埋め込み、クラウドプロバイダー、未検証のベクターデータベース、Docker専用エージェント、定期実行、実験機能。
- **バックエンド制限は維持・強化する**: UIから隠すだけでは不十分です。環境変数の直接編集やAPI呼び出しでも、外部LLM・外部埋め込み・外部検索を有効化できないようにします。

## 2. 製品前提との照合

Windows配布版の設定テンプレートは、以下を前提にしています。

- LLM: `ollama`
- 埋め込み: `ollama` 経由の `bge-m3:latest`
- ベクターデータベース: `lancedb`
- ハイブリッド検索: 有効
- テレメトリ、Swagger: 無効
- Webスクレイピング: 無効
- Hugging Faceの実行時取得: オフライン設定

根拠は [`windows-native/config/server.env.template`](../windows-native/config/server.env.template)、[`windows-native/config/collector.env.template`](../windows-native/config/collector.env.template) です。

また、LLMについてはサーバー側にローカル/self-hostedプロバイダーの許可リストがあります。UIにクラウドプロバイダーが表示される問題は、[`anything-llm/server/utils/helpers/index.js`](../anything-llm/server/utils/helpers/index.js) の制限とUIの選択肢が一致していないことが原因です。

## 4. なぜ「使えそうに見える」のか

設定サイドバーは、ユーザーのロールと `flex` 条件に基づいてメニューを表示します。単一ユーザーモードではユーザーオブジェクトが存在しないため、上流版の「単一ユーザーでも表示する」項目が広く見える状態になります。

その結果、次のような誤解が起こります。

1. 画面は開くため、利用可能に見える。
2. プロバイダーの選択肢が表示されるため、接続できるように見える。
3. 実際には、外部APIキー、Docker、クラウドアカウント、別配布物などが必要な場合がある。
4. LLMについてはバックエンド許可リストがあるため、UIで選択できても起動時に拒否される場合がある。

これは「拡張性が高い」というより、**上流版の汎用設定を製品能力プロファイルで絞り切れていない状態**です。

## 5. 段階的な改修計画

大きな一括削除ではなく、次の順で小さく進めます。

### P0: 表示と実際の能力を一致させる

1. Windowsローカル版の能力プロファイルを定義する。
   - `local_llm=ollama`
   - `local_embedding=ollama`
   - `vector_db=lancedb`
   - `external_network=false`
   - `docker_runtime=false`
   - `multi_user=false`
2. LLM、埋め込み、ベクターデータベースの選択肢を能力プロファイルから生成する。
3. UIで隠した項目も、API・環境変数直接編集時にバックエンドで拒否する。
4. 「選択肢を削除した」のではなく、「この配布版では利用できない」ことを管理者向けログに残す。

### P1: メニューを製品の目的に合わせて整理する

顧客向けには、次の4グループ程度に絞ります。

- **RAG設定**: ローカルLLM、埋め込み、LanceDB、チャンク設定、既定プロンプト
- **資料・ワークスペース**: ワークスペース、履歴
- **運用**: イベントログ、APIキー、セキュリティ
- **表示**: UI、チャット

音声機能は、Whisperモデルの同梱とオフライン動作が確認できた後に、RAG設定へ追加します。

### P2: 将来機能を追加する場合

- ファイルサーバー連携は、汎用ファイルシステムエージェントを有効化するのではなく、**読み取り専用・許可フォルダ固定・差分同期・監査ログ付きの資料コネクター**として実装する。
- 音声入力は、ブラウザ依存の音声認識と、同梱Whisperによる完全ローカル認識を分けて表示する。
- 文書作成は、出力先固定とユーザー確認を備えた「出典付き資料パック生成」から始める。
- MCPは、任意サーバー接続ではなく、審査済みのローカルサーバーだけを製品機能として登録する。

## 6. 今回の判定における未確認事項

今回の調査はソースコード、設定テンプレート、既存の引き継ぎ記録に基づく互換性判定です。次の項目は、Windowsのクリーン環境で実際に画面を開いて確認する必要があります。

- Windows配布物にローカルWhisperモデルが同梱され、ネットワーク遮断状態でも文字起こしできるか。
- ブラウザ標準の音声入力が、使用ブラウザ・OS設定を含めて顧客環境で動くか。
- イベントログ、APIキー、セキュリティ画面が単一ユーザー・パスワード設定済み状態で期待どおり動くか。
- 設定画面で外部プロバイダーを選択した場合に、UIだけでなくAPI側でも確実に拒否されるか。

## 7. Claude Codeへの引き継ぎ要点

- 現在のスパナメニューは上流版由来で、顧客向け製品の機能一覧としては広すぎる。
- 初回の改修対象は、`SettingsSidebar`の表示制御とプロバイダー選択肢の能力プロファイル化に限定する。
- Community Hub、Web系エージェント、クラウド連携、Telegram、モバイル、ブラウザ拡張、Docker専用エージェント、未監査の定期実行は顧客向けに表示しない。
- LLMでは既にバックエンド許可リストが存在する。埋め込み・ベクターデータベースにも同じ思想を適用し、UIとAPIの不一致を解消する。
- 音声・文字起こしは、モデル同梱とネットワーク遮断テストが完了するまで「条件付き」として扱う。
- 本メモ作成時点ではUIコードの変更は実施していない。次の作業はP0の小さな表示制御から開始する。
