## 3. 🔴 前提の訂正 ②：採点器の誤りは**甘い方向が優勢**。(b) は「見かけ上の停滞」を説明しない

`fixtures/calibration/scorer_human_labels_2026-07-27.tsv` と
`docs/SCORER_CALIBRATION_HUMAN_SHEET_2026-07-27.md` 付録A を突き合わせて集計した（型1・17件）。

| | 人=YES | 人=NO |
|---|---|---|
| 採点器=YES | **7** | **3** ← 甘い誤り |
| 採点器=NO | **1** ← 厳しい誤り | **6** |

- TPR = 7/8 = **0.875**（95%CI 0.53–0.98）
- TNR = 6/9 = **0.667**（95%CI 0.35–0.88）
- **誤りの内訳は「甘い3 : 厳しい1」。取りこぼし（厳しい誤り）は1件しかない。**

有病率補正（Rogan–Gladen）を素の 50/79 = 0.633 に当てると

```
補正後 = (0.633 + 0.667 - 1) / (0.875 + 0.667 - 1) = 0.553  →  43.7/79
```

**補正は下向きに効く。**「実際は改善しているのに採点器が見落としている」という仮説とは**逆**である。

### 3-1. ただし較正そのものが n=17 で脆い（正直な注記）

- **甘い誤り3件のうち1件（`Q11/e2`）は、現行の採点器ではすでに解消している。**
  付録Aは 2026-07-26 の `s07_judged_run1.json` から作られており、その後の
  **桁境界チェック（`normalize_marked`）と `not_preceded_by`** が入っていない。
  同じ回答を現行 `judge_element()` で採点し直すと `Q11/e2 → False`（＝人手ラベルと一致）になる。実測。
  → これを反映すると TNR = 7/9 = 0.778、補正後 = 0.629 ≈ **49.7/79**（＝素の値とほぼ同じ）。
- **残る甘い誤り2件（`Q13/e2`「30を超える手当」、`Q13/e3`「約32,000円」）は、
  シートに転記された回答本文が両方とも当該事実を明記している。**
  シート自身の判定則（「数値は合っているが表記が違う → YES」）に照らすと **YES が自然**であり、
  この2件は**人手ラベル側の誤り（または転記ずれ）の疑いが強い**。
  仮に2件とも YES なら TNR = 1.0 となり、補正後は 57/79（＝上向き）に反転する。
- **つまり n=17 では補正の向きが2ラベルで反転する。この較正だけで意思決定してはならない。**

**そこで、較正に頼らず直接確かめた。** 現行構成の欠落要素29件を1件ずつ回答本文と突き合わせた結果、
**「モデルは正しく述べているのに採点器が取りこぼした」型は 1 件（`Q07/e1`）だけ**だった（§5）。
較正が示す 12.5% の取りこぼし率とも整合する（29 × 0.125 ≒ 3.6 に対し実測1件）。
**(b-1) が停滞を説明できる規模ではない。**

| 平均 anchor_coverage@8 | **0.7228** | 0.7579 | +0.035 |
| 決定的必須要素の存在 | **61/79** | 62/79 | **+1** |
| 文脈の文字数（20問合計） | 49,835 | 86,289 | 約 1.7 倍 |

K=32 の保存データ（`gen_k32_1.json`）では **0 件**。

> **クッションは文字数を 42% に圧縮しているのに、gold 要素の損失は 1/79 にとどまる。**
> 「クッションが検索改善を打ち消している」という仮説は、**この経路については不成立**。

### 4-1. 測れていない残り（限界）

コンテナログ実測で、クッションは1問あたり **文 14〜22 / 29〜45 を残し、チャンクを 8 → 6〜8 に減らしている**。
**丸ごと捨てられたチャンク（0〜2件/問）は id が返らないため復元できない。**

生成側の損失（下記 16 件）より小さく、しかも忠実性を壊す。**クッション設定の見直しは最優先ではない。**

（※クッションON/OFFの直接A/Bは実施しなかった。ENVは docker-compose 由来でコンテナ再作成が必要であり、

## 6. 投資判断のための総合

### 6-1. パイプラインの歩留まり（実測）

```
コーパス            79 要素
   ↓  検索（hybrid + rerank K=32）        … 64/79 が文脈へ（81%）
   ↓  クッション（文抽出）                … −1（99% 通過）
```

**律速は最終段（78%）である。** 中間段の損失は 1%。

### 6-2. 追加投資の期待値（実測に基づく試算）

| 投資先 | 直接効果 | 変換率を掛けた**回答への**効果 |
|---|---|---|
| **検索をさらに改善**（Track B 6.5〜7人日） | 文脈内要素 +6〜10 と仮定 | ×0.78 → **+5〜8**（実測の前例では **+6 → +0**） |
| **生成の変換率を 0.78 → 0.95** | いま文脈にある 64 件から | **+11**（追加の検索改善なしで） |
| クッション設定の見直し | 上限 +6（条件D実測） | ハルシネーション 0→3 の代償あり |

**直近の実測が最も雄弁である。検索改善で文脈へ +6 届いて、回答は +0 だった。**

### 6-3. 推奨（優先順）

1. **A2 — 評価セットを 20 → 30〜40 問に拡張（2.0人日、再embed不要）を最優先で先に置く。**
   n=20 では McNemar が p=1.0 になり、**生成側の改善を採否判定できない**（今回も +1 は誤差範囲）。
   ここを直さないと、以下の 2. の効果を「測れない」まま人日を消費する。
   併せて **本診断で判明した評価セット側の欠陥5件を修正する**（(b-1) 1件 + (b-2) 4件、下記6-4）。

2. **Phase F（生成側）に投資する。ただし安い順に、実測で当たりを付けてから。**
   本診断で機序まで見えている順に:
   - **(a-2) 過剰拒否（2件＋既知の hakusho No.7）**: 図表由来の数値行が文脈にあるのに拒否する。
     まず「**文脈中の図表・数値行も根拠として使ってよい**」旨をシステムプロンプトに足して1runで測るのが最安。
     **`limits.system = 8192 × 0.15 = 1,229 トークン`の崖**（§2.5.9）を超えないこと。
   - **(a-1) 抽出失敗（9件）**: 「複数の事実を要求する設問で1つ答えて満足する」型。
     `Q08`/`Q17`、`Q09`/`Q18` のように**同じ本文で設問違いなら答えられている**ため、
     プロンプトまたはクエリ分解（設問を要素へ分けて複数回問う）で救える見込みが高い。
   - **(a-3) 誤選択（2件）**: 目次・見出しの可読性に依存。Track B6（印刷目次パーサ）と重なる。

3. **Track B（構造注入）は 1. と 2. の後。** 対象そのもの（C1・目次・図表）は正しい。
   ただし**いま着手すると、成果が 0.78 のフィルタを通ったうえ、n=20 では検出できない。**
   `Q01/e4,e5,e6` と `Q02` は Track B の本丸なので、**捨てるのではなく順序を下げる**。

4. **クッション設定の再チューニングはしない。** 損失 1/79。上限 +6 に対し捏造 +3 の代償。
