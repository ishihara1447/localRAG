候補Aを採用する。加えて以下2点が決め手になった。

### 候補Bを採らない理由（★判定基準に無かった項目）

1. **応答が対照の 3.6倍遅い**（中央値 17.7秒 対 4.9秒）。
   本製品は「最初の文字まで8秒以内」を顧客要件としており、**この差は要件に直結する**。
   原因は接頭辞の付与か 2048 コンテキストの処理コストと思われるが、切り分けていない。
   **判定基準に速度を入れていなかったのは事前登録の不備**であり、後から基準を足したのではなく
   「基準外だが採否を左右する事実」として記録する。
2. **Gemma Terms かつ HuggingFace ゲート付き**。オフライン配布物への同梱には
   ライセンス条項の確認が別途要る。

## 4. 生成精度（防衛白書30問・各3run・交互実行）

| 設問の種類 | 対照 `bge-m3` | **候補A granite** | 候補B gemma |
|---|---:|---:|---:|
| a) 直接事実 /8 | 8 | 8 | 8 |
| b) 数値判別 /6 | 6 | 6 | 6 |
| c) 定義説明 /6 | 5 | 5 | **4**（−1） |
| **d) 白書外（不明）/5** | **5** | **5** | **5** |
| e) 言い換え /5 | 4 | **3**（−1） | **5**（+1） |
| **合計** | **28/30** | **27/30** | **28/30** |
| 応答 中央値 | 4.9 s | 5.0 s | **17.7 s** |

**3条件とも3run が1問単位で完全に同一**（ばらつき 0）。測定の再現性は高い。

**候補Aの −1問は「言い換えて問う」設問。** 検索では対照を上回っているため、
検索の失敗ではなく生成側の差と考えられるが、**切り分けていない**（推定）。

## 5. 測定条件

- 文書: `R07zenpen.pdf`（令和7年版 防衛白書、544ページ）。**条件ごとに再埋め込み**（1,756チャンク）
- LLM は `granite4.1:8b` に固定、リランカーは `japanese-reranker-xsmall-v2` に固定
- topN=8 / `openAiTemp=0` / `chatMode=query` / 設問ごとに一意な `sessionId`
- 生成評価は **3条件を交互に実行**（bgem3→granite→gemma を1run とし、3周）
- イメージ `localrag-anythingllm:1.1.0` に、接頭辞対応ファイルのみ bind mount で差し込み
- 接頭辞: 対照と候補Aは**なし**（モデルカードに指定なし）、
  候補Bは文書 `title: none | text: ` / クエリ `task: search result | query: `

### 対照を測り直した理由

既存記録（`anchor_coverage@8 = 0.673`）は別ワークスペース・別構成の値。
**条件の違う数値を比較して誤報告する事故を5回起こしている**ため、対照も同一手順で取り直した。

## 6. ★測定を無効にしかけた罠（記録）

最初の再埋め込みが**2秒で完了**し、ログに次が出ていた。

```
Cached vectorized results ... found! Using cached data to save on embed costs.
```

**`bge-m3` のベクトルが再利用され、候補モデルは一度も動いていなかった。**
そのまま測れば「候補が対照と完全に同一」という無意味な結果が出て、
しかも**成功したように見えた**。

対処: `runtime/anythingllm-storage/vector-cache/` を条件ごとに消す。
`out/embswap/run-condition.sh` に、キャッシュ再利用をログで検知して
**エラー停止する**ガードを組み込んだ。

## 7. 前提工事（本測定のために実装）

Ollama 埋め込みエンジンに接頭辞対応を追加した（fork コミット `741f654`）。

- `NativeEmbedder` は対応済みだったが Ollama 側は **0箇所**（未実装）だった
- 配線側（`vectorDbProviders/lance/index.js:663` の `chunkPrefix`）は既に準備済みで、
  embedder 側の getter 2つと `embedTextInput` の上書きで通った
- 環境変数 `EMBEDDING_CHUNK_PREFIX` / `EMBEDDING_QUERY_PREFIX` で与える。
  **未設定なら従来と完全に同じ挙動**
- 変異注入で検出力を確認（適用を削除 → 2件 FAIL、getter を空に固定 → 1件 FAIL、復元 → 全件 PASS）

**これが無いと、接頭辞を前提に学習された候補Bが不当に不利になっていた。**

## 8. 事前の予想と結果

| 予想 | 結果 |
|---|---|
| 候補A（granite）は日本語で不利 | **外れ。検索で全 k 最良、生成も −1問に留まった** |
| 候補B は接頭辞を正しく付ければ対照と拮抗 | 的中（生成は ±0）。**ただし速度が 3.6倍遅いのは予想外** |
| どちらも P1 を満たさない可能性が相応にある | **外れ。両方とも満たした** |

## 9. ★本測定で言えないこと

- **候補Bの接頭辞が正しかったか。** HuggingFace のモデルカードと設定ファイルは
  401（ゲート付き）、Google 公式・Ollama いずれにも記載が無く、**一次情報で確認できなかった**。
  調査値を使ったため、候補Bが不当に不利／有利になっている可能性が残る
- **候補Aの −1問（言い換え設問）が検索と生成のどちらに起因するか。** 切り分けていない
- **候補Bが遅い理由。** 接頭辞か文脈長かを切り分けていない
- **配布物そのものでの挙動。** 本測定は開発環境（Docker）。Windows ネイティブ配布物では未測定
- **入力上限 512 トークンの影響。** 本測定では切り詰め警告ゼロだったが、
  より長いチャンク設定にすれば影響が出うる

## 10. 採用に伴う影響

🔴 **既存の導入先では全文書の再取り込みが必須**（1024次元 → 768次元で互換性が無い）。
新規導入なら影響ゼロ。**Release 本文の最上部に明記すること。**

副次的に、配布物が **約600MB 小さくなり**、VRAM 使用も減るため **8GB 環境には有利**。
