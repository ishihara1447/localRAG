## 【診断】Coverage@k が k に対して単調でない件（S05 実行後の追加調査）

S05 run1 で Q03（@16 0.83→@32 0.67）、Q10（0.60→0.20）、Q16（0.67→0.33）と
**k を増やすと Coverage が下がる**現象が出た。判定ロジック
「k を増やしても取れない＝索引・チャンク分割の問題」を Phase E の投資判断に使う以上、
その前提（top-k が k について入れ子）を検証した。

### 結論: **(A) 実装の性質であり、ハーネスのバグではない**

`vector-search` の返す chunk id 集合は **k について入れ子になっていない**。実測:

```
Q03  top4 ⊆ top8 : True    top8 ⊆ top16 : False (top8のみ2件)
     top16 ⊆ top32: False (top16のみ3件)   top8 ⊆ top32 : False (top8のみ4件)
Q10  top4 ⊆ top8 : True    top8 ⊆ top16 : False (1件)
     top16 ⊆ top32: False (1件)            top8 ⊆ top32 : False (1件)
Q16  top4 ⊆ top8 : True    top8 ⊆ top16 : False (2件)
     top16 ⊆ top32: False (1件)            top8 ⊆ top32 : False (2件)

同一 k を2回叩いた結果は3問とも完全一致（＝k内では決定的。ランダム性ではない）
```

ハーネス側は `{query, topN:k, scoreThreshold:0}` を素直に投げ、返ってきた
`results[]` をそのまま数えているだけである（`scripts/_retrieval.py: vector_search`）。
gold 判定・集計も手計算で追試済み（S05 の検証欄）。**(B) は否定された。**

### 原因は2つ。どちらも `anything-llm/` のコードを読んで確認した（変更はしていない）

**原因1: hybrid の候補数が topN に連動する**

`lance/index.js:96`
```js
hybridCandidateLimit(topN) { return Math.min(50, Math.max(20, topN * 4)); }
```
→ topN=4→20 / 8→32 / 16→50 / 32→50。
`hybridSimilarityResponse` は dense 側・FTS 側をそれぞれこの候補数で切ってから
RRF 融合する（`lance/index.js:341-400`）。候補集合が変われば
「dense にしか出ていなかった文書が FTS 側にも出る」等で RRF スコアの相対関係が変わり、
融合後の順位は入れ子にならない。

ただし **k=16 と k=32 は候補数が同じ 50** である。それでも `top16 ⊄ top32` になるので、
これだけでは説明がつかない。主因は次である。

**原因2（主因）: 文抽出クッションが「文の総数」で上限を持ち、チャンクを間引く**

`lance/sentenceCushion.js`
- 全チャンクの文をフラットに並べ、reranker で全文スコアリング
- **上位 `SENTENCE_CUSHION_TOPK`（既定 8）文＋その隣接1文だけを残す**
- **採用文を含むチャンクだけで result を組み直し**、ベスト文スコア順に並べ替える

実行中のコンテナログ（直接の証拠）:
```
sentence-cushion chunks  4 ->  4, sentences kept 15/21
sentence-cushion chunks  8 ->  7, sentences kept 21/44
sentence-cushion chunks 16 ->  8, sentences kept 21/83
sentence-cushion chunks 32 ->  8, sentences kept 23/150
```

**残る文の数は topN によらず 18〜24 でほぼ一定**である（分母だけが 21→150 と増える）。
つまり **LLM に届く情報量の上限は topN ではなく `SENTENCE_CUSHION_TOPK` が決めている**。
topN を増やすと候補文が増えるぶん競争が激しくなり、
**gold の文が他チャンクの文に押し出されて消える**。これが Coverage の低下の正体である。

### この事実が S05 の判定ロジックに与える影響

- 「k を増やせば取れる／取れない」という切り分けは、
  **『素の検索アルゴリズムの recall』ではなく『topN を上げるという運用施策が効くか』の切り分け**である。
  後者こそ実務上の判断対象なので、**Phase E の投資判断の根拠としては引き続き有効**。
  ただし表現は「k を増やしても取れない＝索引・チャンク分割の問題」ではなく
  **「topN を上げても LLM に届かない」**と読むべきである
- 「索引の問題」に分類した5問（Q02/Q03/Q04/Q10/Q16）のうち、
  **Q03/Q10/Q16 の3問は『クッションに押し出された』ことが下落の原因**であり、
  索引・チャンク分割だけでなく **クッションの文数上限も併せて疑う必要がある**
- **本システムでは「topN を上げれば recall が上がる」という一般的前提が成り立たない。**
  Phase F 以降で topN を触る施策を検討する場合、`SENTENCE_CUSHION_TOPK` を
  同時に動かさないと意味がない。これはロードマップに無い観点である

### 副次的な注意点（記録）

- `returned` 件数は常に topN 以下（topN=32 でも 8〜14件）。これはクッションの間引きの結果であって
  「文書が足りない」わけではない
- Q03 の topN=32 で `page=None` が2件出た。クッション後テキストが短すぎて（12字未満の文しか残らず）
  ページ索引に照合できなかったもの。全80回の検索のうち2件のみで、指標への影響は軽微

## S07. `--phase report`（3run・クラスタブートストラップCI・McNemar）⚠️条件付き完了

### 変更内容

`scripts/complex-eval.py --phase report`。

- 3run の**平均・最小・最大を必ず併記**（単発値の単独表記を禁止する §7-4-2 への対応）
- 要素カバー率の **クラスタブートストラップ95%CI**（リサンプル単位=**設問**、1,000回、seed固定）
- 完全正答率の **Wilson score interval**
- A/B比較時の **McNemar 検定**（要素単位・設問単位の両方、両側の厳密二項検定）
- 判定則（§7-3）を**コードに埋め込んで自動判定**: (a) CIが重ならない かつ
  (b) McNemar p<0.05 かつ (c) 3run全てで改善方向が一致 → それ以外は「差は誤差範囲」
- カテゴリ C1〜C6 別に必ず分解

報告フォーマットは §7-2 の指定どおり:
`要素カバー率 0.608 [95%CI 0.508–0.716]（3run: 0.608 / 0.608 / 0.608）`

### 検証結果

**テスト1（偽陽性を出さないこと）: 同一条件で2セット（各3run）→ ✅ PASS**

topN=8 の run1-3 を条件A、run4-6 を条件B（**まったく同じ設定**）として比較:

```
条件A: 要素カバー率 0.608 [95%CI 0.508–0.716]（3run: 0.608/0.608/0.608）完全正答率 0.350
条件B: 要素カバー率 0.608 [95%CI 0.508–0.716]（3run: 0.608/0.608/0.608）完全正答率 0.350
  McNemar(要素単位) b=0 c=0 p=1.0000 (n=79要素)
  McNemar(設問単位) b=0 c=0 p=0.5000 → b=0 c=0 p=1.0000 (n=20問)
  (a) CIが重ならない: False / (b) p<0.05: False / (c) 方向一致: False
  → **差は誤差範囲**
```

**テスト2（既知の差を検出できること）: topN=8 vs topN=4 → ❌ FAIL（有意差を検出できなかった）**

```
条件A(topN=8): 要素カバー率 0.608 [95%CI 0.508–0.716]（0.608/0.608/0.608）完全正答 7/20
条件B(topN=4): 要素カバー率 0.536 [95%CI 0.432–0.643]（0.544/0.532/0.532）完全正答 5/20
  カテゴリ別で最も落ちたのは C5 推論・含意: 0.500 → 0.100
  McNemar(要素単位) b=7 c=2 p=0.1797 (n=79要素)
  (a) CIが重ならない: False / (b) p<0.05: False / (c) 3run方向一致: True
  → **差は誤差範囲**
```

**実差は確かに存在する**（要素カバー率が7ポイント低下、完全正答が7→5、C5が0.50→0.10、
topN=4 では20問すべてで回答本文が変わっている）。にもかかわらず有意にならない。

**原因は実装の誤りではなく、検出力（統計的パワー）の不足である。** 手計算で追試した:

```
n要素=79  b(topN8で正/topN4で誤)=7  c(逆)=2  不一致ペア=9
両側二項検定 p = 2*(1+9+36)/2^9 = 0.1797
不一致ペアが9件では、仮に全て片側に寄っても（b=9,c=0）p=0.0039 が下限
```
McNemar は不一致ペアの数だけで検定するため、**79要素・不一致9件では 7:2 の偏りを有意にできない**。
これは設計書 §9-2 の「20問は方法論調査の推奨（開発コア50〜100問）を下回る」という
既知の限界が、**実測で確認された**ということである。

**結論**: 判定則そのものは正しく動いている（偽陽性を出さず、実差があっても
根拠不十分なら「誤差範囲」と正しく言う＝**保守側に倒れている**）。
ただし**このセット単体では topN 半減程度の差を検出できない**。
S07 の受け入れ条件のうち「既知の差を検出できる」は**未達**であり、
Phase B 以降でこの評価セットをA/B判定に使う場合は次のいずれかが必要:

1. **設問を30〜40問に拡張する**（設計書 §9-2 の推奨。要素数が増えれば不一致ペアも増える）
2. **retrieval 指標（Coverage@k）を主判定にする** — 決定的でrun間のブレが無く、
   実際 topN=8 vs 4 では Coverage@8 0.798 → 0.638 と明確に差が出ている（S05 の表）。
   設計書 §7-3 も「まず retrieval で差が出るかを見るのがノイズに強い」としている
3. 差が小さい施策については「有意でない」と正直に記載して次へ進む

### ★副次的な重大発見: generation は本環境では完全に決定的だった

topN=8 の**6 run すべてで回答本文がバイト単位で一致**した（20問×6run）。

```
run1 vs run2/3/4/5/6: 一致=True 差分のあった設問=[]
```

内部監査 §3-2 の「同一設定の再実行で 19/20/21/24 と5点ぶれる」という前提と食い違う。
一方 topN=4 では run 間で5問（Q02/Q06/Q08/Q12/Q13）の回答が揺れており、
**非決定性は存在するが条件依存**である。

**仮説（要検証）**: complex-eval は設問ごとに一意な `sessionId` を振っているのに対し、
**`hakusho-eval.py` は `sessionId` を一切指定していない**（同一セッションに30問が積まれる）。
本セッションで hakusho-eval が 27/28/29 と揺れたのは、GPUの非決定性ではなく
**チャット履歴の蓄積状態がrun間で異なることに起因する交絡**である可能性がある
（`openAiHistory=20` なので直前20件が毎回コンテキストに入る）。
もしそうなら、既存ベースラインのノイズの一部は**ハーネス由来で除去可能**である。

**確認方法（未実施）**: `hakusho-eval.py` に `sessionId` を追加した版と現行版を各3run回して
分散を比較する。ただしこれは**既存ベースラインの定義を変える変更**なので、
本タスクの制約（既存3本のスコアを動かさない）に抵触する。**ユーザー判断を仰ぐべき事項**として記録する。
