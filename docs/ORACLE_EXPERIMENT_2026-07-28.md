### 1-1. 何を変えるか（1回に1つ）

**検索経路だけを差し替える。** 生成側（モデル・システムプロンプト・temperature・文脈の整形方法）は一切変えない。

| | 内容 |
|---|---|

### 1-2. 測定手段（**ワークスペースを新規作成せずに oracle を実現する方法**）

AnythingLLM の chat API は「文脈を外から差し込む」口を持たない（`attachments` は collector 経由で
`storage/documents` を汚す）。ワークスペースの新規作成は禁止されている。
そこで **生成段（AnythingLLM → Ollama の呼び出し）を、フォークの実装どおりに Python で再現**して
製品の Ollama（`rag-ollama` コンテナ, `gemma4:12b`）を直接叩く。

再現した実装（すべて `anything-llm/` を**読んだだけ**。1バイトも変更していない）:

| 要素 | 実装 | 出典 |
|---|---|---|
| system メッセージ | `systemPrompt + "\nContext:\n" + 各chunkを整形して連結` | `server/utils/AiProviders/ollama/index.js` `constructPrompt()` / `#appendContext()` |
| chunk の整形 | 本文冒頭が `（出典: <title>）\n` なら `[出典: <title>]\n<本文>\n[出典 <title> ここまで]\n\n` に昇格（フォーク独自改修） | 同上 |

### 1-4. 🔴 gold チャンクの構成規則（**結果を見る前に凍結する**）

1. **候補プール**: 当該ワークスペースの LanceDB テーブルの**全チャンク**（1,756件、実測）の
   **生本文**（クッション前）。`<document_metadata>…</document_metadata>` ブロックは除去する
   （証拠ではなく、通常モデルが見る post-cushion テキストにも含まれないため）。
2. **被覆判定**: チャンク `t` が要素 `e` を被覆する ⇔ **採点器そのもの**
   `complex-eval.judge_element(t, e)` が True。**採点基準を変えないという要請を、gold の定義にも適用する。**
3. **貪欲な集合被覆**: 未被覆の required `[N]`/`[E]` 要素を最も多く被覆するチャンクを1つずつ採る。
   同数の場合のタイブレークは (a) **gold ページ上にあるチャンク**（`pageNumber` が `gold_pages[].phys ± 1` に入る）を優先 →
   (b) 含む anchor 数が多い → (c) `pageNumber` 昇順 → (d) `id` の辞書順（**完全に決定的**）。
4. **上限 8 チャンク**（＝製品既定 topN=8）。「本を丸ごと渡す」ことを避け、文脈長を現行と比較可能に保つ。
5. **水増ししない**（8に満たなくてもパディングしない）。
6. **並び順**: 貪欲に採った順（被覆の大きい順）。
7. **どのチャンクにも存在しない要素は、存在しないまま**にする。分母 79 を変えない。

> この規則は「取りうる最良の検索結果」を機械的に構成するものであり、**検索器を gold 供給に置き換える**
> という標準的 oracle-RAG ablation（BERGEN 他）の定義に一致する。

### 3-6. 🔴 変換率 — 本実験の核心

「文脈内に証拠がある要素」と「回答に現れた要素」を、**同じ凍結採点器**で数え直した。

| 条件 | 文脈内 | 回答内 | 文脈内**かつ**回答内 | 文脈外だが回答内 | **変換率（厳密）** |
|---|---|---|---|---|---|
| A1 / A2 | 61/79 = 0.772 | 49 | 47 | 2 | **0.770** |
| R1 / R2 | 61/79 = 0.772 | 49 | 47 | 2 | **0.770** |
| **O1** | **75/79 = 0.949** | 60 | 58 | 2 | **0.773** |
| **O2** | **75/79 = 0.949** | 61 | 59 | 2 | **0.787** |

- **文脈へ届く量を +14要素（+23%）増やしても、変換率は 0.770 → 0.773/0.787 でほぼ動かない。**
- 「文脈外だが回答内」の2件はいずれも `Q07/e3`(51件)・`Q07/e4`(21件)。
  原典の表記が裸の `51` `21` で alias が `51件` `21件` のため文字列一致しないが、モデルは `件` を付けて述べている。
  **`EVAL_SET_DEFECT_FIX_2026-07-28.md` §5-2 の Watch W2 そのもの**であり、本作業では触っていない。

**この 0.77〜0.79 という値が、モデルの能力上限の実体である。**
仮に検索が完璧になって 79/79 を文脈へ届けても、期待される回答内要素は **79 × 0.78 ≒ 62/79 = 0.78** にとどまる。

一方で、**新たに届いた14要素のうち12件は回答に現れた（12/14 = 0.86）**。
診断レポート（`GENERATION_GAP_DIAGNOSIS_2026-07-27.md` §0）の
「リランクで文脈内 +6 に対し回答内 +0」という観測は、**この規模では再現しなかった**。
→ **「証拠を追加で届けても回答は増えない」は成り立たない。増える。ただし 0.78 の率でしか増えない。**

### 3-8. 過剰拒否 (a-2) の追試 — **oracle でも解消しない**

`Q12`（防衛関係費の使途別内訳。図表Ⅱ-3-2-4 の行）:

## 7. 限界（誇張しないための注記）

1. **oracle 文脈は「最小の gold 集合」であり、「gold チャンク8件」ではない。**
   実測で平均 1.65 チャンク・799字。distractor がほぼゼロの**極めて有利な条件**である。
   したがって 0.766 は **「焦点化された理想の文脈を与えたときの上限」**であって、
   「topN=8 の枠を gold で埋めたときの値」ではない。後者は hard negative の影響で**もっと低くなりうる**
   （調査 §2-2: 強い検索器ほど hard negative が有害で性能は逆U字）。
2. **上限が過小評価されている可能性**: 2要素（`Q01/e1` `Q19/e2`）は**どのチャンクにも存在しない**ため、
   構造的に到達不能である。この2件を分母から外すと 61/77 = 0.792 になるが、
   **分母を動かさない**という原則に従い 79 のまま報告している。
3. **n=20（79要素）の検出限界は概ね15pt**（`EVAL_PROTOCOL` §4）。
   §3-5 のとおり判定則では「差は誤差範囲」であり、**「oracle にしたら改善した」とは主張していない。**
   本書が主張しているのは **上限値の絶対水準が 0.60〜0.85 の区分に入る**ことだけである。
4. **oracle は 2run で1要素揺れた**（§3-3）。`temperature=0` でも完全決定ではない。
5. **gold の構成規則は我々が決めたものである。** 別の規則（例: gold ページの本文をそのまま渡す、
   8チャンクまで水増しする）なら別の値が出る。規則は §1-4 に全文を凍結してあるので追試可能。
6. **[P]（命題）要素は測っていない**（judge の κ=0.536 で不採用のまま）。
   主指標は決定的要素カバー率であり、本実験もそれに従っている。
7. **1回の測定は complex 20問のみ。** `hakusho-eval` は §2.5.17 により判断根拠に使っていない。
