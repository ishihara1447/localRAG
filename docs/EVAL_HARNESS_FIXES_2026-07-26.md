### 1-2. なぜ交絡するのか（コードで確認した機序）

`anything-llm/server/utils/chats/index.js:61-81` の `recentChatHistory()` は

```js
api_session_id: apiSessionId || null,   // ← sessionId 未指定なら NULL セッションを引く
```

で履歴を引き、`apiChatHandler.js:237` の `messageLimit = workspace?.openAiHistory || 20` 件を
**プロンプトに載せる**。本ワークスペースは `openAiHistory = 20`。

つまり `sessionId` を送らないと、**直前20件の質疑（他設問の回答や過去の手動テスト）が毎回コンテキストに入る**。
30問を順に投げれば、i問目は「同runのi-1問目まで＋前runの後半」を見ることになり、
**履歴の中身がrunごとに違う** ＝ 条件が固定できない。
実測でも、実験開始時点で既定セッション（`api_session_id IS NULL`）には
白書ワークスペースだけで**120件**の過去チャットが積まれていた。

## タスク2: `scale-eval.py` のワークスペース削除漏れ

### 2-1. 原因（コードを読んで確定。`anything-llm/` は変更していない）

- `runtime/docker-compose.yml:87` に **`WORKSPACE_DELETION_PROTECTION=1`**
- `anything-llm/server/utils/middleware/workspaceDeletionProtection.js` は
  この環境変数が**存在するだけで**（値によらず）**403** を返す
- `scale-eval.py` は `client.delete(...)` の**戻り値を見ていなかった**ため、403 が沈黙していた

実測（存在しない slug に対する安全なプローブ。ミドルウェアは slug 解決の前に応答する）:

```
status: 403
body  : {"success":false,"error":"Workspace deletion is blocked by the system administrator."}
```

### 2-2. ★重要な訂正: **UI からも削除できない**

Phase A の記録は「UIから手動削除する（APIでは消せない）」としていたが、これは**誤り**である。
`workspaceDeletionProtection` は**3つの削除経路すべて**に付いている:

| 経路 | ファイル:行 | 用途 |
|---|---|---|
| `DELETE /api/v1/workspace/:slug` | `endpoints/api/workspace/index.js:230` | 開発者API（スクリプトが使う） |
| `DELETE /workspace/:slug` | `endpoints/workspaces.js:279` | **UI の削除ボタン** |
| `DELETE /admin/workspaces/:id` | `endpoints/admin.js:300` | 管理者画面 |

したがって、この環境変数が有効な限り**どの経路でも削除できない**。

### 2-3. 回避手段の調査結果

**評価実行時だけ保護を回避する正当な手段は存在しない。** 根拠:
- ミドルウェアは**リクエスト単位のオプトアウトを持たない**（ヘッダ・クエリ・ロールによる例外なし）。
  判定は `"WORKSPACE_DELETION_PROTECTION" in process.env` の1行のみ
- 環境変数はサーバプロセス起動時に固定されるため、**コンテナを作り直さずに外すことはできない**

→ **結論: 手動での後始末が必要**。唯一の正当な手順は次のとおり（**本作業では実行していない**）:

1. `runtime/docker-compose.yml` の `WORKSPACE_DELETION_PROTECTION=1` を一時的にコメントアウト
2. `docker compose up -d`（コンテナ再作成）
3. UI から対象ワークスペースを削除
4. 環境変数を戻して再度 `docker compose up -d`

**削除は不可逆であり、この作業には `runtime/` の変更とコンテナ再作成を伴うため、
本セッションでは一覧の提示に留めた。実行はユーザー判断。**

### 2-4. 現在漏れているワークスペースの一覧（実測）

## タスク3: Q19 に `gold_pages` を与える

### 3-1. 与えた gold と、その根拠

**正しく否定するには「本白書が第Ⅰ部〜第Ⅴ部の5部構成である」という事実を引けている必要がある**。
そこで目次ページを gold とした。

| phys | page（印字） | weight | 根拠 |
|---:|---|---:|---|
| **5** | null（目次1ページ目） | **2** | 「本文第Ⅰ部～第Ⅴ部の記述について」という**5部構成を直接示す唯一の記述**。実測（`PageIndex.count`）で全544ページ中 **1箇所のみ**（`第Ⅰ部～第Ⅴ部` の出現回数 = 1、出現ページ = phys 5） |
| 6 | null | 1 | 目次の続き（補助） |
| 7 | null | 1 | 目次の続き（補助） |
| 8 | null | 1 | 目次の続き（補助） |

物理5〜8が目次であることは実測で確認済み（`PHASE_A_IMPLEMENTATION_2026-07-26.md` §0-1 と同じ `PageIndex` で本文を目視）。
weight は **5部構成を直接立証できる phys 5 だけを必須(2)、残りの目次3ページを補助(1)** とした。
同じ目次を gold に持つ Q01（各部のタイトルを列挙させる設問）は4ページとも weight 2 だが、
Q19 が必要とするのは「5部しかない」という一点であり、それは phys 5 の1行で立証できるためである。

アンカー方式の集計母数（n=19問）を動かさないため。ページ方式のみ n=20 になる。
