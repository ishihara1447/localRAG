# OTE-RAG アイデアメモ: 音声入力とファイルサーバ連携

作成日: 2026-07-24
状態: アイデアのストック。実装未着手。

## 1. アイデアの概要

OTE-RAGに次の2つの入口を追加する。

1. **音声入力**: マイクから日本語の質問を入力し、文字起こし結果を確認してからRAG検索を実行する。
2. **ファイルサーバ連携**: Windowsの共有フォルダや社内ファイルサーバ上の顧客資料を、アップロードせずにRAGの対象として同期・検索する。

組み合わせると、利用者は例えば次のように操作できる。

> 「昨年度の契約更新に関する注意点を、根拠ページ付きでまとめて」

音声を文字に変換し、許可されたファイルサーバの資料を検索し、引用付きの回答を返す。資料のアップロードや長い質問文の入力を減らせるため、現場利用との相性がよい。

## 2. 期待する顧客価値

### 音声入力

- キーボード入力が難しい利用者でも使いやすい
- 長い質問、専門用語、会議中の確認事項を入力しやすい
- 車内、現場、窓口など、手がふさがっている場面に対応できる
- 日本語の質問を自然な形で入力できる
- 将来は会議録、決定事項、アクションアイテムの整理へ拡張できる

### ファイルサーバ連携

- 顧客資料を別の場所へ手動コピー・アップロードする手間を減らせる
- 既存のフォルダ構成をそのままナレッジの入口にできる
- ファイルの追加・変更・削除を検知し、RAGの内容を更新できる
- 顧客の業務フローを変えずに導入しやすい
- 社内NAS、Windows Server、部門共有フォルダなど、現場の実データに近い

## 3. 最初に想定する仕様

### 3.1 音声入力の初期仕様

| 項目 | 初期案 |
|---|---|
| 入力 | 画面のマイクボタン、または押している間だけ録音するプッシュ・トゥ・トーク |
| 認識 | ローカル音声認識モデル。音声を外部サービスへ送信しない |
| 言語 | 日本語を優先。数字、日付、固有名詞、専門用語を確認しやすくする |
| 確認 | 認識結果をテキストで表示し、利用者が修正してから検索できる |
| 保存 | 音声ファイルは既定で保存しない。保存する場合も利用者が明示的に選択する |
| 実行 | 初期段階では「音声で質問する」ことに限定し、削除・送信などの操作は音声から直接実行しない |

「録音開始から即時実行」ではなく、**文字起こし結果を一度確認する**ことを初期原則とする。誤認識した質問で機密資料を検索したり、将来のツール連携を誤操作したりするリスクを下げられる。

### 3.2 ファイルサーバ連携の初期仕様

| 項目 | 初期案 |
|---|---|
| 対象 | Windows共有フォルダ、UNCパス、社内NAS。まずSMB/CIFSに限定 |
| 権限 | 読み取り専用。既存のWindows/共有フォルダ権限を尊重 |
| 認証 | Windowsの資格情報を優先。パスワードを平文で設定ファイルへ保存しない |
| 同期 | 手動同期、定期スキャン、変更・追加・削除の差分検知 |
| 対象選択 | 共有全体ではなく、利用者が指定したフォルダ単位 |
| 状態表示 | 同期中、完了、失敗、権限エラー、未対応形式、削除反映済みを表示 |
| 検索 | OTE-RAGのBM25・ベクトル・再ランキングの既存経路へ接続 |
| インデックス | 初期はOTE-RAGを実行するWindows PC内に作成。元ファイルはファイルサーバに残す |
| 更新 | 更新日時・サイズ・ハッシュなどで変更を検知し、不要な再埋め込みを避ける |

重要なのは、ファイルサーバを単なる「一括コピー元」にしないことである。ファイルの更新、削除、権限変更、接続断を扱える同期機能として設計する。

## 4. 想定ユースケース

1. **士業・法務**: 音声で相談内容を入力し、契約書・規程・過去案件の根拠を確認する。
2. **営業**: 顧客との会話後、共有フォルダの提案書・仕様書・FAQから回答案を作る。
3. **製造・保守**: 現場で質問を音声入力し、点検手順・障害履歴・マニュアルを検索する。
4. **社内ヘルプデスク**: 「この申請に必要な書類は何か」と尋ね、総務・情シスの共有資料から出典付きで回答する。
5. **会議後の整理**: 録音を常時保存するのではなく、必要な発言や確認事項を短く音声入力し、関連資料と照合する。

## 5. 技術的な課題

### 音声入力

- 日本語の固有名詞、法律用語、製品名、数字の誤認識
- 音声認識モデルがLLMと同時にGPUを使用する場合のVRAM競合
- ストリーミング認識時の遅延と、停止・再開の扱い
- マイク権限、複数マイク、入力音量、周囲の雑音
- 音声認識結果をRAG検索向けに整形する際の誤った補正
- 音声データ、文字起こし、検索ログの保存範囲

### ファイルサーバ

- SMB接続断、サーバ停止、ネットワーク遅延、ロック中のファイル
- UNCパス、ドライブレター、シンボリックリンク、循環参照
- 共有権限とNTFS権限の組み合わせ
- 利用者ごとの閲覧権限を、ローカルインデックス検索で漏らさないこと
- 大量ファイルの初回インデックス時間と、更新時の負荷
- ファイル名変更、移動、削除、同一ファイルの重複
- インデックス側に残った削除済み資料の扱い
- PDF、Office、スキャン文書、表、画像などの抽出品質

## 6. セキュリティと製品原則

このアイデアは、OTE-RAGの「顧客資料を外部へ送らない」という方針と相性がよい。ただし、ファイルサーバ連携によって検索対象が広がるため、次を必須条件とする。

- 音声認識はローカル実行を基本とし、クラウド音声APIは既定で無効
- ファイルサーバは読み取り専用から開始
- 資格情報をログ、環境変数、設定ファイルへ不用意に残さない
- 接続先と対象フォルダを利用者が明示的に選択する
- 同期対象・同期時刻・エラー・削除反映を監査可能にする
- 回答の引用元に、共有名・フォルダ・ファイル名・ページを表示する
- ファイル内容に含まれる命令文を、システム命令やツール実行命令として扱わない
- 将来のMCP・ファイル操作連携では、読み取り専用、確認付き書き込み、削除禁止を初期値にする

## 7. 段階的な実装候補

| 段階 | 内容 | 判定基準 |
|---|---|---|
| Phase A | マイクボタン、ローカル文字起こし、テキスト修正、RAG検索 | 日本語質問を修正可能な形で安定して検索できる |
| Phase B | UNCパスの手動接続、読み取り専用、手動同期 | 指定フォルダの資料を引用付きで検索できる |
| Phase C | 定期同期、差分更新、削除反映、状態画面 | ファイルサーバの変更が再現可能にインデックスへ反映される |
| Phase D | 音声とファイルサーバの統合、引用付きEvidence Pack | 音声質問から根拠付き報告書を作成できる |
| Phase E | 音声会議、話者分離、読み取り専用MCP/API | 利用場面を広げても権限・証跡を維持できる |

## 8. 優先度の仮置き

- **ファイルサーバ連携: P1候補**。顧客資料の同期問題を解消し、日常利用に直結する。
- **音声入力: P1〜P2候補**。実装は比較的小さく始められるが、認識品質と利用場面の検証が必要。
- **音声会議アシスタント: P2候補**。価値は大きいが、保存・話者分離・GPU負荷・個人情報の扱いが増える。

初期実装の組み合わせとしては、次が現実的である。

1. 音声入力を「質問テキストの作成」に限定する。
2. ファイルサーバ連携を「指定フォルダの読み取り専用同期」に限定する。
3. 両方を既存の検索・引用表示へ接続する。
4. ツール実行や自動送信は後回しにする。

## 9. 次回検討時の確認事項

- 顧客環境のファイルサーバはWindows Server、NAS、Linux Sambaのどれが多いか
- OTE-RAGを実行するPCが、共有フォルダの全資料を読める前提でよいか
- 利用者ごとに異なる権限を必要とするか、まずは管理者が指定した共有フォルダだけでよいか
- 音声入力の主用途は単発質問、会議後メモ、現場作業のどれか
- 音声認識モデルを常駐させるか、ボタン押下時だけ起動するか
- 共有フォルダの資料をPC内へ一時保存することを顧客が許容するか
- 顧客資料の更新頻度とファイル数はどの程度か
