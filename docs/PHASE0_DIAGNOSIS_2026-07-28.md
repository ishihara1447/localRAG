## 🔴 先に読む — 5行の結論

1. **天井 0.712 の犯人は「候補生成」でも「reranker」でもない。**
   候補プール(K=32)には既に **0.914** のアンカーが入っている（K=128 なら 0.957）。
   そこから **上位8件への切り捨てで −0.103**、**文抽出クッションで −0.099** 落として 0.712 になる。
2. **cross-encoder は集計では改善している**（RRF top8 0.774 → 0.811, +3.7pt）。
   ただし **C5 推論・含意（−9.8pt）と C6 回答不能（−7.7pt）では悪化させている**。
3. **「数値が取れていない」は 166問では成立しない。**
   数字を含むアンカーの最終取得率 **0.789** に対し、含まないアンカーは **0.699**。
   数値質問で reranker が有害という T²-RAGBench の報告も**再現しなかった**（+11件改善）。
4. **オラクル文脈でも要素カバー率は 0.765/0.766 が上限**（現行 0.675）。**変換率 0.777/0.778 は動かない。**
   検索を完璧にしても伸びは **+9pt** で、残り 23% は生成側である。
5. **→ Phase 1（coarse-to-fine）が本命。Phase 2（数値正規化 + 凸結合）は前提が実測で崩れたので優先度を下げる。**

### 0-3. 測定手段 — 「製品を変えずに中間結果を取る」方法と、その妥当性の実証

### 1-3. 🔴 判定 — 「reranker が沈めている」でもない

事前に想定された分岐は「1段目 >> 最終 → 犯人は reranker」だったが、**実測はそうならなかった。**

- **cross-encoder は改善している**: RRF top8 の 0.774 → cross-encoder top8 の **0.811（+3.7pt）**。
- top32 の集合は cross-encoder の前後で同一（順序が変わるだけ）なので **0.914 のまま**。
  つまり **reranker が候補を「捨てている」ことは無い**。順序だけを変えている。
- arXiv:2411.11767 の "phantom hits"（K を増やすと retrieval 単独より悪化）は、
  **本コーパス・本設問セットでは集計上は再現しなかった**（ただしカテゴリ別では再現する。§1-4）。

**したがって天井 0.712 の主因は、reranker の質ではなく
「32件の候補プールを8件に切り、さらに8文に切る」という 2 回の絞り込みそのものである。**

### 1-3-1. アンカー単位で数えた損失（分母 584）

| 損失の種類 | 件数 | 割合 | カテゴリ内訳 |
|---|---:|---:|---|
| **候補プール(K=32)には在るが上位8件に入らなかった** | **53** | 9.1% | C1 7 / C2 14 / C3 4 / C4 10 / **C5 12** / C6 6 |
| **上位8件の生本文には在るがクッションで落とされた** | **59** | 10.1% | C1 5 / C2 14 / C3 5 / **C4 26** / C5 7 / C6 2 |

**合わせて 112 アンカー（584 の 19.2%）が「一度は取れていたのに文脈に届かなかった」。**
アンカー単位（micro）で見ると、候補プール(K=32) に入っている **544/584 = 0.931** から、
最終的に文脈へ届くのは **428/584 = 0.733** である（後者はベースライン §2-1 の micro 値と一致）。

- **C4 要約の損失はクッションに集中（26/30件）**
- **C5 推論・含意の損失は上位8件への切り捨てに集中（12/19件）**

**この 2 つは対処法が違う。** C4 は文予算、C5 は候補の順位付けである。

### 1-5. この結果が Phase 1（coarse-to-fine）に与える意味

- **証拠は既に候補プールの中にある（0.914 @K=32、0.957 @K=128）。**
  「取れていない」のではなく「捨てている」。
- Phase 1 が想定していた上限は `page_coverage = 0.946` だったが、
  **`anchor` ベースでも候補プール段階で 0.914〜0.957 が既に取れている**ことが分かった。
  ページ展開に頼らずとも、**「候補32件の中から文を選び直す」だけで大半が回収できる可能性がある**（推測）。
- ただし `anchor_coverage` の**理論上限は 0.980**（§5-4）であり、1.00 ではない。

## 2. D2: 数値質問の層別と、reranker が有害でないかの確認

### 2-1. アンカー単位の層別（n=584）

| 段 | 数字を含むアンカー(218) | 数字を含まないアンカー(366) |
|---|---:|---:|
| dense@128 | **0.963** | 0.932 |
| BM25@128 | **0.963** | 0.940 |
| RRF(K=128)@128 | **0.977** | 0.954 |
| RRF(K=32)@32（候補プール） | **0.931** | 0.921 |
| cross-encoder後@32（同一集合） | 0.931 | 0.921 |
| **1段目 RRF top8** | **0.826** | 0.757 |
| **2段目 cross-encoder top8** | **0.876（+11件）** | 0.809（+19件） |
| **3段目 クッション後（最終）** | **0.789** | 0.699 |

**🔴 どの段でも数値アンカーのほうが取得率が高い。** 「数値が取れていない」という前提は
166問セットでは成立しない（§3-5 に長さ・カテゴリでの交絡確認あり）。

### 2-2. reranker は数値質問で有害か → **有害ではない（改善している）**

| 層 | top8 の変化（RRF → cross-encoder） | プール内の平均順位変化 |
|---|---|---|
| 数値アンカー（n=203 がプール内） | 180 → **191**（+11件, 0.826→0.876） | **−0.84 位（上昇）** 上昇69 / 不変99 / 下降35 |
| 非数値アンカー（n=337 がプール内） | 277 → **296**（+19件, 0.757→0.809） | **−1.35 位（上昇）** 上昇122 / 不変138 / 下降77 |

**end-to-end（reranker ON/OFF をクッションまで通した A/B、§1-1-1）でも同じ結論になる:**

| 層 | reranker OFF | reranker ON | Δ |
|---|---:|---:|---:|
| **数値アンカー（218）** | 160/218 = 0.734 | **172/218 = 0.789** | **+0.055** |
| 非数値アンカー（366） | 239/366 = 0.653 | **256/366 = 0.699** | +0.046 |

**数値アンカーのほうが reranker の恩恵が大きい（+5.5pt vs +4.6pt）。**

**T²-RAGBench（arXiv:2506.12071）の「reranker が Base RAG より悪化（MRR@3 30.3 vs 36.9）」は、
本コーパス・本設問セットの数値アンカーでは再現しなかった。**
したがって **`QUALITY_PLAN_UPDATE` §3 D2 が条件付きで用意していた
「数値質問だけ reranker をバイパスする分岐」は、実装する根拠が無い。**

### 2-3. 設問単位の層別（必須 `[N]` 要素の有無）

| 層 | 1段目 RRF@8 | 2段目 rerank@8 | 3段目 final@8 | 1段目 RRF@32 |
|---|---:|---:|---:|---:|
| 必須 `[N]` あり（128問） | 0.788 | **0.845** | 0.756 | 0.932 |
| 必須 `[N]` なし（37問） | 0.726 | **0.694** ⬇ | 0.559 | 0.852 |

**`[N]` を持たない37問（C5/C6 に偏る）でのみ reranker が悪化させている。**
§1-4 と同じ現象を別の切り口で見たものである。

### 2-4. 🔴 したがって層別すべき軸は「数値か否か」ではない

**実測が示した有害領域は C5（推論・含意）/ C6（回答不能）である。**
両者に共通するのは「**質問文に答えの語が出てこない**」こと
（C6 は「無いこと」を言うため、C5 は含意を問うため）。
cross-encoder はクエリと文書の**語彙的・意味的な直接照合**をするので、
この構造では 1段目（BM25 の低DFトークン一致を含む）より不利になる、と考えられる。
※ **この機構の説明は推測**であり、アブレーションで確かめていない。

## 3. D3: bge-m3 トークナイザと日本語bi-gram BM25 の実測

### 3-1. 使ったトークナイザが本当に bge-m3 のものであることの確認

bge-m3 は Ollama 経由（GGUF）で動いており、HF の `tokenizer.json` は同梱されていない。
そこで **Ollama が実際にロードしている GGUF ブロブ
（`sha256-daec91ff…`, 1,157,671,200 バイト）を直接パースし**、
同梱の `bge-reranker-v2-m3-ONNX/tokenizer.json` と語彙を突き合わせた。

```
GGUF v3 / general.architecture=bert / tokenizer.ggml.model = t5（SentencePiece Unigram）
tokenizer.ggml.tokens : 250,002 件      tokenizer.json の vocab : 250,002 件
  トークン文字列の不一致 : 1件（index 250001 の <mask> / [PAD250000] のみ）
  Unigram スコアの不一致 : 1件（同上）
```

**→ bge-m3 と bge-reranker-v2-m3 のトークナイザは（マスクトークンの名前を除いて）同一である。**
以下の分割は、bge-m3 が実際に行う分割である。

### 3-2. bge-m3（XLM-RoBERTa系 SentencePiece Unigram）の実測分割

| 入力 | bge-m3 の分割（`<s>`/`</s>` 除く） | 所見 |
|---|---|---|
| `34万4,000円` | `34` / `万` / **`4,000`** / `円` | **カンマ付きで1トークン**。壊れていない |
| `344000円` | `34` / `4000` / `円` | カンマを外すと**別の分割になる** |
| `2兆5,245億円` | `2` / `兆` / `5` / **`,`** / `2` / `45` / `億円` | 🔴 **カンマが単独トークンとして孤立し、`5245` が `5`,`2`,`45` に砕ける** |
| `2兆5245億円` | `2` / `兆` / `52` / `45` / `億円` | 🔴 **カンマ有無で共通トークンが `2`/`兆`/`45`/`億円` しかない** |
| `1,422` | **`1,4`** / `22` | 🔴 **最悪ケース。トークンがカンマを跨いで桁を切る** |
| `1422` | `14` / `22` | 🔴 `1,422` と**共通トークンが `22` だけ** |
| `計121件、約234億円` | `計` / `121` / `件` / `、` / `約` / `23` / `4` / `億円` | `121` は保たれるが `234` は `23`+`4` に割れる |
| `2027年度` | `20` / `27` / `年度` | 年は常に2桁ずつに割れる |
| `令和7年度` | `令` / `和` / `7` / `年度` | 「令和」は1トークンにならない |
| `約2,500億円` | `約` / `2` / `,` / `500` / `億円` | カンマ孤立型 |
| `第Ⅴ部` | `第` / **`V`** / `部` | 正規化で全角ローマ数字 `Ⅴ`(U+2164) が Latin `V` になる |

**結論（実測）**:
EACL2026（arXiv:2509.05691）が「カンマ区切り数値が最悪」とした指摘は、**bge-m3 にも部分的に当てはまる**。
ただし**一律ではない**。`4,000` のように語彙に載っているカンマ付き数値は 1 トークンで保たれる一方、
`1,422` → `1,4`+`22`、`5,245` → `5`+`,`+`2`+`45` のように**桁境界を無視した分割**が起きる。
**同じ数値でもカンマの有無で共通トークンがほぼ消える**ため、
「質問文はカンマ無し、原典はカンマ有り」（あるいはその逆）のときに dense 側の一致が崩れる機構は実在する。

> ⚠️ 上記は**トークン列の観測**であって「埋め込みが数値を区別できない」ことの直接証明ではない。
> 埋め込み空間での距離は測っていない（§7 参照）。

### 3-3. 日本語bi-gram BM25（`tokenizeForFts`）の実測分割

| 入力 | BM25 トークン |
|---|---|
| `34万4,000円` | `万` / `円` / `34` / **`4`** / **`000`** |
| `2兆5,245億円` | `兆` / `億` / `円` / `2` / `5` / `245` |
| `1,422` | **`1`** / **`422`** |
| `1422` | `1422` |
| `4,000` | `4` / `000` |
| `4000` | `4000` |
| `2027年度` | `年度` / `2027` |
| `可動率` | `可動` / `動率` |

**🔴 実装を読んだ結果、既存調査の推論は誤りだった。**
`RESEARCH_NUMERIC_ENTITY_RETRIEVAL_2026-07-28.md` §A-2 は
「`34万4,000円` を文字bi-gramに分割すると `34 / 4万 / 万4 / 4, / ,0 / 00 / 00 / 0円`」と推論していたが、
**製品の `tokenizeForFts()` は CJK ラン（漢字・かな・カナ）だけを bi-gram 化し、
ASCII（数字を含む）は `[a-z0-9]+` の連続として丸ごと1トークンにする**。
数字が bi-gram に割られることはない。

**実際の壊れ方は「カンマが数字ランを分断すること」である。**
`4,000` は `4` と `000` の**2トークンに分断**され、`4000`（1トークン）とは**一致しない**。


**🔴 新規発見（製品側の欠陥）: `<document_metadata>` ヘッダが BM25 索引に入っている。**

全1,756チャンクの本文先頭に

```
<document_metadata>
sourceDocument: R07zenpen.pdf
published: 7/27/2026, 2:38:12 PM
</document_metadata>
```

が付いており、`tokenizeForFts()` はこれも索引化する。その結果:

- `published` / `metadata` / `sourcedocument` / `document` / `pdf` / `r07zenpen` / `pm` が DF=100%
- **投入日時に由来する数字 `7` `27` `2026` `2` `38` `12` が DF=100% → IDF = 0**

**したがって「2」「7」「12」「27」「38」「2026」を含む数値クエリは、
その桁について BM25 の識別力を完全に失っている。**
`2兆5,245億円` は `2`(IDF 0) / `兆` / `5` / `245` / `億円` に分かれ、先頭の `2` は無効である。

ただし**IDF=0 の項は BM25 スコアに寄与しないだけでランキングを歪めはしない**（全文書で等しい）。
実害は「クエリ語の一部が無駄になる」ことと、
**dense 側では逆に全チャンクに同じ日付文字列が入るためベクトルにバイアスが乗りうる**ことである
（後者は未測定。§7）。

**修正候補（本タスクでは実施しない）**: FTS サイドカー構築時（`buildOrOpenFtsTable`）と
embed 時に `<document_metadata>…</document_metadata>` を除去する。
`sentenceCushion.js` は既に `stripMetadata()` で除去しており、**索引側だけが取り残されている**。

## 6. 🔴 総合判定 — Phase 1 と Phase 2 のどちらが本命か

### 6-1. 結論

**Phase 1（coarse-to-fine 二段化）が本命である。Phase 2（数値正規化 + 凸結合）は
「数値が取れていない」という前提が実測で否定されたため、優先度を下げるべきである。**

### 6-2. 根拠（すべて実測）

| # | 実測 | 含意 |
|---|---|---|
| 1 | **候補プール(K=32)の `anchor_coverage` は 0.914**、K=128 なら 0.957 | **証拠は既に取れている。取れていないのではなく捨てている** |

## 7. 測定できなかったこと・限界（必ず読む）

| # | 測れなかったこと | 理由 |
|---|---|---|
| L1 | **`LANCE_HYBRID_RERANK=false` の end-to-end 値（RRF top8 → クッション後）** | 環境変数の変更にはコンテナ再起動が必要で制約に反するため、同じ読み取り専用ハーネスで「RRF(K=32) 上位8件をそのまま `applySentenceCushion` に通す」反実仮想を**起動したが、本報告の締め切りまでに完走しなかった**（166問 × 文単位リランクで CPU 律速）。したがって §1-1 の「1段目 RRF top8 = 0.774」は**クッション適用前の生本文**での値であり、実機で reranker を切ったときの最終値ではない。**reranker の効果 +3.7pt は生本文どうしの比較（0.774 vs 0.811）で読むこと** |
| L2 | **埋め込み空間での数値の距離** | D3 はトークン列を観測しただけで、`4,000` と `4000` の埋め込みコサイン類似度は測っていない。「トークンが違う → 埋め込みが違う」は**推論** |
| L3 | **`<document_metadata>` を索引から外したときの効果** | 索引の再構築（＝製品の書き込み）が必要なため実施しなかった。IDF=0 の実害の大きさは**未測定** |
| L4 | **oracle の条件R（本番文脈の再生）を166問で再検証していない** | 旧20問で A と R が要素79/79・本文20/20 一致した実証を根拠に省略した。**166問での再現ハーネスの妥当性は再検証していない** |
| L5 | **C5/C6 で cross-encoder が悪化する機構** | 「質問文に答えの語が出てこないから」は**推測**。アブレーションしていない |
| L6 | **オラクルの gold チャンク構成が最適である保証** | 凍結済みの貪欲被覆規則に従っただけで、平均1.71チャンクと短い。**短さ由来の過剰拒否（22問）が上限を過小評価している可能性がある**。0.765 は**下界としても読める** |
| L7 | **生成フェーズの run 間ゆらぎ** | oracle は 2run（不一致 1/650）。本番Aは既存の3run を再利用した |
| L8 | **`Q130` の `民間空港・港湾`（7字）が到達不能な原因** | 未特定 |

### 7-1. 測定方法自体への疑義（自己申告）

- **§1-1 の段別比較は、テキストの粒度が段によって違う。**
  1段目・2段目は「生チャンク本文（約500字×8）」、3段目は「クッション後（約2,300字）」で判定している。
  これは**意図した比較**（クッションの損失を測るのが目的）だが、
  「1段目 0.774 vs 最終 0.712」を「順位付けの差」と読んではならない。
  **順位付けだけの比較は 0.774 → 0.811（どちらも生本文）で見ること。**
- **`anchor_coverage` は「アンカー文字列が文脈に含まれるか」であって「LLM が答えられるか」ではない。**
  D4 が示すとおり、文脈に届いても変換率は 0.78 である。
  **検索指標の改善幅をそのまま最終品質の改善幅と読んではならない。**
- **本診断は 1 コーパス（令和7年版防衛白書）1 設問セット（166問）の結果である。**
  「数値は取れている」は**この白書の書き方に依存する可能性が高い**。
  想定文書（行政資料・製品ヘルプ）で同じとは限らない。
