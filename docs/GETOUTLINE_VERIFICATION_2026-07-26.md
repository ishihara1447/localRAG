# `getOutline()` 再検証 — しおり付きPDFでは主経路になりうる

実施日: 2026-07-26 / 実施: Claude Code
関連: `TIER0_DOCUMENT_STRUCTURE_DESIGN_2026-07-26.md`（当初の評価）、`QUALITY_ROADMAP_2026-07-26.md`（S21〜S24）

## 1. なぜ再検証したか

`TIER0_DOCUMENT_STRUCTURE_DESIGN_2026-07-26.md` は、防衛白書に対する実測にもとづき **`getOutline()` を「第2候補に降格」** と結論した（DTP入稿ファイル名が並び、階層がフラット）。

しかしその後、**利用者が実際に読み込む文書が判明した**。

- **① 行政資料**（段組みPDF、DTP制作）
- **② 製品のヘルプファイル** — **AcrobatまたはWordで作成しPDF化したもの**で、**Acrobat上で「見出し」（＝PDFのしおり／アウトライン）が確認できる状態**

②は当初の評価対象（DTP制作の白書）とは**生成経路がまったく異なる**。Wordの見出しスタイルはPDF化時に**入れ子のしおり**として書き出されるのが通常であり、降格の判断が②に当てはまるとは限らない。**そこで、しおりを持つPDFに対して同じコードパスがどう振る舞うかを実測した。**

## 2. 方法

**製品実装と条件を揃えた。** `anything-llm/collector/processSingleFile/convert/asPDF/PDFLoader/index.js:56-64` と同じ `pdfjs-dist`（collector の `node_modules` 実体）・同じ `getDocument` オプションを用い、`getOutline()` と `getPageIndex()` を呼ぶ検証スクリプトを scratchpad に作成して実行した。

- 検体A: **しおり付きPDF**（`reportlab` で生成。見出し11件・3階層・日本語タイトル。**Wordの見出しスタイルからのPDF化を模した合成文書**）
- 検体B: **防衛白書** `fixtures/local/R07zenpen.pdf`（546ページ、DTP制作）

**`anything-llm/` は一切変更していない**（読み取りとモジュール参照のみ）。

## 3. 結果（実測）

| | 検体A: しおり付きPDF | 検体B: 防衛白書（DTP） |
|---|---|---|
| `getOutline()` | 11件 | 42件 |
| **最大深さ** | **2（正しく入れ子）** | **0（完全フラット）** |
| タイトルの実際 | `第1章 はじめに` / `2.1 動作環境` / `2.1.1 必要なGPU` / `付録A トラブルシューティング` | `防衛2025_1-3_01-04_sh0503_注意_sh0301` / `防衛2025_0-2_目次_sh0301` / **`空白ページ`** |
| ページ解決 | **11/11** | 35/42 |
| 所要時間 | 4ms | 12ms |

検体Aでは**日本語の見出しテキストがそのまま取得でき、章・節・項の親子関係も保持され、全項目のページが解決した**。

## 4. 結論

**当初の「`getOutline()` は使い物にならない」という評価は、DTP制作された行政資料に対する評価であって、コードパスの限界ではない。**

しおりが正しく設定されたPDFに対しては、`getOutline()` は**入れ子構造・日本語タイトル・ページ番号をミリ秒で返す**。ヘルプファイル（Word/Acrobat由来）が想定どおりのしおりを持っているなら、**これが系統Bの構造情報源として最も安価で最も確実な経路**になる。LLM呼び出しは不要、再embedも不要、パースのヒューリスティックも不要である。

→ **ロードマップ S22（`getOutline()` の品質ゲート）は「フォールバック」ではなく「系統Bの主経路」として設計すべき。**

## 5. ⚠ この検証が証明していないこと（重要）

**検体Aは `reportlab` で生成した合成PDFであり、実際のWord/Acrobat出力ではない。** 実物のヘルプファイルはユーザーから提供不可との回答があったため、代理検証にとどまる。

したがって本検証が示したのは:

- ✅ **消費者側（pdfjs〜自製品のコードパス）は、入れ子のしおりを正しく扱える**
- ✅ **白書のフラット・DTP名という結果は、文書側の性質である**
- ❌ **実際のWord/Acrobat出力が「良いしおり」を持つことは証明していない**（Wordが見出しスタイルからしおりを生成するのは一般的な挙動だが、本検証の対象外）

**実物が入手できた時点で、必ず検体Aと同じスクリプトで再確認すること。**

## 6. 品質ゲート（S22）の判定条件案

今回、**良い例と悪い例の実測値が両方揃った**ため、ゲートの条件を具体的に書ける。以下を満たさない場合は `getOutline()` を採用せず、印刷目次ページのパース（S21）にフォールバックする。

| 判定項目 | 条件案 | 根拠（実測） |
|---|---|---|
| 階層の有無 | **最大深さ ≥ 1** | 検体A=2 / 白書=0。**これ単独で白書を確実に弾ける** |
| 制作ツール由来名の混入 | `_sh\d+`、`_OK_`、連番＋アンダースコアの羅列など**DTP入稿名パターンを含む項目が全体の一定割合以上なら不採用** | 白書は42件中ほぼ全件が該当 |
| 無意味タイトル | `空白ページ` 等の定型無意味語の比率が閾値未満 | 白書に実在 |
| ページ解決率 | **解決率 ≥ 0.9** | 検体A=1.00 / 白書=0.83 |
| タイトルの妥当性 | 平均長が極端に長くない、日本語または見出し番号を含む | 検体Aは `第N章`/`N.N` 形式 |

**「最大深さ ≥ 1」が最も安価で効果的な判定**である。実装時はこれを第一条件に置き、他は補助とするのが良い。

- 品質ゲートの判定条件は §6 を実装の出発点とする
