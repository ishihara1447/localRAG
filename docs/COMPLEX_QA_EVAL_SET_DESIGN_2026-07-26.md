### 1-2. 設問の作り方（共通思想）

無作為抽出ではなく「RAGが失敗しやすい典型パターンの狙い撃ち」。すべての設問が
**単一チャンク内で完結する一問一答（factoid抽出）**であり、答えは短い固有名詞・数値・
決まり文句である。これが「頭打ち」の直接原因である。

### 1-3. 現行スコア【確認】

- 防衛白書 28〜29/30（平均28.5、think:false+P1+ルール8のベースライン）

天井に張り付いており、**この2セットではもう施策の良し悪しを判別できない**。

## 2. 内部監査の指摘と、本設計での対応方針

内部監査（2026-07-16）の指摘は本設計の制約条件そのものである。対応表を先に置く。

| # | 監査の指摘 | 本設計での対応 |
|---|---|---|
| §1-1 | 採点正規表現のバグ→**手動でのスコア補正が常態化** | **生スコアの手動補正を禁止**。偽陰性を見つけたら採点定義（alias辞書）を直して**全問再実行**。補正値は一切記録に残さない（§6-7） |
| §1-2 | (c)キーワード判定に空白許容がない | 正規化を採点関数の入口に一本化（§6-2 Layer 0） |
| §1-3 | UNKNOWN正規表現が肯定文にも誤マッチ | 複雑質問では「不明」判定を正規表現に依存させない。unanswerable設問はLLM-as-judgeの専用ルーブリックで判定（§6-4） |
| §1-4 | 白書側に出典検証がない | **全設問にgoldページ集合を必須**とし、retrieval指標を独立に計測（§5） |
| §2-2 | **マルチホップ問題がゼロ** | 本設計の中核。20問中12問がgoldページ2つ以上（§4） |
| §2-3 | 推奨規模50〜200問に対し30問のまま | 本セット20問を追加し、要素単位採点で実効nを約140に拡大（§7-2） |
| §2-4 | 「言い換え可」と言いながら語彙一致を要求する自己矛盾 | キーワード一致を主採点から外す。要素は**命題**として定義し、表層一致は補助（§6-2） |
| §2-5 | 「文書に無い」ことの立証手順が非開示 | unanswerable設問に**grepコマンドと結果件数を評価セットに同梱**（§4-6に実測値を記載済み） |
| §3 | n=30の点差は有意でない／同一設定の再実行で5点ぶれる | 最低3run、要素単位クラスタブートストラップCI、McNemar検定（§7） |
| §4 | retrieval評価が手作業・事後的 | `vector-search` APIで自動化。Coverage@k / All-Hit@k / MRR / nDCG（§5） |
| §6 | temperature未固定・条件不一致のA/B | temperature=0固定、judge側もseed固定。生成フェーズとjudgeフェーズを分離し条件を凍結（§8） |
| §7-9 | 作成主体と検証主体が同一 | 設問データを**JSONに外出し**してCodex等の別主体がレビューできる形にする（§8-2） |

**最大の論点への回答（先出し）**: 複雑質問はキーワード一致が原理的に機能しない。
本設計は「**1問1スコア**」をやめ、**設問を必須要素（atomic claim）に分解し、要素ごとに
YES/NO判定する**方式を採る。判定単位を最小化することで、
(a) 部分点が自然に得られ、(b) LLM-as-judgeの verbosity/position bias が構造的に効きにくくなり、
(c) 数値・固有名詞の要素は**LLM不要の決定的判定**に落とせる。詳細は §6。

### 3-2. ページ番号の対応関係（重要な落とし穴）【確認】

- 本設計での pypdf 抽出ページ = **白書の印字ページ（ノンブル）+ 10**
  - 例: pypdf 242 のフッタは「232日本の防衛」／pypdf 207 は「197 令和7年版 防衛白書」／pypdf 71 は「61」
- 一方、既存の `docs/RAG_HAKUSHO_EVAL_SET_2026-07-14.md` の `===PAGE n===` は **印字ページ + 9**
  - 例: 「市ヶ谷に設置」を PAGE 241 と記載（印字232）。本設計の抽出では pypdf 242
  - 「専守防衛とは」PAGE 206（印字197→本設計 pypdf 207）、「1.4％」PAGE 234（印字225→pypdf 235）、
    「きらめき2号」PAGE 229（印字220→pypdf 230）と、確認した4件すべてで**1ページずれている**

**したがって本設計の全設問は、gold を「白書の印字ページ（フッタのノンブル）」で記載する。**
印字ページは PDF 本文に印字されており第三者が検証できる唯一の不変な参照系である。
pypdf ページは抽出ライブラリのバージョンで変わりうるため、参考値としてのみ併記する。

### 3-3. ページ番号メタデータ【確認 + 未確認】

## 5. 採点設計（1）retrieval 評価の分離

内部監査 §4 が「体系的な Hit Rate@k / MRR が未実装」と指摘した部分を、本セットで先行実装する。
**retrieval評価は生成を一切呼ばないため、決定的・高速・LLMバイアスの混入なし**であり、
複雑質問の評価では最も費用対効果が高い。

### 5-1. gold の定義

各設問に **gold page set `G`（白書の印字ページ番号の集合）** を持たせる。§4 の「gold」欄がそれ。
マルチホップ設問は `|G| ≥ 2`。さらに各ページに重みを付ける【提案】:

- `weight 2` = **必須ページ**（これが無いと絶対に答えられない）
- `weight 1` = **補助ページ**（あると答えの質が上がる。ダイジェスト・目次など）

### 5-2. 取得側の観測

`POST /api/v1/workspace/{slug}/vector-search` に `{query, topN: k, scoreThreshold: 0}` を投げ、
返る `results[].metadata.pageNumber` を取得する。【確認】このAPIは `text` / `metadata` / `distance` / `score` を返す。
`scoreThreshold: 0` にするのは、閾値による切り捨てとランキング性能を分離して見るため。

**ページ判定は `G ± 1ページ` を許容する**（§3-3 のとおりチャンク内多数決でページが1つずれうるため）。

### 5-3. 指標

| 指標 | 定義 | 用途 |
|---|---|---|
| **Coverage@k** | `|取得ページ集合 ∩ G| / |G|` | **マルチホップの本命指標**。「何ホップ取れたか」 |
| **All-Hit@k** | `Coverage@k == 1.0` となった設問の割合 | マルチホップの真の成功率 |
| Hit Rate@k | goldを1つでも含む設問の割合 | 既存30問との比較用（`|G|=1` 相当） |
| MRR | 最初のgoldページの順位の逆数 | 上位表示の質 |
| nDCG@k | weight（2/1/0）を relevance とした標準式 | 必須ページを上位に置けているか |

`k` は 4 / 8（既定topN）/ 16 / 32 の4点で測り、**k を増やせば取れるのか（＝ランキングの問題）、
k を増やしても取れないのか（＝索引・チャンク分割の問題）**を切り分ける。
Q3（個室化）で判明した「チャンク境界での語中分断」型の障害は後者に分類される。

### 5-4. フォールバック【提案】

`metadata.pageNumber` が実データに存在しない場合（§3-3 の【未確認】）は、
gold ページの本文から抽出した**アンカー文字列**（例: Q9なら「総額9.9兆円」「GDPの2％に達する」）が
取得チャンクの `text` に含まれるかで判定する。アンカーは空白除去・全半角正規化のうえ照合する。
この方式は pageNumber の実装状況に依存しないため、**先にこちらで実装しておくのが安全**。

### 5-5. retrieval と generation の突き合わせ

各設問について `(Coverage@8, 要素カバー率)` の2次元で分類し、失敗モードを自動判定する【提案】:

| Coverage@8 | 要素カバー率 | 判定 |
|---|---|---|
| 低 | 低 | **(A) retrieval失敗** — 索引・チャンク分割・クエリ拡張の領域 |
| 高 | 低 | **(C) 生成失敗** — プロンプト・LLM選定の領域 |
| 高 | 高 | 成功 |
| 低 | 高 | **要調査** — パラメトリック知識での回答（＝出典なき正答）の疑い。**危険信号** |

最後の行が重要である。複雑質問では「gemma4 が事前学習で知っている一般常識で答えてしまい、
たまたま正解する」ケースが起こりうる。現行評価はこれを検出できない。

## 6. 採点設計（2）generation 評価 — キーワード一致からの脱却

### 6-1. 大原則: 「1問1スコア」をやめる

複雑質問の回答は数百字におよび、`re.search` も `all(k in ans)` も機能しない。
本設計は次を採る。

> **設問を「必須要素（atomic claim）」に分解し、要素ごとに YES/NO を判定する。
> 設問のスコアは要素の集計として事後的に決まる。**

利点:
1. **部分点が自然に得られる**（7つ挙げるべきところ5つ挙げた回答を 5/7 と評価できる）
2. **LLM-as-judge のバイアスが構造的に効きにくい** — 判定対象が「この命題が含まれるか」という
   最小単位のYES/NOになるため、verbosity bias（長い回答を高評価）も
   position bias（先に出た方を高評価）も入り込む余地が小さい。judge は総合点を付けない
3. **要素の型ごとに、LLMを使わない決定的判定に落とせる**（`[N]`数値・`[E]`固有名詞）
4. **実効サンプルサイズが増える** — 20問 × 平均7要素 ≒ 140要素。統計的検出力が上がる（§7-2）

### 6-2. 4層の採点パイプライン

```
Layer 0  正規化（決定的・LLM不要）
Layer 1  要素判定 [N][E][X] … 決定的マッチ（LLM不要）
Layer 2  要素判定 [P]        … LLM-as-judge（reference-guided、要素単位YES/NO）
Layer 3  人手スポットチェック（キャリブレーション）
```

**Layer 0: 正規化**（内部監査 §1-1/§1-2 の再発防止をここに一本化）
- `<think>...</think>` 除去（既存3スクリプトと同じ）
- 空白（半角・全角・改行）を全除去してから比較
- 全角英数・記号 → 半角、`％`→`%`
- 数値の表記ゆれを正規化: `8兆4,748億円` / `84,748億円` / `8兆4748億円` → 同一表現
- 年号: `令和7年` ⇔ `2025年` の相互変換テーブル

**Layer 1: 決定的な要素判定**
- `[N]`（数値）: 正規化後の数値一致。許容誤差を要素ごとに指定可（例: 「約1.1兆円」に対し ±0.1兆円）
- `[E]`（固有名詞・術語）: **alias配列**で判定する。
  例: `機動展開能力・国民保護` の alias = `["機動展開能力・国民保護", "機動展開能力と国民保護", "機動展開能力"]`。
  内部監査 §2-4 が指摘した「言い換え可と言いながら語彙一致を要求する自己矛盾」は、
  **alias を明示的に列挙して評価セットに書き込む**ことで解消する。aliasの妥当性はレビュー対象になる
- `[X]`（禁止要素）: ハルシネーション検出。正規表現または alias で「書いてはいけない主張」を定義。
  1つでもヒットしたらその設問は**完全正答から除外**し、別途 hallucination として集計

**Layer 2: LLM-as-judge（`[P]` 命題要素のみ）**
- judge への入力は **(a) 判定対象の要素1つ、(b) 被評価回答の全文、(c) gold原文の抜粋** の3点のみ。
  出力は `{"verdict": "YES"|"NO", "evidence": "回答中の該当箇所"}` の JSON 固定
- **reference-guided**（gold原文を渡す）方式にする。方法論調査【確認】でも
  「reference-guided（正解回答をjudgeに与える）方式が精度を上げる」とされている
- judge は**総合点・5段階評価を出さない**。YES/NO のみ。ルーブリック採点（1〜5点）は
  スケールの解釈がモデル依存で不安定になるため採らない
- `evidence` を必ず出させ、**回答本文に実在しない `evidence` を返した判定は無効**として
  人手キューに回す（judge自身のハルシネーション検出）

**Layer 3: 人手スポットチェック**
- 各 run から全要素の **20%を無作為抽出**して人手判定し、Layer1+2 との一致率（Cohen's κ）を出す
- **κ < 0.6 の場合、その run の generation スコアは信頼できないものとして扱う**
- 抽出は要素IDで層化（`[P]` を厚めに）

### 6-3. LLM-as-judge の自己評価バイアス問題（本設計の最重要論点）

**結論: 被評価モデルである `gemma4:12b` を judge に使ってはならない。**

理由【確認: `RAG_EVAL_METHODOLOGY_RESEARCH_2026-07-16.md` §3】:
- **Self-preference bias**: judge が自分自身の出力を高く評価する。特に本セットの
  faithfulness/推論系設問では、gemma4 が生成した「もっともらしい捏造」を
  gemma4 judge が「根拠あり」と追認する方向に系統的に歪む。C5・C6 の `[X]` 判定が最も汚染される
- **Verbosity bias**: 長い回答を高評価。position bias より除去が困難
- 同系統モデルは judge プールを分けても系統的バイアスが残る

**現状の制約【確認】**: ローカルの Ollama モデル manifest に存在するのは
`gemma4` と `bge-m3` の**2つだけ**（`runtime/ollama-models/models/manifests/registry.ollama.ai/library/`）。
つまり**今すぐには別系統 judge を立てられない**。

**対処方針【提案】（優先順）**

1. **judge を使わなくても成立する設計にしておく（必須）**
   `[N]` と `[E]` と `[X]` は Layer 1 で判定できる。§4 の20問は
   **全問について `[N]`+`[E]`+`[X]` を最低3つ含むよう設計してある**。
   judge が使えない環境では「決定的要素カバー率」を主指標として運用できる。
   これは「judge が無いと何も測れない」状態を避けるための保険であり、設計上の必須要件とする。

2. **judge 用に別系統モデルを1つ導入する（推奨）**
   評価ハーネスは**開発機でのみ動き、顧客配布物には含まれない**。したがって
   「非中国系」「Apache/MIT」といった製品同梱の制約（`CLAUDE.md`）が judge にそのまま
   適用されるかは**ユーザーの判断事項**である。本書では判断せず、選択肢のみ示す:
   - `phi4`系: 本体LLMとしては「架空引用の捏造」で不採用【確認】だが、
     judge の仕事は生成ではなく **YES/NO の含意判定**であり、失敗モードが異なる。
     ただし採用するなら §6-4 のキャリブレーションで実証すること
   - Prometheus 2 (7B) / M-Prometheus: 方法論調査が推奨【確認】。16GB VRAM で動作、
     人間評価との相関 0.897 と報告。ただし Ollama 公式配布ではないため導入手順の確認が必要
   - qwen系: 製品には非採用（中国系）。評価専用なら技術的には可だが、**要ユーザー判断**
   いずれも**モデル取得時に一度だけネットワークが必要**であり、その後はオフラインで回る。
   製品の「完全オフライン」制約には抵触しない（開発機の評価用途）。

3. **二重 judge の合議（余力があれば）**
   2モデルで判定し、不一致の要素だけ人手に回す。単一 judge の癖が可視化でき、
   人手コストは不一致分のみに抑えられる。

4. **どうしても gemma4 を judge に使う場合の最低限の条件**
   - **`[X]`（ハルシネーション検出）には絶対に使わない**（自己追認が最も強く出る）
   - `[P]` の YES/NO のみに限定し、gold原文を必ず渡す
   - **人手スポットチェック率を20%→50%に引き上げる**
   - レポートに「judge=被評価モデルと同一。self-preference bias により generation スコアは
     過大評価の方向に偏っている可能性がある」と**毎回明記する**

### 6-4. judge のキャリブレーション（導入時に一度だけ、必須）

judge を導入するとき、**先に judge 自体を評価する**。内部監査 §5 が指摘した
「作成主体と検証主体が同一」問題への対応でもある。

1. 人手で **50〜100要素分の正解ラベル**を作る（YES/NO）
2. judge にかけ、Cohen's κ と、YES/NO それぞれの誤り率を出す
3. **κ ≥ 0.7 を judge 採用の下限**とする【提案】
4. 判定が割れやすい要素の型（否定を含む命題、程度表現など）を記録し、
   要素の書き方のガイドラインに反映する
5. judge も **temperature=0・seed固定**で、同一入力の再実行が一致することを確認する
   （一致しないなら判定の信頼性以前の問題）

### 6-5. スコアの定義

設問 `q` について:

```
必須要素カバー率(q) = (満たした required 要素数) / (required 要素数)
完全正答(q)         = 必須要素カバー率 == 1.0 かつ [X] ヒット 0件
ハルシネーション(q) = [X] を1つ以上ヒット
```

セット全体の報告値:

| 指標 | 意味 | 主/副 |
|---|---|---|
| **要素カバー率**（全要素をプールした比率） | 主指標。連続値でノイズに強い | **主** |
| 完全正答率（20問中） | 従来の「◯/30」に相当。人間に伝わりやすい | 副 |
| ハルシネーション率 | `[X]` を含む設問の割合 | **主**（安全性） |
| 決定的要素カバー率（`[N][E]` のみ） | judge非依存の指標 | **主**（再現性の基準線） |
| Coverage@8 / All-Hit@8 | retrieval（§5） | **主** |

**カテゴリ別（C1〜C6）にも必ず分解して報告する**。総合値だけでは
「マルチホップは伸びたが要約が落ちた」といった打ち消し合いが見えない。

## 7. 統計的信頼性の設計

内部監査 §3・§6 が最も強く指摘した部分。

### 7-1. 実行回数と温度

- **temperature=0 を必ず設定**（既存3スクリプトと同じく、実行前に `openAiTemp=0` を POST）
- **それでも最低3run**。temperature=0 でも GPU の非決定性・バッチング・KVキャッシュ状態で
  出力が揺れうる。内部監査 §3-2 は「同一設定の再実行で19/20/21/24」という実測を示している【確認】
- 3run の**平均・最小・最大を必ず併記**する。単発値の単独表記を禁止する（監査 §7-3）
- judge も temperature=0・seed固定。**judge を掛け直すたびにスコアが動くのは論外**

### 7-2. 信頼区間

- 要素は設問内で相関する（同じ検索結果に依存する）ため、**単純な二項CIは狭すぎる**。
  → **クラスタブートストラップ**を使う: リサンプリング単位を**要素ではなく設問**にし、
  1,000回リサンプルして要素カバー率の 95%CI を出す【提案】
- 完全正答率（n=20）には **Wilson score interval** を併記（方法論調査でn=10程度でも妥当と確認【確認】）
- **報告フォーマットを固定する**:
  `要素カバー率 0.72 [95%CI 0.61–0.82]（3run平均: 0.70 / 0.74 / 0.71）`

### 7-3. 施策 A/B の判定則

同一設問セットに対する対応ありの比較になるので:

- **McNemar 検定**（要素単位・設問単位の両方）を出力に自動で含める（監査 §7-7）
- 判定則を**事前に**固定する【提案】:
  > 「改善した」と言ってよいのは、**(a) 3run平均のCIが重ならない、かつ (b) McNemar p < 0.05、
  > かつ (c) 改善方向が3runすべてで一致** の3条件を満たしたときのみ。
  > 1条件でも欠けたら「差は誤差範囲」と記載する。
- retrieval 指標（Coverage@k）は決定的なので run 間でぶれない。**まず retrieval で差が出るかを見る**のが
  ノイズに強く、費用対効果が高い。

### 7-4. 禁止事項（内部監査の再発防止として明文化）

1. **生スコアの手動補正を禁止する**。「内容を見れば正解だから補正して◯点」という運用を廃止する。
   偽陰性を見つけた場合は **alias / 正規表現 / 要素定義そのものを修正し、全設問を再実行**する。
   修正内容は評価セットJSONの差分としてコミットに残す
2. **単発実行値の単独表記を禁止する**
3. **既存の hakusho-eval / ambiguous-eval のスコアと合算しない**。別レポート・別ファイルで報告する
   （難易度が違うセットを足すと平均が意味を失う）
4. **unanswerable の非存在根拠は、grepコマンドと結果件数を評価セットに同梱する**（監査 §2-5）。
   本書では Q19・Q20 で実施済み

## 8. 実装方針【提案】

実装自体は本タスクの範囲外。既存3スクリプトの構造に合わせる方針のみ記す。

### 8-1. スクリプト構成

新規 `scripts/complex-eval.py` を追加する。既存の作法を踏襲する点:

- PEP 723 のインラインスクリプトメタデータ（`# /// script` ブロック、`httpx>=0.27`）
- `LOCALRAG_BASE_URL` / `HAKUSHO_SLUG` 環境変数
- `POST /api/system/generate-api-key` でキー自動発行（scale-eval のように**実行後に削除**する方が望ましい）
- 実行前に `openAiTemp=0` を POST
- `<think>` 除去
- 設問ごとに一意な `sessionId`（ambiguous-eval の作法。**複雑質問では特に重要** —
  前問の長い回答が履歴に残ると次問を汚染する）
- `--top-n` / `--chat-model` / `--system-prompt-file` 相当のパラメータ上書き

既存と変える点:

- **CASES をPythonリテラルに書かない**。設問・gold・要素定義は
  `fixtures/complex/hakusho-complex-qa.json`（git管理）に外出しする。
  理由: (a) 要素定義が大きく Python に埋めると可読性が壊れる、
  (b) **Codex 等の別主体がレビューできる**（内部監査 §7-9 のクロスチェック要求）、
  (c) Claude/Codex 並行編集での競合が起きにくい（`CLAUDE.md` のマルチエージェント運用）
- **フェーズを分離する**: `--phase retrieval|generate|judge|report`
  - `retrieval`: LLM不使用。`vector-search` を叩いて Coverage@k / MRR / nDCG を出す（数十秒）
  - `generate`: chat API を叩き、**回答全文をJSONに保存**（20問×3run）
  - `judge`: 保存済みJSONに対して Layer1/2 を適用。**生成をやり直さずに judge だけ掛け直せる**
    （judgeモデルを変えて感度を見る、alias を直して再採点する、が安価にできる）
  - `report`: 集計・CI・McNemar・カテゴリ別内訳・失敗モード分類を出力
- judge は **Ollama の `/api/generate` を直接叩く**。AnythingLLM 経由にしない
  （RAG の検索文脈やシステムプロンプトが judge の入力に混入するため）。
  `options: {temperature: 0, seed: <fixed>}`、`format: "json"` を指定

### 8-2. 評価セットJSONのスキーマ（案）

```

  "question": "...",
```

### 8-3. 出力

- `COMPLEX_OUT` に run 別・要素別の全生データを JSON 保存（後から再集計できるように）
- 標準出力にはカテゴリ別内訳・retrieval指標・CI・McNemar を出す
- **既存 hakusho-eval の合計点と混ぜない**。レポートは `docs/COMPLEX_QA_EVAL_RESULT_<date>.md` として別立て

### 8-4. 既存スクリプトへの横展開

本セットで実装した資産は、既存30問にも後から適用できる:

- 正規化 Layer 0 の共通化 → `scripts/_eval_common.py` として切り出し、
  hakusho-eval / ambiguous-eval / scale-eval / complex-eval の4本で共用する
- **ただし本セットの実装が安定するまで既存3本には手を入れない**。
  ベースライン（28〜29/30、15/15+15/15）が動かなくなると比較の基準を失うため。

### 9-2. 本設計の限界（正直に）

- **設問の難易度は未検証**【未確認】。本設計作業では実際にRAGへクエリを投げていない
  （ローカルにモデルが無いため）。「なぜ難しいか」は原文の配置・既知の失敗モード・
  チャンク分割の性質からの**予測**であり、実測ではない。
  実装後の初回実行で「全問正解」または「全問不正解」に張り付いた場合、
  設問の難易度調整（gold の分散度を上げる／下げる）が必要になる
- **Q15（防衛この一年）は抽出テキストの劣化が大きい**。期待要素は抽出テキスト上で
  確実に読めた項目に限定してあるが、gold を増やす際は PDF ビューアでの目視確認が必要
- **20問は方法論調査の推奨（開発コア50〜100問）を下回る**【確認】。
  ただし要素単位採点により実効n≒140となり、単純な20問セットよりは検出力がある。
  本セットが機能することを確認したうえで、同じ型で30〜40問に拡張するのが望ましい
- **`fixtures/scale/` の規程10本を使った複雑質問は本書に含めていない**。
  各4KBと短く章立ても浅いため集約・要約の素材として弱い。
  ただし「規程横断のマルチホップ」（例:「出張中に慶弔事由が発生した場合、
  どの規程のどの手続きがそれぞれ必要か」）は作れるため、**士業シナリオ向けの
  第2弾として別途設計する価値がある**【提案】。実運用（複数文書ワークスペース）に
  近いのはむしろこちらであり、事業上の優先度は高い可能性がある

### 9-3. この評価セットで測れないもの

- 応答速度・トークン消費（複雑質問は回答が長くなるため、実用上は無視できない。別途計測すること）
- 対話の継続（フォローアップ質問での文脈保持）。本セットは1問1セッションで測る
- 実ユーザーの質問分布との一致。本セットは「難しい型」を狙い撃ちした人工セットであり、
  **実運用の平均難易度を代表しない**。現行30問と併記して初めて意味を持つ

## 10. まとめ

1. 現行3スクリプトはすべて**単一チャンク抽出型のfactoid**であり、天井に達している【確認】
2. 新セットは **集約4/マルチホップ5/比較3/要約3/推論3/unanswerable2 の計20問**。
   **全問を防衛白書546ページの原文と照合済み**、gold は印字ページで記載
3. 既存evalセットのページ番号は本設計の抽出と**1ページずれている**【確認】。印字ページを正とする
4. 採点は **「1問1スコア」を捨て、必須要素（atomic claim）単位のYES/NO**に分解する。
   `[N]`数値・`[E]`固有名詞・`[X]`禁止 は LLM 不要の決定的判定、`[P]`命題のみ judge
5. **judge に被評価モデル gemma4 を使わない**。self-preference bias が
   特に `[X]`（ハルシネーション検出）を汚染する。judge が無くても
   「決定的要素カバー率」だけで運用できる設計を必須要件とする
6. **retrieval を独立に自動計測**（Coverage@k / All-Hit@k / MRR / nDCG）。
   `vector-search` API と `metadata.pageNumber` で実装可能【コード確認済】。
   retrieval×generation の2次元で失敗モードを自動分類する
7. **最低3run・クラスタブートストラップCI・McNemar検定**、判定則を事前固定。
   **生スコアの手動補正を禁止**する
