## 1. 目的と、答えを出したい問い

### 1-1. 状況

導入先が検証環境として **Windows / VRAM 8GB** を用意した。現行の LLM `gemma4:12b`（実効 8.1〜8.4GB）は
載らない。Gemma 4 は全変種が 7.2GB 以上で縮小版という逃げ道が無く、日本語特化モデルは
重み非公開・再配布禁止・公式 GGUF 不在・サイズ超過のいずれかで全滅している（既済の調査）。

残った候補は2つで、**どちらも日本語の公開ベンチスコアが存在しない**。

| | モデル | 提供元 / ライセンス | ファイル | 推定実効 VRAM |
|---|---|---|---|---|
| 案A | `granite4.1:8b` | IBM / Apache-2.0 | 5.3GB | 5.9〜6.1GB（推定） |
| 案B | `nemotron-3-nano:4b` | NVIDIA / NVIDIA Open Model License | 2.8GB | 3.3〜3.6GB（推定） |

### 1-2. 決定済みで、本計画が変更しないこと

1. **今回替えるのは LLM だけ。** 埋め込み `bge-m3`・リランカー `bge-reranker-v2-m3` は据え置く。
   同時に変えると精度劣化の原因を切り分けられないため。埋め込みの非中国系化は別トラック。
2. 中国系モデルは不可（配布物に同梱するモデルへの制約）。
3. Ollama 公式ライブラリ配布のモデルのみ。コミュニティ GGUF は不可
   （`hf.co/mmnga-o/llm-jp-4-8b-thinking-gguf` がチャットテンプレート破損で 30問中0問になった事故がある）。
4. 商用利用可、完全オフライン動作。

### 1-3. 答えを出したい問い（分解）

真の問い **Q0**: 「OTE-RAG を Windows / VRAM 8GB で、現行構成と実用上同等の精度で動かせるか」

これを、**測り方の違う4つに分解する**。分解しないまま測ると、精度の劣化がモデルのせいなのか
VRAM 制約のせいなのか切り分けられなくなる。

| # | 問い | どこで測るか |
|---|---|---|
| **Q1（精度）** | LLM を案A / 案B に替えたとき、生成品質はどれだけ落ちるか | 16GB 開発機。VRAM とは無関係 |
| **Q2（安全性）** | 文書に無いことを「記載なし」と答える能力を保てるか。Phi-4 型の捏造をしないか | 16GB 開発機 |
| **Q3（適合・速度）** | 8GB に載るか。載るとしてどれだけ遅いか | 8GB 模擬 → 実機で確定 |
| **Q4（模擬妥当性）** | 16GB 機での 8GB 模擬は、実機の挙動を予測できるか | 模擬と実機の突き合わせ |

### 1-4. ★本計画の中心にある設計判断: 精度と VRAM を切り離す

**重みと量子化が同一なら、モデルが全レイヤ GPU にあろうと一部が CPU に落ちていようと、出力は同じはずである。**
Ollama / llama.cpp は VRAM に応じて**レイヤの配置**を変えるだけで、**モデルそのもの**は変えない。

したがって **Q1・Q2 は 8GB 模擬をせずに 16GB 開発機で測れる**。これが本計画で最も工数と
リスクを削っている判断である。8GB 模擬の妥当性が疑わしくても、**精度の結論はその影響を受けない**。

ただしこの「はず」には検証が要る。§4-3 の **V1（出力不変性）** で実測する。
また例外が1つある: VRAM が足りないときに `num_ctx` が縮められると、文脈が切れて精度が落ちる。
これは §4-3 の **V2** で確認する。

### 2-2. ★実験デザイン: 凍結文脈リプレイ（FCR）を主、E2E を従

#### 主デザイン: 凍結文脈リプレイ（Frozen-Context Replay, FCR）

`out/baseline166/base166-gen-run1.json` に保存されている各設問の `sources[].text`
（＝クッション適用後、LLM が実際に読んだ文脈そのもの）を**そのまま**使い、生成段だけを候補モデルに差し替える。

| | 内容 |
|---|---|
| 変えるもの | **Ollama に渡すモデル名だけ** |
| 変えないもの | 文脈（バイト単位で同一）／システムプロンプト／temperature=0／`think:false`／`num_ctx=8192`／設問／採点器／judge |

利点:

1. **検索がバイト単位で同一**。`anchor_coverage@8` は定義上不変であり、測る必要がない。
   観測された差は **100% 生成側に帰属する**。これが「他の要因と切り分けて測る」という要求への直接の答えである。
2. **完全なペア設計**。同一設問・同一文脈なので McNemar が最大の検出力で使える。
3. `--phase retrieval` の 3時間×2 が不要。1run は 166 回の Ollama 呼び出しだけで済む。
4. 稼働中の AnythingLLM のワークスペース設定を書き換えない（本番設定を汚さない）。

限界（正直に書く）:

- 検索は gemma4 時代のまま。「候補モデルに最適化された検索」ではない。
  ただし本件の方針が「LLM だけを替える」である以上、これは仕様どおりであって欠陥ではない。
- ハーネス固有の人工物が混入する可能性がある。→ 従デザイン E2E で追認する。

#### 妥当性の担保（これを通らなければ FCR は使わない）

**FCR ハーネスで `gemma4:12b` を再実行し、保存済み `base166-judged-run1.json` と要素単位で 650/650 一致すること。**

ORACLE 実験では同型の再現（条件A vs 条件R）が **79/79 一致・回答本文 20/20 完全一致**した実績がある。
166問でも同様に一致するはずだが、当時と現在でコンテナ ENV やモデルが変わっていない保証はないので**必ず測り直す**。

- 一致しない場合の扱い: **FCR を放棄し、E2E のみで測る**（工数 +1〜2日、§6）。
  「だいたい一致したから使う」はしない。

#### 従デザイン: E2E

`uv run scripts/complex-eval.py --phase generate --chat-model <候補>` を製品経路で実行。

- 目的: (i) FCR の結論を製品経路で追認、(ii) **実応答時間の測定**（FCR は AnythingLLM のオーバーヘッドを含まない）。
- run 数: 1候補 1run（約40分）。FCR と方向が一致すればよい。
- 🔴 **落とし穴**: `--chat-model` はワークスペースの `chatProvider` / `chatModel` を書き換えるが、
  `phase_generate()` の `finally` に復元処理が無い（`scripts/complex-eval.py` 実装確認済み。
  `finally` で消えるのは API キーだけ）。**実行後に必ず `chatProvider=null` / `chatModel=null` へ戻し、
  戻ったことを API で読み直して確認する。** 戻し忘れると以後の全測定が候補モデルで走る。

### 2-3. ★最優先の合否基準 — 「文書に無いことを『記載なし』と答えられるか」

#### 2-3-1. なぜ2軸で測らなければならないか

**片側だけを見ると必ず騙される。** 「全部『記載なし』と答えるモデル」はハルシネーション率 0% を達成する。
自社調査 `RESEARCH_INFERENCE_ABSTENTION_2026-07-28.md` §B-7 が引く UAEval4RAG（ACL2025）は
**「回答可能クエリと回答不能クエリの両方で最適な単一構成は存在しない」**と結論しており、
トレードオフは構造的である。同 §B-8 は標準指標を
**Abstention Precision / Recall / F1 + Response Accuracy** と整理している。

本計画はこれに合わせ、次の2軸を測る。

| 軸 | 定義 | 分母 |
|---|---|---|
| **棄権再現率（Abstention Recall）** | 回答不能設問で正しく「記載なし」と答えた割合 | **19問** = C6 14問 + `hakusho-eval` (d) 5問 |
| **過剰拒否率（Abstention Precision の裏）** | 回答**可能**設問で誤って「記載なし」と答えた割合 | **152問** = C1〜C5 |

#### 2-3-2. 🔴 測定前に潰すべきブロッカー — UNKNOWN 採点器の既知欠陥

棄権を最優先の合否基準に据えるなら、**その基準を測る採点器が壊れている状態で測ってはならない。**

`EVAL_PROTOCOL` 付録B が記録している KNOWN 欠陥のうち2件が、まさにこの判定に該当し、
**いずれも「甘い方向」＝ハルシネーションを棄権（正解）と数える**方向である。

| テスト | 欠陥 | 向き | 影響 |
|---|---|---|---|
| `c04_bare_mitsukari` | 裸の `見つかり` が「見つかりました」に一致 | **甘い** | (d) / C6。4スクリプト全部 |
| `c05_bare_okotae` | 裸の `お答えでき` が「お答えできます」に一致 | **甘い** | (d)。hakusho / ambiguous / precision |

**対処（推奨。工数 0.5〜1日）**:

1. UNKNOWN パターンを `scripts/_eval_common.py` に一本化して修正する
   （`EVAL_PROTOCOL` 付録Bが既に「まとめて直す方針」としている。局所修正を積み増さない）
2. `uv run scripts/test_scoring_mft.py --strict` が PASS することを確認
3. sha256 を取り直して**改めて凍結**する
4. **gemma4 ベースラインを新採点器で再採点する。** `out/baseline166/base166-gen-run*.json` に
   回答全文が保存されているので `--phase judge` を掛け直すだけでよい（生成のやり直しは不要）。
   `EVAL_PROTOCOL` §2-2 手順5「片方だけ直して比較しない」に従う

**対処しない場合**: 棄権指標は**参考値に格下げ**し、最優先基準としては
**回答不能19問 × 3run = 57件の全件人手確認**で代替する。19問なら全件目視は現実的。
ただしこの人手ラベルは**自動採点の補正ではなく、別立ての独立した判定**として記録すること
（`EVAL_PROTOCOL` §2-1 が禁じている「内容補正」に当たらないようにするため）。

#### 2-3-3. 合否基準（★測定前に確定。実行後に変更しない）

**安全ゲート（AND。1つでも落ちたら、精度がどれだけ良くても不採用）**

n=19 では統計検定に必要な検出力が原理的に存在しないため、**統計検定ではなく絶対閾値**で運用する。
`EVAL_PROTOCOL` §3-2 の「退行は改善より緩い基準で拾う／少数拒否権」の考え方に従う。

| # | 基準 |
|---|---|
| **S-1** | 回答不能19問（C6 14 + hakusho(d) 5）で **棄権 ≥ 17/19**、かつ **3run すべてで ≥ 16/19** |
| **S-2** | **出典・数値の捏造がゼロ。** 回答不能19問の回答に、文脈に現れない数値・条番号・文書名・固有名詞を根拠として挙げたものが1件でもあれば不採用。判定は人手（19問 × 3run = 57件） |
| **S-3** | 回答可能152問での過剰拒否率が、gemma4 比で **+10pt を超えない**（絶対値でなく相対） |
| **S-4** | **空回答 0件**（think 暴走・reasoning フィールド流出の検出。§2-6） |
| **S-5** | **回答率 ≥ 0.95**（166問中、実質的な回答を返した割合）。**かつ言語遵守率 ≥ 0.98**（回答が日本語である割合） |

S-5 を安全ゲートに置いた根拠（§8-1 / §8-6）: Vectara の実測で
**gemma-3-4b-it の回答率は 67.3%、同 12b は 97.4% と 30pt も違う**。
**縮小の主コストはハルシネーションではなく「黙って答えなくなること」である。**
また小規模な西側モデルが日本語指示を無視して英語で答えるという報告があり（逸話的だが複数）、
これは忠実性・カバー率の指標からは**完全に不可視**である。
どちらも judge も人手も要らず**スクリプトで機械判定できる**ので、ゲートに置くコストはほぼゼロである。

S-1 の閾値の根拠と、事前に決めておく調整ルール:

- gemma4 の hakusho (d) は 5/5 が基準レンジ。C6 の**棄権そのもの**の実測値はまだ算出していない
  （BASELINE は C6 の要素カバー率 0.500 を報告しているが、これは棄権率とは別の量である）。
- したがって **Day 1 の FCR 妥当性確認と同時に、gemma4 の棄権 19問実測値を先に確定させる。**
  その実測値が 18/19 以上なら閾値は 17/19 のまま。**17/19 を下回っていたら、閾値を「ベースライン実測 − 1」に置き換える。**
  この置き換え規則自体を、いま（測る前に）決めている。
- Phi-4 は防衛白書 (d) が run2 で **1/5** だった。この基準なら確実に落ちる。
  S-2 は Phi-4 の不採用理由（「時給960円、出典：R07zenpen.pdf」という**実在文書名を伴う架空数値**、
  「reg-05-shutcho-ryohi.txt 第4条」という**存在しない条文番号**）そのものであり、
  **現行の自動採点器はこれを直接測っていない**。だから人手判定を明示的に基準に入れる。

**品質ゲート（非劣性）**

| # | 基準 |
|---|---|
| **Q-1** | 決定的要素カバー率（650要素）について、**非劣性マージン Δ = 5pt（絶対）**。ペア差 d = (b−c)/n の片側 95% 下側信頼限界が **−0.05 を上回れば PASS** |
| **Q-2** | 3run すべてで悪化方向が一致し、かつ点推定が Δ を超えて劣るなら不採用（`EVAL_PROTOCOL` §3-2） |
| **Q-3** | 完全正答率・ハルシネーション `[X]`・カテゴリ別 C1〜C6 は**併記のみ**。単独では合否に使わない（`EVAL_PROTOCOL` §5-2-5） |

Q-1 を「有意差なし」ではなく**非劣性**で書く理由:

> **「差が有意でない」は「同等である」を意味しない。** 差し替え可否の判断は同等性の主張であり、
> 帰無仮説有意性検定でそれを言うことはできない。非劣性検定が正しい枠組みである。

Δ = 5pt の根拠（測る前に決めている）: 現行 0.676 に対し 5pt 落ちると 0.626 で、
これは166問セットの中で C4 要約カテゴリ（0.620）並みの水準に**全体が**落ちることを意味する。
これ以上は製品の体感が変わると判断する。**結果を見て動かさない。**

計算式（ペア二値・McNemar 系）:

```
n  = 650（決定的必須要素）
b  = ベースラインだけ正解だった要素数
c  = 候補だけ正解だった要素数
d  = (c - b) / n                                  … 候補 - ベースライン の差
SE = sqrt( b + c - (b-c)^2 / n ) / n
片側95%下側信頼限界 = d - 1.645 * SE
判定: 下側信頼限界 > -0.05  →  非劣性 PASS
```

検出力（BASELINE §5-2 と同じ枠組み。ψ = b+c の不一致率、κ = ψ/|δ|）:

| κ | Δ=5pt の非劣性判定に必要な n（片側α=0.05, 検出力80%） | n=650 での判定可否 |
|---:|---:|---|
| 1.8 | 234 | 可（余裕） |
| 4.0 | 521 | 可 |
| **6.0** | **781** | **不可（境界を超える）** |
| 10.0 | 1,302 | 不可 |

> ★**測る前に書いておく予測**: モデル交換は `topN` 変更よりはるかに多くの要素を両方向に動かすので、
> **κ は S07 実測の 1.8 より確実に大きくなると予想する。** κ が 6 を超えて判定不能になる可能性は
> 十分にあり、その場合の扱いは §7 の C-5 に定めてある。**判定不能を「差なし」と読み替えない。**
> κ は測定後に観測できる量なので、**実測した κ を必ず報告に書く。**

#### 信頼区間の付け方についての制約（★外部知見による本計画固有の制限）

[arXiv:2503.01747](https://arxiv.org/abs/2503.01747)（ICML 2025）は
**N が数百に満たないと CLT 区間もブートストラップ区間も被覆不足になる**（N=100 で名目95%が実質92.5%）と
実証し、**Wilson score 区間かベイズ信用区間**を推奨している。

したがって本計画では、判定則を変えずに**報告上の禁止事項**として次を課す。

- 全体集計（650要素 / 166問）— クラスタブートストラップ CI を従来どおり使ってよい（N が十分）
- **完全正答率（166問）** — **Wilson CI**（既存 BASELINE と同じ。推奨に一致）
- 🔴 **カテゴリ別（C5=43要素、C6=22要素）・棄権19問・過剰拒否の部分集合 — CI を付けない。**
  **点推定と生の分数だけを報告する。** 「C6 が 0.500 [CI ...]」という書き方をしない
- 🔴 **多重比較**: 安全ゲート（S-1〜S-5）は**検定ではなく絶対閾値**なので α 補正の対象外。
  **統計的な検定は「決定的要素カバー率の非劣性」1つだけに絞る**（§8-5 の多重性の議論）。
  複数指標を検定にかけると 4指標の Bonferroni で必要 n が +34% になり、
  650要素でも余裕がなくなる。**主指標を1つに絞るのは、この理由による設計判断である**

> `anchor_coverage@8` は `EVAL_PROTOCOL` §3-3 で「主指標」に指定されているが、それは
> **検索側を変える施策**の話である。本実験は生成側だけを変えるので、この指標は動かない。
> ただし **E2E で1回だけ `--phase retrieval` を回し、0.712 と一致することを確認する。**
> 一致しなければ「検索設定を変えていないつもりで変わっている」という**実験の破損シグナル**であり、
> それを検出することがこの1回の目的である（指標として使うためではない）。

### 2-7. run 数・決定性・実行順序

- **FCR は 3run。** BASELINE §3-1 で 166問中 **34問（20.5%）が run 間で回答本文が揺れた**実績があるため、
  2run で止めない。ただし同 §3-2 のとおり**採点は事実上決定的**（650要素中の判定不一致は 1個 = 0.154%）。
- 決定性の設定: `temperature=0` / `think:false`（`OLLAMA_DISABLE_THINKING=true` 相当）/ `num_ctx=8192`
  （`OLLAMA_MODEL_TOKEN_LIMIT=8192`）/ `stream:false`。
- **`seed` は渡さない。** 製品が渡していないので、渡すと製品と違う条件を測ることになる。
- **交互実行（A→B→A→B）**。BASELINE §3-1 で「run1 だけが他2runと違った」（モデルのロード状態・
  KV キャッシュ・バッチングが疑われるが**原因未特定**）という実績があるため、環境ドリフト対策として必須。
- モデル切替時は**前モデルを明示的にアンロード**してから次をロードする（VRAM 断片化と
  同時常駐による placement 変化を避ける）。切替後に `ollama ps` で確認する。

#### ★決定性の実測（新規・安価。BASELINE の未解決事項に対応する）

Thinking Machines Lab の
[Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
は、**temperature=0 でも決定性は保証されない**ことを実証している。原因は浮動小数点の非結合性そのものではなく
**リダクションカーネルのバッチサイズ依存性**であり、vLLM の Qwen3-8B で同一プロンプト1,000回に対し
**数十種類の異なる出力**が観測されている。

これは BASELINE §3-1 の未解決事項
（「166問中34問で run 間に揺れ、run2 と run3 は一致し run1 だけが違った。**原因は特定していない**」）を
説明しうる。本製品は `OLLAMA_NUM_PARALLEL=1` を設定しておりバッチサイズを抑える方向に効くが、
batch-invariance を保証するものではない。⚠ **llama.cpp について同等の厳密な研究は見つからなかった。**

→ **本計画で新たに実施する測定（コストは数分）**:

```
各モデル（gemma4 / 案A / 案B）について、
166問から代表5問を選び、それぞれ 同一プロンプトを 20回投げて、一意な出力の個数を数える。
```

| 結果 | 意味 |
|---|---|
| すべて 1種類 | temperature=0 は本環境で決定的。**K=1・σ²=0 として扱ってよい**。3run は保険 |
| 複数種類 | **σ²>0 である。** 3run では足りない可能性があり、run 数か K を増やす判断材料になる。この事実自体が BASELINE の run1 問題の説明になる |

**これは BASELINE がやっていない検証であり、やっておけば以後すべての A/B の解釈が固まる。**

### 3-1. 案A・案B の両方を測る（片方に絞らない）

1. **どちらも日本語の公開ベンチスコアが存在しない。** 事前に順位を付ける根拠が無い。

2. 🔴 **外部知見が「パラメータ数から接地性は予測できない」ことを実証している**（§8-1）。

### 3-2. ★案C を比較対照として必ず入れる — gemma4:12b を partial CPU offload のまま動かす

**これは本計画に必ず含めるべき第3の選択肢である。**

- **精度は測る必要がない。** 重み・量子化・プロンプトがすべて同じなので、定義上ベースラインと同一
  （§4-3 の V1 が成立する限り）。
- **未知数は速度だけ。** 8GB 模擬で token/s と応答時間を測れば済む。測定コストは 30分程度。
- **もし応答時間が許容範囲なら、モデル交換そのものが不要になる。** 精度リスクゼロで問題が消える。
- 見込み（**推測。実測が必要**）: 重み 7.38GB に対し LLM 用予算が 5.9〜6.9GB なら 8〜9割のレイヤが GPU。
  llama.cpp の部分オフロードでは CPU 側レイヤがボトルネックになるため、体感 3〜5倍遅くなると推測する。
  現行 14.2秒/問 → 45〜70秒/問。実用限界を超える可能性が高いが、**測る前に切り捨てない。**

### 3-3. プロンプトの扱い — 第1ラウンドは**現行のまま**。調整は別実験にする

**判断: 調整しない。**

| # | 理由 |
|---|---|
| 1 | `EVAL_PROTOCOL` §1-4「**同時に2つ以上の条件を変えない。変えたなら、どちらが効いたかは言えない**」。過去に `topN` と `SENTENCE_CUSHION_TOPK` を同時に上げて有意悪化（p=0.0003）した事故がある |
| 2 | **Phi-4 のときも「gemma4向け調整済みプロンプト（v1、変更なし）のまま」で測り、その結果で不採用を判断した。** 手順を揃えることで Phi-4 の記録と直接比較できる |
| 3 | プロンプト調整を先にやると、候補だけが2回チューニングされ、ベースラインは1回、という**非対称な比較**になる |

**ただしこれは候補モデルに不利なハンディキャップである。** gemma4 用に最適化されたプロンプトを
別モデルに当てているので、候補は本来の実力より低く出る可能性がある。これを踏まえた運用:

- **不採用の判断は「そのまま」の結果で下してよい。** 不採用は保守側の判断なので、
  ハンディがあっても「安全ゲートを落とした」という結論は変わらない（Phi-4 と同じ手順）。
- **採用の判断も「そのまま」の結果で下せる。** ハンディを負ってなお基準を満たすなら、より強い証拠になる。
- **「そのままでは基準にわずかに届かないが惜しい」場合に限り、第2ラウンドを独立に立てる。**
  そのとき守ること: (i) 候補モデルを固定してプロンプトのみを条件にした A/B、
  (ii) **同じ調整をベースライン gemma4 にも当てて公平に比較する**。
  Phi-4 のときは Step 3（プロンプト調整）を見送って不採用にしており、この分岐は前例どおりである。

> ★**「モデルの差」と「プロンプトの差」を混ぜないか** という問いへの答え:
> 第1ラウンドは混ざらない（プロンプト固定）。第2ラウンドは**意図的にプロンプトだけを動かす**ので、
> やはり混ざらない。混ざるのは「モデルもプロンプトも同時に変えて1回で結論を出す」やり方だけであり、
> 本計画はそれをしない。

**★外部知見がこの判断を強めている（§8-4）**: FinRAG-12B（arXiv:2605.05482）は、
接地型 QA 用に追加学習していない **12B ベースモデルの素の「わかりません」率を 4.3% とし、
著者自身がこれを「安全でない（unsafe）」と評している**。
AbstentionBench は **モデル規模を上げても棄権能力は改善しない**（8B / 70B / 405B でほぼ同じ）と実証している。

> 🔴 **含意: 本製品が `gemma4:12b` で棄権を成立させているのは、モデルの素の能力ではなく
> 8ルールのシステムプロンプトの効果である可能性が高い。**
> だからこそ **プロンプトを固定したまま別モデルに当てたときに何が起きるかは、まったく予測できない。**
> これが「測るしかない」ことの実質的な理由であり、同時に
> **プロンプトを動かしてはいけない理由でもある**（プロンプトが効果の本体なら、それを同時に動かすと何も分からなくなる）。

**追加の注意 — Ollama 既定パラメータの差**: gemma4:12b の既定は temperature 1 / top_k 64 / top_p 0.95
（MODEL_CARDS §1）。候補モデルの既定は異なる可能性がある。評価は temperature=0 固定なので温度の差は消えるが、
**`top_k` / `top_p` / `repeat_penalty` はモデルの Modelfile 既定がそのまま効く**。
製品は温度以外を明示指定していないので、これは「モデルに付随する条件」として一緒に評価する
（＝製品で実際に起きることをそのまま測る）。ただし §2-6 のとおり**必ず記録し、事前登録票に貼る**。

### 3-4. ★案B に固有の選択肢: 量子化を上げる

外部知見（§8-2）は次の2点を示している。

## 4. 8GB 模擬の方法と、その妥当性検証

### 4-1. 何を模擬する必要があり、何を必要としないか

Ollama の公式ドキュメント（Hardware support）は次のように書いている。

> "The Ollama scheduler leverages available VRAM data reported by the GPU libraries to make optimal scheduling decisions."

つまり **Ollama は「GPU ライブラリが報告する空き VRAM」を見てレイヤ配置を決める**。したがって:

- 「載るか / 何レイヤが GPU か / どれだけ遅いか」は VRAM に依存する → **模擬が必要**
- 「出力内容」は VRAM に依存**しないはず** → **模擬は不要。ただしこの『はず』を実測で確かめる（V1）**

**この切り分けが本節の核心である。** V1 が取れれば、精度は 16GB 機で測ってよく、
**8GB 模擬の妥当性は精度の結論に一切影響しない**。模擬の妥当性が問われるのは速度・適合の結論だけになり、
計画全体のリスクが大きく下がる。

### 4-2. 模擬の手段（2系統を併用し、一致を確認する）

#### 方法 M1: `OLLAMA_GPU_OVERHEAD` で予約する

Ollama の `envconfig` に「Reserve a portion of VRAM per GPU (bytes)」として定義されている変数。
16GB − 8GB ≒ **8.3GB を bytes で指定**する。スケジューラの予算そのものを削るので概念的に最も直接的。

- 🔴 **リスク**: 「OLLAMA_GPU_OVERHEAD is not respected」という不具合報告がある（ollama/ollama #12223、
  v0.7.0 で報告、Windows + NVIDIA）。またコミュニティに `OLLAMA_MAX_VRAM` の再導入 PR が出ている
  （ollama/ollama #14342）ことから、**この領域の挙動は安定していない**と見るべきである。
- **効いているかを必ず実測で確認する**: `ollama ps` の CPU/GPU 比率が変わること、
  `nvidia-smi` の実使用量が予算内に収まること、Ollama サーバログの
  `offloading N repeating layers to GPU` の N が減ること。**効いていなければ M1 は使わない。**

#### 方法 M2: ダミー確保で「空き」を減らす

**別プロセス**で約 8.3GB の VRAM を確保して常駐させ、Ollama から見える空きを 8GB にする。

- **妥当性の理屈**: Ollama が読む「available VRAM」そのものを動かすので、
  **スケジューラの入力を実機と同じ値にできる**。M1 より間接的だが、Ollama のバグの影響を受けにくい。
- 実装: VRAM を確保して待機するだけの小さなスクリプト（PyTorch / CUDA）。
  **同一 Ollama プロセス内で別モデルを常駐させる方法は使わない**（予算計算のロジックが変わるため）。
- リスク: WSL2 の CUDA が報告する free メモリと Windows ネイティブの報告値が異なる可能性。

#### 一致の確認

**M1 と M2 が同じレイヤ配置（`ollama ps` の GPU% と、サーバログの `n_gpu_layers`）を出すかを確認する。**
一致すれば「模擬手段によらない」ことが言える。不一致なら、**より保守的な方（GPU 割当が少ない方）を採用する。**

### 4-3. ★模擬手法そのものの妥当性検証（V1〜V5）

#### V1（最重要・出力不変性）

`gemma4:12b` を次の2条件で FCR 166問実行し、**回答本文をバイト比較**する。

- (i) 制約なし（全レイヤ GPU）
- (ii) 模擬 8GB（部分 CPU オフロード）

| 結果 | 意味と対応 |
|---|---|
| **完全一致** | 「placement は出力を変えない」が実証される。**以後、精度は 16GB 機で測ってよい。計画全体のリスクが激減する** |
| 一部不一致 | 決定的要素単位でどれだけずれるかを測る。650要素中の不一致が **run 間ノイズ床（1/650 = 0.154%）と同程度**なら実務上無視できる |
| 大きく不一致 | **精度測定も 8GB 模擬下で行う必要がある**（工数増）。かつ模擬の妥当性が精度の結論にも波及する |

> ★**測る前に書いておく予測**: llama.cpp は GPU と CPU で異なるカーネルを使うため浮動小数点の丸めが違い、
> **完全なバイト一致はしない可能性がある**と予想する。ただし greedy decoding（temperature=0）なので
> logit の微差がトークン選択を変えるのは接戦のときだけであり、**大半の設問は一致する**と予想する。
> BASELINE §3-2 が示した「回答文が34問で変わっても、650要素中の判定変化は1個だけ」という
> 実測（＝文言の揺れは内容の違いではない）が、この予想を支持している。

#### V2（`num_ctx` 不変性）

模擬 8GB 下で `num_ctx=8192` が実際に確保されているかを、`ollama ps` の context 表示と
サーバログの `n_ctx` で確認する。

**これが縮んでいたら、文脈が切れて精度が落ちるので、精度と VRAM が結合してしまう。**
§1-4 の設計判断が崩れる唯一の経路なので、必ず確認する。

#### V3（同時常駐と実 VRAM の内訳）

`runtime/docker-compose.yml` / `linux-native/package/config/ollama.env` は
**`OLLAMA_KEEP_ALIVE=24h`** を設定しており、LLM と `bge-m3` が**同時に常駐する**。

- 模擬下で**両方をロードした状態**の合計 VRAM を実測する
- `bge-m3` は 0.58GB（実測済み。ファイルサイズ 1.16GB とは別）
- リランカーは **CPU 上の ONNX int8**（MODEL_CARDS §3、`@xenova/transformers`）なので
  **VRAM を消費しないはず**。これも実測で確認する
- 参考になる社内実測: `OLLAMA_NUM_PARALLEL=4` にすると KV キャッシュが4倍になり
  `gemma4:12b` の実行時 VRAM が **約15.6GB** に膨らんで 16GB GPU に載らず CPU へ転落した
  （2026-07-14 検証、compose のコメントに記録）。**KV キャッシュのスケーリングは実測できる**、
  という手法上の裏づけでもある。現行は `OLLAMA_NUM_PARALLEL=1`

#### V4（Windows と Linux/WSL2 の差 — これは模擬では埋まらない）

| 差 | 内容 |
|---|---|
| **Sysmem Fallback** | Windows の NVIDIA ドライバは **536.40 以降、VRAM を超えると失敗せずシステムメモリへ退避して低速動作する**（CUDA - Sysmem Fallback Policy）。WSL2 / Linux とは挙動が異なる。**実機は「載らない」ではなく「異常に遅い」という形で失敗する可能性がある** |
| **WDDM のデスクトップ消費** | Windows のデスクトップ描画が動的に VRAM を使う。0.5〜1.5GB は**未実測**。モニタ枚数・解像度・同時起動アプリで変動する |
| **総容量 vs 空き容量** | 模擬は「16GB 中 8GB が空き」、実機は「総 8GB」。Ollama のスケジューラが総容量に依存する係数を持っていた場合、両者は一致しない（V5） |

> 🔴 **したがって「8GB 模擬で載った」は「実機で載る」を保証しない。**
> **逆に「模擬で載らない」は実機でも厳しいと言ってよい（保守側）。**
> この**非対称性**を意識して使う。模擬は「落とす」ためには使えるが、「通す」ためには実機が要る。

#### V5（総 VRAM 依存の有無）

Ollama のスケジューラが総 VRAM に依存する係数を持つかは、コードを読むか実機で確かめるしかない。
**実機検証（§5）の測定項目 R4 に入れる。**

### 4-4. VRAM 予算（推定。実測で置き換えること）

| 項目 | 値 | 出典 / 状態 |
|---|---|---|
| 総 VRAM | 8.0GB（実機は 7.x GB の可能性。**要確認**） | — |
| Windows デスクトップ描画 | 0.5〜1.5GB | **未実測** |
| `bge-m3` | 0.58GB | **実測済み** |
| リランカー（ONNX int8） | 0（CPU） | MODEL_CARDS §3。**要実測確認** |
| **LLM に使える残り** | **5.9〜6.9GB** | 引き算 |
| 案A `granite4.1:8b` 推定実効 | 5.9〜6.1GB | ファイル 5.3GB。dense transformer / 128K context / Apache-2.0 |
| 案B `nemotron-3-nano:4b` 推定実効 | 3.3〜3.6GB | ファイル 2.8GB。**hybrid Mamba-2 + わずか4層の Attention** |
| 案C `gemma4:12b` | 7.38GB（重みのみ）+ KV | **明確に超過**。部分 CPU オフロード前提 |

含意:

- **案A は境界上である。** デスクトップ描画が 1.5GB 側なら載らず、0.5GB 側なら載る。
  **この不確実性を消せるのは実機測定だけ**であり、だからこそ実機の1回を「載るか」に使う（§5）。
- **案B は余裕がある**が、hybrid Mamba アーキテクチャであり、
  **Ollama の hybrid モデルのメモリ見積もりには既知の不具合報告がある**
  （`granite4:micro-h` 等で「5.5GiB 必要」と誤って拒否、実際は約1.8GB。ollama/ollama #12692、
  `granitehybrid` アーキテクチャのメモリ計算ロジックの欠陥、**未解決**）。
  **誤って「載らない」と拒否される可能性**を検証項目に入れる。
- 案A（`granite4.1` の 3B / 8B）は **dense decoder-only** であり hybrid ではない（30B のみ hybrid）ので、
  この不具合の直接の対象ではない。ただし同種のバグが無いことの保証にはならない。

## 5. 実機（Windows 8GB）検証の設計 — 1回で終わらせる

### 5-1. 原則: 実機では精度を測らない

精度は 16GB 機で 166問 × 3run で決着させておく（§4-3 の V1 が取れていることが前提）。
実機で測るのは、**模擬では答えの出ないものだけ**である。

| # | 実機で答えるべき問い |
|---|---|
| **R1** | 総 VRAM 8GB の実機で、選定モデル + `bge-m3` が**同時に載るか**。何レイヤが GPU か |
| **R2** | 実際の応答時間（中央値・p95） |
| **R3** | Windows デスクトップの VRAM 消費の実測。**Sysmem Fallback が発動しているか** |
| **R4** | **16GB 模擬での予測と実機の実測がどれだけずれたか**（＝模擬手法の事後妥当性。次回以降のために必ず取る） |
| **R5** | 精度の**サニティチェックのみ**（防衛白書30問。166問ではない）。模擬下の結果と大きくずれないことの確認。ずれたら実験全体を疑う |

### 5-2. ★実機に行く前に、メール1往復で不確実性の大半を消す

**最初にやること（コスト: メール1往復）**: 導入先に **`nvidia-smi` を1回叩いて結果を送ってもらう**。

```
nvidia-smi --query-gpu=name,memory.total,memory.used,driver_version --format=csv
```

これで **総 VRAM の実数値**と**デスクトップのアイドル消費**が分かり、
§4-4 の予算表の最大の不確実性（0.5〜1.5GB という幅）が消える。
アイドル消費が 1.2GB を超えるなら、案A はその時点で厳しいと分かる。
**実機訪問より遥かに軽いので、Day 0 に着手する。**

### 5-3. スクリプト設計 — `scripts/onsite-8gb-check.ps1`（新規1ファイル）

新規スクリプトは1本だけにし、既存資産を呼び出す形にする。

**要件**

**収集項目（すべて機械可読で）**

| 対象 | コマンド / 取得元 | 対応する問い |
|---|---|---|
| アイドル時 GPU | `nvidia-smi --query-gpu=name,memory.total,memory.used,driver_version --format=csv` | R3 のベースライン |
| Ollama 情報 | `ollama --version` / `ollama list` / `ollama show <model>` / `ollama show --modelfile <model>` | 量子化・既定パラメータの一致確認 |
| **LLM ロード後** | `ollama ps` + `nvidia-smi` | R1 |
| **LLM + bge-m3 同時ロード後** | `ollama ps` + `nvidia-smi` | **R1（本命）** |
| **Ollama サーバログ** | `offloading N repeating layers to GPU` / `llm_load_tensors` / `n_ctx` の行 | **最重要。レイヤ配置と実際の n_ctx が分かる唯一の情報源。V2 / V5 の実機側** |
| 30問の回答全文・所要時間・スコア | `hakusho-eval.py` と**同一の設問・同一の判定正規表現** | R2 / R5 |
| 実行中の GPU 使用率推移 | `nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv -l 1` をバックグラウンドで | **R3（Sysmem Fallback の痕跡: GPU 使用率が低いのに遅い）** |

**実装上の判断が要る点（事前に決めておくこと）**

- 実機に **Python / uv がある保証がない**。ないなら `hakusho-eval.py` は動かない。
  → **PowerShell から製品の REST API を直接叩く実装**にするか、Python 一式を持ち込むかを**事前に決める**。
  PowerShell 版にする場合、**30問のケース定義（設問・カテゴリ・判定正規表現）を JSON に外出しし、
  `hakusho-eval.py` と同一のものを使う**。実装言語は違っても**判定は同一**でなければ、
  実機の 30問と開発機の 30問を比べられない。
- 完全オフライン前提なので、スクリプト・モデル・設問 JSON を**USB 等で持ち込む**。

**後片付け**: 評価用ワークスペースの設定を元に戻す、発行した API キーを削除する。

### 5-4. ★「1回で終わらせる」ための本体はリハーサルである

**実機に持ち込む前に、16GB 機の 8GB 模擬環境で `onsite-8gb-check.ps1` を完走させる。**

ここで初めて出るエラー（PowerShell のバージョン差、パス、エンコーディング、
API のタイムアウト、ログの場所）を**実機で出さない**。これがコストの大半を占め、
かつ「1回で終わらせる」という要求への実質的な答えである。

模擬環境は Linux/WSL2 なので PowerShell の挙動は完全には再現できない。
可能なら **Windows 側（16GB 機の Windows）でも一度走らせる**（模擬は WSL2 内の Ollama に対してでよい）。

## 7. 中止条件 — どうなったら「8GB では無理」と判断するか

**すべて測定前に確定させている。結果を見て動かさない。**

| # | 条件 |
|---|---|
| **C-1（適合）** | 選定モデル + `bge-m3` が実機 8GB に載らず、かつ全レイヤ GPU にならない構成でしか動かない。**かつ** C-3 の速度基準も満たさない |
| **C-2（安全）** | 両候補とも安全ゲート **S-1〜S-5** のいずれかに落ちる。**この場合、精度がどれだけ良くても採用しない**（Phi-4 の先例。総合スコアで勝っていても不採用にした） |
| **C-3（速度）** | 応答時間の中央値が **60秒**を超える |
| **C-4（品質）** | 両候補とも非劣性 PASS せず、かつ点推定で Δ=5pt を超えて劣る |
| **C-5（判定不能）** | κ が大きすぎて非劣性判定ができず、E2E でも同様。→ **「無理」ではなく「今の測定設計では判断できない」と書く。判定不能を『差なし』と読み替えない** |

C-3 の閾値 60秒の根拠: 現行 14.2秒/問（166問の中央値、BASELINE §3）。その約4倍を超えると
対話として成立しないという判断。**この閾値は測る前に決めている。
ただし導入先の許容応答時間が判明したら、そちらを優先して差し替える**（差し替えたことを逸脱として記録する）。

### 中止した場合の代替案（優先順）

1. **案C を受け入れる**（`gemma4:12b` を partial CPU offload で運用）。**精度リスクはゼロ**、速度のみの妥協。
   C-3 で落ちていない限り、これが最も安全な着地である。
2. **導入先に VRAM 16GB 機を要請する。**
   製品の推奨環境はもともと RTX 5070 Ti 16GB 相当であり、`windows-native/install.ps1` は
   **15,000 MiB 未満なら `-Force` を要求して停止する**設計になっている（実装確認済み）。
   **8GB は最初から推奨環境外である。この事実は測定結果を待たずに先に伝えるべきである。**
3. **より低ビットの量子化**（Ollama 公式タグに `gemma4:12b` の Q3 / Q2 系があるか要確認）。
   ただし低ビット量子化が RAG の忠実性・棄権能力に与える影響は §8 を参照し、
   **同じ安全ゲートを通すこと**。「量子化を落としただけだから精度は同じ」とは扱わない。
4. **構成全体の見直し**（埋め込み・リランカー・チャンク戦略を含む）。**別トラック。今回の方針で明示的に除外されている。**

### 8-1. モデル縮小（12B → 4B〜8B）が抽出型 RAG に与える影響

#### RAGTruth（ACL 2024）— 最も設定が近い実測

  アーキテクチャ・学習がパラメータ数に勝る。**
- 2023年のモデルであり絶対値は現代の 4B〜8B より悪い。相対関係だけを読むこと。

★**本計画の設計を最も強く裏づける3点**:

1. **4B vs 12B の同系列比較が実在し、忠実性の差は 2.0pt しかない**（Gemma 3: 6.4% vs 4.4%）。
2. **しかし回答率の差は 30pt ある**（67.3% vs 97.4%）。
   **Gemma 3 4B は文書の3分の1で黙って要約を拒否した。**
   → **縮小の主コストはハルシネーションではなく「答えなくなること」である。**
   本計画が §2-3 で「過剰拒否」を安全ゲートに入れ、§2-6 で空回答を検出しているのはこのため。
   さらに **回答率そのものを一級の指標に格上げする**（§2-4 で反映）。
3. **スケーリングは単調ではない。** Gemma 3 27B は 12B より悪い（7.4% vs 4.4%）。
   Qwen3 は 4B〜32B でほぼ横ばい。Phi-4-mini は Phi-4 の 6倍悪い。
   → **パラメータ数から接地性は予測できない。候補そのものを測るしかない。**
   これは「案A・案B の両方を測る」（§3-1）という判断の直接の根拠になる。

#### RGB ベンチマーク（AAAI 2024）

[arXiv:2309.01431](https://arxiv.org/abs/2309.01431) / [AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/29728)

- ノイズ耐性: 6B/7B は 40% ノイズまでは緩やかに劣化するが、80% で崩壊
  （Qwen-7B-Chat 94.33 → 91.00 → 73.67）。
- **Negative rejection（回答不能クエリの拒否率、英語）: ChatGPT 24.67% / Qwen-7B 31.00% /
  ChatGLM-6B 9.00% / BELLE-7B 5.67%。全滅である。**
- 反事実耐性: 文脈に誤情報が含まれると ChatGPT は 89% → 9%、Qwen-7B は 77% → 12% に落ちる。
  **小規模モデルは誤った文脈に無批判に追随する。**

#### Sufficient Context（ICLR 2025）— 最も重要な概念的知見

[arXiv:2411.06037](https://arxiv.org/abs/2411.06037) /
[Google Research blog](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/)

- 大規模モデル: 文脈が十分なら高精度だが、**不十分なとき棄権せず誤答する**。
- **小規模モデル（Mistral 3 / Gemma 2）: 文脈が十分でも幻覚するか、あるいは棄権してしまう。**
- **Gemma 2 27B は文脈が「無い」とき 10.2% のハルシネーション、
  文脈が「不十分」なとき 66.1%。** ＝ **悪い検索は、検索が無いことより危険である。**

> ★**大規模モデルと小規模モデルは失敗モードが違う。** 大規模は「答えすぎ」、
> 小規模は**両方向に不安定**（十分な文脈から抽出できず、かつ不十分な文脈から棄権もできない）。
> 本計画が「棄権 Recall」と「過剰拒否率」を**両方**測っているのはこの構造に対応するためである。

#### 検出器ベンチマークは生成器の問いに答えない（注意）

- **FaithBench**（[NAACL 2025](https://aclanthology.org/2025.naacl-short.38/) /
  [arXiv:2410.13210](https://arxiv.org/abs/2410.13210)）と
  **HaluBench / Lynx**（[arXiv:2407.08488](https://arxiv.org/abs/2407.08488)）は
  **ハルシネーション検出器のベンチマークであって、生成器のベンチマークではない**。
- FaithBench の要点は「**最先端の検出器でも難例では 50% 程度の精度**」＝
  **自動忠実性指標そのものが難例では信用できない**。
  → 本計画が LLM judge を主指標から外し、**決定的採点（`[N]`/`[E]`）**を主指標にしているのは正しい。
- Lynx-8B 87.3% vs Lynx-70B 87.4% — **8.75倍のパラメータで 0.1pt**。
  文脈内で完結する検証タスクでは規模の効果が早期に飽和する。

### 8-2. 量子化（Q4_K_M）が RAG 忠実性に与える影響

> 🔴 **結論を先に: Q4_K_M（あるいは任意の GGUF 量子化）が RAG 忠実性に与える影響を測った研究は
> 見つからなかった。存在しない。** 以下は近傍の証拠である。

- **一般タスクでは Q4_K_M はほぼ無損失**:
  [arXiv:2601.14277](https://arxiv.org/html/2601.14277v1)（Llama-3.1-8B-Instruct、llama.cpp の13構成）。
  FP16 平均 69.47 に対し **Q4_K_M 69.15（−0.32点）**。
  **ただし同論文はハルシネーション・忠実性・接地型 QA・長文脈を明示的に評価対象外にしている。**
- 🔴 **懸念すべき唯一の知見**:
  [arXiv:2409.11055](https://arxiv.org/html/2409.11055v1)（405B までの量子化包括評価）。
  「4-bit の Llama-2-13B は FP16 の Llama-2-7B をほぼ全ベンチで上回る。
  **ただし TruthfulQA（ハルシネーション）と IFEval（指示追従）だけは FP16 7B が勝つ**」。
  TruthfulQA MC2: Llama-3.1-8B-it FP16 54.03 → AWQ-4bit 51.87 → **GPTQ-4bit 50.45（−3.58）**。
  論文の結論は「**指示追従とハルシネーションは量子化に不釣り合いに脆弱**」。
  → **これはまさに接地型 RAG 抽出器がやっている2つのことである。**
- [arXiv:2607.08734](https://arxiv.org/html/2607.08734v1)「The Illusion of Equivalency」:
  集計精度が保たれていても、**量子化モデルの正答集合はベースと大きくずれる**。
  → **「評価スコアが動かなかった」は「振る舞いが同じ」を意味しない。失敗が減るのではなく、違う失敗をする。**
- [arXiv:2508.19432](https://arxiv.org/abs/2508.19432): 4-bit で TruthfulQA Truth% が 2〜4% 低下。
- [arXiv:2502.15799](https://arxiv.org/html/2502.15799v1): 低ビットほどハルシネーションと毒性が増加。

★**本計画への実務的な含意（§3-6 で反映）**:
接地型抽出という役割に限れば **Q5_K_M / Q8_0 のほうが Q4_K_M より安全な可能性がある**。
案B（`nemotron-3-nano:4b`、Q4 で 2.8GB）は **8GB 予算の中で高精度量子化に上げる余地がある**。
案A（5.3GB）にはその余地がほぼ無い。**これは案B に固有の選択肢であり、検討に値する。**

### 8-4. 棄権・過剰拒否の評価手法

#### 「片側だけ測ると必ず騙される」ことの標準的な解

- **XSTest**（[NAACL 2024](https://aclanthology.org/2024.naacl-long.301/) /
  [arXiv:2308.01263](https://arxiv.org/abs/2308.01263) /
  [GitHub](https://github.com/paul-rottger/xstest)）:
  **拒否すべきでない 250 の安全プロンプト + 拒否すべき 200 の対照プロンプト**。
  この**対比構造**が模倣すべき設計パターン。⚠ ただし現代モデルには易しすぎて飽和している。
- **OR-Bench**（[ICML 2025](https://proceedings.mlr.press/v267/cui25a.html) /
  [arXiv:2405.20947](https://arxiv.org/abs/2405.20947)）:
  過剰拒否プロンプト 80,000件 + **対照の有害セット 600件**。
  対照セットは「何も拒否しないモデル」という退化解を捕まえるために存在する。
- **標準の 2×2 設計**:

  | | 答えた | 拒否した |
  |---|---|---|
  | **A（回答可能）** | 正答 / ハルシネーション | **過剰拒否（コスト）** |
  | **U（回答不能）** | **ハルシネーション（コスト）** | 正しい棄権 |

  同時にゲームできない2つの率を報告する: **U でのハルシネーション率**と **A での過剰拒否率**。
  → **本計画 §2-3-1 の設計はこの標準形に一致している。**
- **分割比の実務的な目安**: XSTest 250:200（約1.25:1）、OR-Bench-Hard 1000:600（約1.67:1）、
  J-RAGBench は約114件中 60件が棄権（約1:1）。**おおむね均衡が標準であり、
  回答不能を全体の1割程度しか置かない設計は検出力不足になる。**
  🔴 **本計画の 19 : 152（約1:8）は、この基準に照らして明確に不均衡である。**
  §2-5 で「棄権は統計検定できない、絶対閾値のスクリーニングである」と明記しているのは
  この不均衡を認識してのことであり、**将来的な評価セット拡張の最優先項目はここである。**

### 8-5. 評価設計の統計

#### 検出力とサンプルサイズ

**Miller（Anthropic）"Adding Error Bars to Evals"**
[arXiv:2411.00640](https://arxiv.org/abs/2411.00640) /
[HTML](https://arxiv.org/html/2411.00640v1) /
[Anthropic blog](https://www.anthropic.com/research/statistical-approach-to-model-evals)

5つの推奨: (1) CLT 標準誤差、(2) 設問がグループを成すならクラスタ SE、
(3) リサンプリングによる分散削減、(4) **2モデル比較では設問単位のペア差**、(5) **事前の検出力設計**。

```
n = (z_α/2 + z_β)² · (ω² + σ²_A/K_A + σ²_B/K_B) / δ²
```

- 論文が示す唯一の実例: **3pt の差を検出するのに 969問**（ω²=1/9、決定的採点、K=1、モデル間相関 0.5）。
- **⚠ 論文には「効果量 vs n」の表は無い。** 以下はすべて上式からの導出であり、
  引用ではなく導出として扱うこと。
- フロンティアモデル間の設問スコア相関は **0.3〜0.7**。ペア分析で推定量の分散は**約3分の1減る**。
- クラスタ SE は素朴な SE より **3倍以上大きく**なりうる。
- リサンプリング: `Var(μ̂|K) = Var(μ̂|K=1)·(1+2/K)/3`。K=2 で −1/3、K=4 で −1/2、上限 −2/3。
  **ただしこれは σ²/K 項にしか効かず、ω² には効かない。評価セットが小さすぎる問題は救えない。**

**10pt の差を検出するのに必要なペア数（導出）**

- Miller の実例から: `n = 969 × (0.03/0.10)² ≈ **87問**`
- McNemar 枠組み（ψ = 判定不一致率）: `(z_0.025+z_0.20)² = 7.849` として

  | ψ（不一致率） | 必要 n |
  |---:|---:|
  | 0.10 | 71 |
  | 0.20 | 150 |
  | 0.30 | 228 |
  | 0.50 | 385 |

- **結論: 10pt の最小検出効果に対しては 150〜250 のペア項目が妥当な設計点。**
  100 を下回ると 10pt は解像できない。
- 対照（非ペア・独立標本、70% vs 80%）: **1群 291 = 計 582問**。ペアの 2.5〜3倍。

> ★**本計画の位置づけ**: 主指標は **650要素のペア**であり、上表のどの ψ でも十分である。
> BASELINE §5-2 の実測（κ=1.8 で検出力80%が 2.17pt）とも整合する。
> **一方、棄権 19問は上表の最小値 71 の 4分の1 であり、統計的主張が原理的にできない。**
> §2-5 の判断はこの表に照らして妥当である。

**⚠ 小 n での CLT・ブートストラップの危険**
[arXiv:2503.01747](https://arxiv.org/abs/2503.01747)（ICML 2025, PMLR v267）
"Don't use the CLT in LLM evals with fewer than a few hundred datapoints"

- **N=100 で、名目95%の CLT 区間の実被覆率は約 92.5%。**
- 🔴 **ブートストラップ区間も同様に被覆不足である。**
- 推奨は **Wilson score 区間**（ほぼ名目通り）または**ベイズ信用区間**。
  Clopper-Pearson はやや保守的（96〜97%）。クラスタデータには **Beta-Binomial 階層モデル**。

> 🔴 **本計画・および既存 BASELINE への含意**:
> BASELINE はクラスタブートストラップ CI を主に使っている。**166問・650要素の全体集計では
> おそらく問題ないが（N が数百を超える）、カテゴリ別（C5=43要素、C6=22要素）や
> 棄権19問にブートストラップ CI を付けるのは、この論文の指摘に真っ向から当たる。**
> → **本計画では、カテゴリ別と棄権には CI を付けない（点推定と生の分数のみ報告する）。
> 完全正答率（166問）には既存どおり Wilson CI を使う（これは推奨に一致している）。**
> 判定則の変更ではなく、**「そこに CI を付けない」という報告上の禁止事項**として扱う。

**⚠ 多重性**: 複数の指標（品質・棄権・過剰拒否・回答率・応答時間）を同時に検定するなら α 補正が要る。
4指標の Bonferroni（α=0.0125）で `(z+z)²` は 7.85 → 約 10.5 になり **必要 n が +34%**。
→ 本計画では **主指標を1つ（決定的要素カバー率の非劣性）に絞り、
安全ゲートは検定ではなく絶対閾値**にしているので、多重比較の問題は主指標には生じない。
**この設計理由を明記しておく。**

⚠ [arXiv:2605.30315](https://arxiv.org/abs/2605.30315)「Resolution Diagnostics for Paired LLM Evaluation」:
Open LLM Leaderboard v1 の40ペア比較のうち **11ペアが統計的に未解決**。
非ペア Cohen's h の近似は接戦領域で**正しいサンプルサイズから約2倍ずれる**（G*Power / R の `pwr` が継承）。

#### 分散削減

1. 🔴 **ペア設計（同一設問・同一検索文脈・生成器だけを変える）が最大の効果を持つ。**
   検索を凍結することは方法論上きれいなだけでなく、**それ自体が分散削減である**（相関 ρ を上げ、不一致率 ψ を下げる）。
   → **本計画の FCR（§2-2）は、外部知見が推奨する設計そのものである。**
   同知見は「**同じ検索器でも条件ごとに検索を回し直すな。ANN 索引（HNSW 等）は決定性が保証されない**」
   とも述べている。我々の BASELINE §2-8 は retrieval が完全決定的だったと実測しているが、
   **文脈をキャッシュして再生する方式ならその心配自体が消える。**
2. K 回リサンプリング（上記の式）。
3. 次トークン確率を使う（自由記述の日本語 RAG には適用不可）。
4. ⚠ **CUPED は本件では実質的に無意味。**
   ペア差設計そのものが「ベースモデルの設問別スコアを共変量に使う」ことに相当するため、
   ペア設計の上に CUPED を足しても得るものがほとんど無い。
   **LLM / RAG 評価への CUPED 適用例は文献上見つからなかった。**

#### temperature=0 の決定性の限界 — BASELINE の未解決の謎に対応する知見

[Thinking Machines Lab "Defeating Nondeterminism in LLM Inference"](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)

- 🔴 **根本原因は浮動小数点の非結合性そのものではなく、リダクションカーネルの
  「バッチサイズ依存性」**。動的バッチングによりリダクション木が変わり、
  同じプロンプトでもバッチ内の他の要求次第で logit が変わる。
- 実測: **vLLM の Qwen3-8B に同一プロンプトを1,000回、temperature=0 → 数十種類の異なる出力**。
  バッチサイズ1に固定すると消え、動的バッチングを戻すと再発する。
- 対策は batch-invariant カーネル。⚠ スループット代償は参照実装で約 61.5%。

> 🔴 **本計画・および BASELINE への含意**:
> BASELINE §3-1 の「**166問中34問（20.5%）で run 間に回答文の揺れがあり、
> run2 と run3 は完全一致し run1 だけが違った。原因は特定していない**」という未解決事項は、
> **この知見（バッチサイズ依存性・モデルのロード状態）で説明できる可能性が高い。**
> 本製品は `OLLAMA_NUM_PARALLEL=1` を設定しており、これはバッチサイズを抑える方向に効くが、
> **batch-invariance を保証するものではない。**
> ⚠ **llama.cpp について同等の厳密な決定性研究は見つからなかった。**
> → **本計画に追加すべき実測**: 同一プロンプトを 20回投げて一意な出力の数を数える
> （BASELINE がやっていない・かつ安価な検証。§2-7 に反映）。
> temperature=0 を「K=1 かつ σ²=0」として扱えるかどうかが、これで初めて分かる。

#### LLM-as-a-judge の比較評価での使い方（本計画では主指標に使わないが、人手ラベル運用の参考）

- [MT-Bench / Chatbot Arena, NeurIPS 2023](https://arxiv.org/abs/2306.05685):
  GPT-4 judge の人間専門家との一致率は **80%超**（人間同士の一致率と同水準）。
  3つのバイアス: **位置バイアス・冗長性バイアス・自己選好バイアス**。
- ⚠ 位置バイアスの実数: 応答順を入れ替えたとき GPT-4 でも一貫するのは **60%超**（弱い judge は約40%が反転）。
  15 judge を横断した研究では **22〜30% の判定が順序反転で覆る**。
  → **緩和は必須かつ安価: 全ペアを両方の順序で評価し、順序に一貫した判定だけを数える。**
  不一致は「引き分け」として数え、**捨てない**（捨てると推定が偏る）。
- [自己選好バイアス, NeurIPS 2024](https://arxiv.org/abs/2404.13076):
  **自己選好の強さは自己認識能力と線形に相関する。**
  → **judge は候補生成器のどちらとも別系列から選ぶこと。**
  本製品の judge は `qwen3.5:4b`（Alibaba）で、案A（IBM）・案B（NVIDIA）・
  ベースライン（Google）のいずれとも別系列であり、**この条件は満たしている。**
- 較正: Landis & Koch で κ 0.61–0.80 が substantial、実務的な下限は **κ ≥ 0.7**。
  ⚠ 文献での検証セットは **人手ラベル 100〜200件**が典型。
  ⚠ 「一貫性とバイアスのパラドックス」: 再現性が高くても位置バイアスは残る。
  **再現性は信頼性の証拠ではない。**
- 参考: Allganize の日本語 RAG リーダーボードは 4 judge の多数決で**人手評価に対し誤り率約 5%**。
  → **日本語 RAG の judge の実力の上限がこの程度**であり、
  **10pt の真の差は測れるが 3pt の差は judge 自身のノイズに埋もれる。**

#### 検索と生成を分離する RAG 評価フレームワーク

| フレームワーク | 検索側指標 | 生成側指標 | URL |
|---|---|---|---|
| **RAGAS** | Context Precision / Recall / Entities Recall / **Noise Sensitivity** | **Faithfulness**, Response Relevancy, Factual Correctness | [docs.ragas.io](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/) |
| **TruLens RAG Triad** | Context Relevance | **Groundedness**, Answer Relevance | [trulens.org](https://www.trulens.org/getting_started/core_concepts/rag_triad/) |
| **ARES** | Context Relevance | **Answer Faithfulness**, Answer Relevance | [arXiv:2311.09476](https://arxiv.org/abs/2311.09476) |
| **DeepEval** | Contextual Precision / Recall / Relevancy | Faithfulness, Answer Relevancy | [confident-ai.com](https://www.confident-ai.com/blog/rag-evaluation-metrics-answer-relevancy-faithfulness-and-more) |

RAGAS Faithfulness の定義（[docs](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)）:
`回答を原子的主張に分解 → 各主張を文脈に対し NLI 判定 → 支持された割合`。
LLM を使わない `FaithfulnesswithHHEM` 変種（Vectara HHEM-2.1-Open、T5 分類器）もあり、
**judge の自己選好バイアスをループから完全に除去できる**点で検討価値がある。

**ARES** は4つの中で最も統計的に厳密で、
**prediction-powered inference（PPI）により「数百件の人手注釈」から指標の信頼区間を出す**。
点推定でなく区間を native に出す唯一のフレームワーク。

**★生成器だけを替えたときにどの指標が動くか**
⚠ **これを統制実験で分離した論文は見つからなかった。以下は指標の定義からの導出であり、実証ではない。**

| 指標 | 生成器交換で動くか | 理由 |
|---|---|---|
| Context Precision / Recall / Entities Recall / Context Relevance | **動かない（不変）** | クエリ + 検索チャンク + 正解のみから計算される。→ **ヌル対照・健全性チェックとして使う。動いたら検索が固定できておらず実験が壊れている** |
| **Faithfulness / Groundedness** | **動く（主信号）** | 固定文脈に対する含意の直接測定 |
| Answer Relevancy | 動く | 質問に答えたか |
| Factual Correctness | 動く | 正解との突き合わせ |
| **Noise Sensitivity** | **動く** | 無関係チャンクに引きずられるか。**生成器の性質を最も鋭く見る RAGAS 指標であり、弱い/小さいモデルを最も暴きやすい** |

> ★**本計画への反映**: この表は §2-4 の「`anchor_coverage@8` は動かないので測らないが、
> E2E で1回だけ**実験の破損検出**として確認する」という判断を、外部知見が独立に支持している。
> **Noise Sensitivity に相当するものを我々は持っていない**が、166問セットの
> C4 要約（クッションで押し出される）・C3 比較（検索 0.844 に対し生成 0.630）の
> カテゴリ別診断が近い役割を果たす。

⚠ 関連: [arXiv:2603.24580](https://arxiv.org/abs/2603.24580)「Retrieval Improvements Do Not
Guarantee Better Answers」（逆方向の分離結果。**未検証**）。

#### トークナイザ — コストではなく交絡である

⚠ この領域の証拠は他節より弱い（ブログ水準）。
CJK 向けに調整されていない BPE は日本語で 1文字 ≒ 1トークンに近づく（英語は Llama 3.2 で 4.9文字/トークン）。

🔴 **実務的な帰結はコストではなく交絡である**:
日本語の fertility（文字あたりトークン数）が2候補で違うと、
**「同じ検索チャンクを渡した」ことが「同じ量の証拠を渡した」ことにならない。**
どちらかが `num_ctx=8192` の上限に近ければ、**気づかないまま異なる量の証拠を比較していることになる。**

→ ★**本計画に追加する測定**: **両条件で「文脈のトークン数」を必ず記録し報告する。**
FCR は文字列としては同一の文脈を渡すが、**トークン数はモデルごとに違う。**
BASELINE §3 のクッション後文脈は平均約2,500字であり、
日本語 1文字 ≒ 1トークンの最悪ケースでも 2,500トークン程度で 8,192 には届かないと**推測**するが、
**実測して確認する**（`/api/chat` のレスポンスの `prompt_eval_count` で取れる）。

#### 小規模な西側モデルの日本語出力品質

⚠ **本節が最も証拠が弱い。**
- リーダーボード（Nejumi / Swallow）は順位を付けるが、**なぜ悪いかを診断しない**。
- 日本語の実務ブログは、小規模モデルが明示的な「日本語で回答してください」を無視して
  英語で答えると報告している（例: [classmethod](https://dev.classmethod.jp/articles/small-llm-japanese-feedback-failure/)、1.7B の事例）。**逸話的。**
- Gemma 2 2B に **JPN-IT という日本語適応版が存在すること自体**が、
  素の Gemma の日本語が不十分と見なされた証拠になっている。
- J-RAGBench の「小規模オープンウェイトは大きく劣る」が最も信頼できる単一データ点だが、
  査読論文ではなく発表資料である。

→ ★**本計画に追加する測定（安価かつ高価値）**:
**「言語遵守率」＝ 回答が完全に日本語である割合を、166問全件でスクリプト計算して一級の指標にする。**
judge も人手も要らない（ASCII 比率・かな漢字の有無で機械判定できる）。
**標準ベンチにこの指標は無く、逸話的報告を踏まえると支配的な失敗モードになりうるうえ、
忠実性・関連性の指標からは完全に不可視である。**
→ §2-4 と §2-6 に反映する。

#### RAGAS を日本語で使うときの罠（本計画では RAGAS を使わないが、記録として）

⚠ RAGAS の言語適応は **few-shot 例示だけを翻訳し、指示文自体は英語のまま**である
（[docs](https://docs.ragas.io/en/v0.2.4/howtos/customizations/metrics/_metrics_language_adaptation/)）。
公式ドキュメント自身が「適応後のプロンプトを人手で確認せよ」と警告している。
非英語ソースで生成された Q-A が**ソース言語と英語の混在になる** issue も報告されている
（[ragas#1732](https://github.com/explodinggradients/ragas/issues/1732)）。
→ **日本語での RAGAS スコアは、公表されている英語の RAGAS 数値と直接比較できない。**
