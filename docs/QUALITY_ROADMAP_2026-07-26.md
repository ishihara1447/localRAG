## 1. 目指すべき姿（To-Be）

### 1.1 対象文書の2系統

品質目標は文書系統ごとに違う。まずここを固定する。

| | **系統A: 行政資料** | **系統B: 製品ヘルプファイル** |
|---|---|---|
| 形式 | 段組みPDF（白書・通知・ガイドライン・報告書） | HTML / HTM / XHTML（将来 CHM 展開物） |
| 規模 | 1ファイル数百ページ（防衛白書=546p, 66MB） | 1トピック1ファイル × 数百〜数千ファイル |
| 構造の在り処 | **本文中に印刷された目次ページ**（PDFしおりは汚染されていて使えない） | **h1/h2/h3 タグ＝機械可読な階層が最初から存在する** |
| 構造抽出の確実性 | 中（ヒューリスティック依存、失敗しうる） | **高（タグを読むだけ）** |
| ノイズ源 | 柱（running header）、縦組み見出しの1文字改行、リーダー罫線、図表の崩壊 | ナビゲーションメニュー、パンくず、フッタ、`<script>`/`<style>` |
| 典型の質問 | 事実照会・数値比較・全体構成の把握 | **手順の照会（「〜するには」）**・設定項目の意味・エラーの対処 |
| 出典として示すべき単位 | 文書名 + **印刷ページ番号** | 文書名 + **トピック見出し（h1>h2>h3）** |

> **重要な帰結**: 調査レポート（`RESEARCH` §4）が上位に置く「**条文単位チャンキング**」は、主対象が規程・法令・通達である前提に立っている。F1により**この前提は成立しない**。したがって条文単位チャンキングの優先度を下げ、代わりに
> - 系統A → **印刷目次ページのパース＋章節見出し**
> - 系統B → **HTMLタグ由来の見出し階層**
>
> を構造の主データ源とする。§4のステップ順はこの判断を反映している。

### 1.2 質問の型ごとの「こう答えられる」（応答契約）

曖昧な形容詞（「精度が高い」「賢い」）で目標を書かない。**型ごとに、入力・出力・出典粒度・失敗時の振る舞いを契約として定義する**。この契約が §2 の現状評価軸であり、§4 の各ステップの検証条件でもある。

---

#### 型T1 単一事実の抽出

- **入力例（A）**: 「きらめき2号は何年度に運用を終了する予定ですか」
- **入力例（B）**: 「自動保存の間隔の既定値は何分ですか」
- **出力契約**: 該当する事実を1つ、原文の表記を保って提示する。**言い換え・単位換算で勝手に丸めない**。
- **出典契約**: 文書名 + ページ番号（A）／文書名 + 見出しパス（B）。**回答に使ったチャンクが出典として提示されていること**。
- **失敗時**: 記載がなければ「文書に記載がありません」。近傍に紛らわしい数値があっても代用しない。

#### 型T2 構成・目次の照会（集約クエリ）

- **入力例（A）**: 「この白書は全体でいくつの部に分かれていますか。各部のタイトルも」
- **入力例（B）**: 「このヘルプにはどんな章がありますか」「印刷関連のトピックを一覧で」
- **出力契約**: **階層を保った列挙**。`第Ⅰ部 > 第1章 > 第1節` のインデント構造で返す。**個数を問われたら正しく数え上げる**（「5部」）。検索で拾えた分だけの部分列挙は不合格。
- **出典契約**: 目次ページ（A）／見出しインデックス（B）を出典として示す。
- **失敗時**: 構造情報を持たない文書に対しては「この資料からは目次情報を抽出できませんでした」と正直に言う。**それらしい章立てを捏造しない**。
- **設計上の要点**: これは**検索問題ではなくメタデータ問題**として解く（`RESEARCH` §2）。top-kを大きくしても解決せず、ノイズ蓄積でむしろ悪化することが実証されている（arXiv:2602.01355）。

#### 型T3 位置指定の局所要約

- **入力例（A）**: 「第3章を要約して」「第Ⅱ部は何について書かれた部ですか」
- **入力例（B）**: 「『バックアップ』の節に書いてあることをまとめて」
- **出力契約**: **指定された範囲のチャンクを列挙的に集めて**（類似度上位k件ではなく）要約する。範囲外の内容を混ぜない。
- **出典契約**: 範囲の開始・終了ページ（または見出しパス）を明示。
- **失敗時**: 指定された章・節が存在しなければ「第Ⅵ部は存在しません（本書は第Ⅰ部〜第Ⅴ部の5部構成です）」と、**構造情報に基づいて否定する**。
- **設計上の要点**: `sectionPath LIKE '第3章%'` の**列挙的フィルタ検索**が必要。これはチャンク側に構造メタデータが載っていて初めて可能（＝Phase E依存）。

#### 型T4 マルチホップ（離れた複数箇所の合成）

- **入力例（A）**: 「自衛隊に統合作戦司令部が新設されたのと同じ時期に、在日米軍側ではどのような組織変更が始まりましたか」（印字2ページ目と印字54ページ目の合成）
- **入力例（B）**: 「A機能を使うために事前に設定しておく必要がある項目は何ですか」（機能説明トピックと設定トピックの合成）
- **出力契約**: 必要な箇所すべてに到達し、**主張ごとに出典を分けて**提示する。片側だけで断定しない。
- **出典契約**: gold pageが2つ以上ある設問では、**Coverage@8 = 1.0**（全gold到達）を目標に置く。
- **失敗時**: 片側しか取れなかったときは「〜については記載を確認できましたが、〜については本文書内で確認できませんでした」と**到達できた範囲を明示**する。

#### 型T5 比較（表・2項目以上の対比）

- **入力例（A）**: 「予備自衛官と即応予備自衛官では手当がどう違いますか」
- **入力例（B）**: 「Standard版とPro版で使える機能の違いは」
- **出力契約**: **どの数値がどちらの区分か**を取り違えない。可能なら表形式で返す。
- **出典契約**: 表の所在（ページ／見出し）。
- **失敗時**: 抽出テキスト上で行列対応が壊れている場合は、**推測で対応付けず**「表の対応関係が判別できませんでした。原典のp.436の図表をご確認ください」と誘導する。
- **設計上の要点**: HTMLの `<table>` は構造が機械可読。**系統Bでは正しく答えられるのが当然のライン**。系統A（PDF）は難易度が桁違いに高いので、目標水準を分けて設定する。

#### 型T6 手順の照会（系統B固有・実運用で最頻）

- **入力例**: 「ライセンスを別のPCに移すにはどうすればよいですか」
- **出力契約**: **番号付き手順を原文の順序どおりに**提示する。途中の注意書き（Note / 警告 / 前提条件）を落とさない。手順が複数トピックにまたがるなら、トピック単位で区切って示す。
- **出典契約**: トピック名（h1）＋見出しパス。「ヘルプのどのページを開けばよいか」が利用者に伝わること。
- **失敗時**: 手順の一部しか見つからないときは、途中で切れていることを明示する。**もっともらしい手順を補完しない**。
- **設計上の要点**: 手順は**順序と完全性が本質**。フラットな500字チャンクで途中分断されると致命的。ここは Parent-Document / Auto-Merge（子で検索し親トピックに展開）が最も効く型。

#### 型T7 回答不能の識別

- **入力例（易）**: 「国民年金の保険料は月額いくらですか」（文書と完全に無縁）
- **入力例（難）**: 「次期防衛通信衛星はいつ打ち上げられる予定ですか」（**同じチャンク内に別衛星の「2026年度打ち上げ予定」と「2030年度に運用終了」があり、誘導される**）
- **出力契約**: 「文書に記載がありません」と言い切る。そのうえで**近いことが書いてある箇所を代替提示する**（「2025年度から整備に着手、という記述はあります」）。
- **失敗時の定義**: 記載のない数値・年度・条番号を1つでも断定したら**不合格**（ハルシネーション扱いで別集計）。
- **設計上の要点**: 士業・実務利用では**正答率の向上より、誤答を「不明」に変える価値のほうが高い**場合がある（`RESEARCH` #6）。

#### 型T8 文書横断（複数文書ワークスペース）

- **入力例**: 「この件はどの資料に書いてありますか」「バックアップについて、行政資料側とヘルプ側で言っていることは違いますか」
- **出力契約**: **どの文書のどこか**を先に確定してから内容を答える。複数文書にまたがるなら文書ごとに分けて提示する。
- **失敗時**: 文書を特定できないときは、候補の文書名一覧を出して**問い返す**。
- **設計上の要点**: 実運用は「行政資料 + ヘルプファイル多数」の**混在ワークスペース**であり、単一文書での評価（現行の白書30問）は実態を代表していない。

### 1.3 製品として言えるようになりたいこと（言語化）

上の契約を満たしたとき、製品としてこう言える:

> 「手元の行政資料と製品ヘルプを取り込むと、**中身の事実**だけでなく**どこに何が書いてあるか（構成）**、**手順の全体**、**複数箇所にまたがる話**にも答えます。答えには必ずページ番号または見出しが付き、**書いていないことは書いていないと言います**。すべてローカルで動き、文書は外に出ません。」

現時点で正直に言えるのは前半の「中身の事実」と末尾の「ローカル」だけである。§2でその差を確認する。

### 2.2 横断する構造的欠陥（4つ）

型ごとの症状の裏にある原因は4つに集約される。**§3の順序はこの4つをどの順で潰すかの議論である。**

#### 欠陥1: 測定が検索を測っていない ― (iv)

- `scripts/hakusho-eval.py:94` が `sources` を捨てている（F6）。**retrieval指標（Hit Rate / Coverage / MRR / nDCG）が1つも存在しない**。
- したがって「検索が悪いのか、生成が悪いのか」を**構造的に切り分けられない**。2026-07-18の失敗分析はこれを手作業で行ったが、恒常的な仕組みになっていない。
- 現行30問はすべて単一チャンク完結のfactoidで、**T2/T3/T4/T5/T6/T8をひとつも測っていない**。28〜29/30という天井の数字は「測っている範囲では良い」以上のことを意味しない。
- n=30 では Wilson 95%CI が ±17ポイント。**17ポイントの改善ですら有意と言えない**（`RESEARCH` §5）。
- 統計処理（複数run・CI・McNemar）が無く、過去に「同一設定の再実行で19/20/21/24」という実測ブレが記録されている。

> **この状態で §4 の他のどのステップに着手しても、効果があったかどうかを判定できない。** これが順序決定の最大の制約である。

#### 欠陥2: 入力が壊れている系統がある ― (ii)

- **系統B（ヘルプ）は取り込みそのものが壊れている**（F2/F3/F4）。`<div class="nav">` や `<script>` の中身がベクトル化され、本文の意味ベクトルを汚染している。しかも `.htm` は登録すらされていない。
- **これは検索アルゴリズムの問題ではない。** ハイブリッド検索もrerankerもcushionも、壊れた入力の上では効果が出ない。
- 同時に、HTMLは **h1/h2/h3 という機械可読な階層**を持っている。今はそれをノイズとして混入させている（F4）。**修復と構造獲得が同じ作業で同時に達成できる、極めて費用対効果の高い箇所**である。
- 系統Aの表崩壊も同種の入力破損だが、こちらはPDF抽出の本質的難しさに由来し、修復コストが桁違いに高い。

#### 欠陥3: 構造メタデータが存在しない ― (i)

- チャンクはフラットな Recursive 分割で、**親子関係も見出しも持たない**。持っているのは `pageNumber` のみ（2026-07-22実装）。
- 実効チャンクサイズは1000字ではなく **500字**（`EMBEDDING_MODEL_MAX_CHUNK_LENGTH=500` と `determineMaxChunkSize` の min により）。**500字は国内外の推奨域（400〜512トークン ≒ 520〜670字）の下限を割っている**。分断事故（「海上・航空自｜衛隊」でチャンク境界の語中分断）が既に観測されている。
- 構造メタデータが無いことは、**T2・T3・T6・T8のすべてを同時にブロックしている**。個別の型に個別の対策を打つより、共通の土台を1つ作るほうが全体最適である。

#### 欠陥4: 検索経路が7つに分散している ― 事故構造

- `performSimilaritySearch` の呼び出しは **7箇所**（F7）。過去に `stream.js` にだけ実装して評価経路（`apiChatHandler.js`）に反映されず、効果が出ないという事故が実際に起きている（P1実装時）。
- **検索経路に触る改修を「まず1箇所に入れてみる」形で始めてはいけない。** 共有モジュール化を先に済ませることが、後続すべてのステップの前提になる。既に `queryReformulation.js` という良い先例がある。

### 2.5.4 §2 の前提を訂正する2つの発見

**発見1: 文抽出クッションは topN と無関係に「文の総数」で上限を持つ（重要）**

### 2.5.13 【2026-07-27】文字化け（U+FFFD）の実態 — **先行研究の前提が実測で覆った**

### 3.2 順序を決める4つの根拠

**根拠1: 測定できない状態で改良しても効果が判定できない（G1〜G3 が最優先）**

現行ベースラインは hakusho 28〜29/30 で天井に張り付いており、**どんな改修を入れても数字が動かないか、動いてもノイズと区別できない**。しかも retrieval 指標がゼロなので、効果が出なかったときに「検索が悪い」のか「生成が悪い」のかを切り分けられない。この状態で Phase C〜E の大型改修に入るのは博打であり、**手戻りのリスクが最も高い**。
加えて、Phase A の中でも **retrieval 計測（S03/S05）を generation 評価より先に置く**。retrieval は LLM を呼ばないため決定的・高速で run 間のブレが無く、**ノイズに強い判定軸を先に手に入れられる**（`COMPLEX_QA_EVAL_SET_DESIGN` §7-3）。

**根拠2: 壊れた入力の上に検索改良を積んではいけない（G4/G5 が構造化より先）**

系統BはHTMLタグが混入した状態でベクトル化されている。この上で「チャンキングを改善した」「rerankerを強くした」と測っても、**測っているのは壊れた入力に対する性能**であり、入力を直した瞬間にすべての測定値が無効になる＝**手戻りが確定している**。したがってG4/G5はPhase Cより前に置く。
さらに重要な点として、**HTML修復とHTML構造抽出は同じパース処理の中で同時にできる**（F4/F5）。タグを解析する以上、h1/h2/h3を取り出すのは追加コストがほぼゼロである。分けて2回パーサを書くほうが無駄。

**根拠3: 構造メタデータは複数手法の共通土台であり、単独手法より先に置く（G6/G7 → G8）**

`docStructure`（文書レベル）と `sectionPath`（チャンクレベル）は、T2（構成照会）・T3（範囲要約）・T6（手順の親展開）・T8（文書特定）の**4つの型が同時に乗る土台**である。型ごとに個別対策を打つと、後から土台を入れた時点で全部作り直しになる。**土台を先に置き、その上に型ごとの利用を薄く載せる**のが全体最適。
そのうえで **Phase C（HTML起点）→ Phase D（PDF起点）の順にする**。理由は次項。

**根拠4: 不確実な生産者より、確実な生産者で先に縦切りを通す（Phase C が Phase D より先）**

`docStructure` を作る側（生産者）は2つある。

| 生産者 | 確実性 | 根拠 |
|---|---|---|
| **HTMLのh1/h2/h3** | **高**。タグを読むだけ | F4。構造が機械可読 |
| PDFの印刷目次ページ | **中**。ヒューリスティック依存 | `TIER0` §3.1。防衛白書1本でしか検証しておらず、行政文書一般への一般化は未検証（リスクR2） |

一方、消費者側（保存・予算内整形・注入・7経路配線・誤爆対策）は**両者で完全に共通**である。
したがって **確実に成功する生産者（HTML）で消費者側まで一気に縦切りを通し、end-to-endで動くことを確認してから、不確実な生産者（PDF目次パーサ）を同じ受け口に差し込む**。
逆順（PDFを先）にすると、目次パーサが失敗した場合に**下流の消費者側が一度も動かないまま終わる**リスクがある。これは典型的な局所最適の罠であり、原則2に反する。

> **なお、この順序変更は調査レポート（`RESEARCH` §6 の着手順序）と意図的に異なる。**
> レポートは「#2 目次インデックス（PDF前提）」を第1波に置いているが、これは主対象を士業の規程集・条文と想定していたためである。F1により前提が変わったため、**条文単位チャンキング（元A判定）を後方に下げ、HTML起点の構造抽出を前方に上げる**。

### 本ロードマップ自体の限界（正直に）

- **ヘルプファイルの実物を確認していない。** F2〜F5はコードから確定した事実だが、「実際のヘルプがどんなHTMLか」（フレーム構造か、単一ファイルか、生成ツールは何か）は未確認。S09の設計はS11で実物に当てて初めて検証される。
- **Phase B以降の人日は、Phase Aの測定結果を見ないまま見積もっている。** S05で「kを増やしても取れない」設問が想定より多ければ、Phase Eの重要度が上がり Phase F が下がる。**Phase A完了時点で §3.3 の順序を見直すこと**を明記しておく。
- **構造考慮RAGの日本語での統制実験は存在しない。** 効果量の根拠はすべて英語または自社ブログ由来である。だからこそ Phase A を最優先に置いている。
