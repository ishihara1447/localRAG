## 1. なぜ測るのか

顧客ゴールは **Windows / VRAM 8GB で動く製品とそのオフラインインストーラー**。
現行 LLM `gemma4:12b` は 16GB 機の実測で **8.4GB** を占め、埋め込み `bge-m3`（0.58GB）と
合わせて約 9GB になる。**8GB には載らない**（実測値と容量の引き算であり、推測ではない）。

そこで LLM を小型モデルへ差し替える。**差し替えで精度がどれだけ落ちるかを測るのが本測定。**

## 2. 測る対象

| 条件 | LLM | 出自 / ライセンス | 重み |
|---|---|---|---|
| **現行（対照）** | `gemma4:12b` | Google / Apache-2.0 | 7.38GB |
| **候補A** | `granite4.1:8b` | IBM / Apache-2.0 | 5.35GB |

**候補B `nemotron-3-nano:4b`（NVIDIA Open Model License）は本測定では測らない。**
ライセンスが Apache-2.0 でなく、配布物同梱には法務判断が要るため。候補Aが不合格だった
場合にのみ、法務確認とセットで着手する。

`gemma4` の小型版（4b 等）は Ollama ライブラリに**存在しない**ことを確認済み
（`registry.ollama.ai` の manifest 取得が 404）。同系統で揃える選択肢は無い。

### 変えないもの

- 埋め込み `bge-m3`、リランカー `hotchpotch/japanese-reranker-xsmall-v2`
- `topN=8` / `LANCE_SENTENCE_CUSHION=true` / `LANCE_HYBRID_SEARCH=true` / ハイブリッド設定一式
- システムプロンプト（**gemma4 向けに調整したものをそのまま使う**。候補Aに合わせて
  プロンプトを調整すると「モデルの差」と「プロンプトの差」が混ざるため。
  候補Aが不利になりうるが、それは結果の解釈で述べる）
- 評価セット・採点器（`scripts/hakusho-eval.py`）

## 3. 測り方

- 評価セット: 防衛白書30問（`fixtures/` の既存セット。文書は `R07zenpen.pdf` 544ページ）
- **各条件3run**。設問ごとに一意な `sessionId` を振る（省略すると履歴が交絡する既知事故）
- **交互実行**（現行→候補A→現行→候補A→…）。時間帯による揺れを両条件に等しく載せるため
- 各 run の前にコンテナを作り直す（両条件ともコールドで対称）
- `openAiTemp=0` / `chatMode=query`

### 対照を測り直す理由

`out/reranker-ab-2026-08-04/` に現行 27/30 の記録があるが、**それを対照に流用しない。**
イメージ 1.0.7 での測定であり、今回は配布構成に近い環境で測るため条件が違う。
**条件の違う数値を比較して誤報告する事故を4回起こしている。**

## 4. 判定基準（★測定前に確定）

### 採用条件（すべて満たすこと）

| # | 条件 | 根拠 |
|---|---|---|
| **P1** | 30問の合計が **対照 −3 問以内** | 27/30 なら 24/30 以上。3問＝10ポイントを実用上の許容幅とする |
| **P2** | **白書外（不明と答えるべき）設問 5/5 を維持** | 文書に無いことを答えてしまうのは、精度低下より重い。**1問でも落ちたら不採用** |
| **P3** | 架空の出典・条文番号の**捏造がゼロ** | Phi-4 を不採用にした基準と同じ（`docs/PHI4_AB_TEST_RESULT_2026-07-15.md`） |
| **P4** | 空回答がゼロ | llm-jp GGUF のテンプレート破損事故と同じ検査 |
| **P5** | **VRAM 実測が 6.5GB 以下** | 8GB − デスクトップ描画1GB − 埋め込み0.58GB ≒ 6.4GB。実機情報が無いので保守的に置く |

### 中止条件（1つでも該当したら候補Aを捨てる）

- **C1**: P2 または P3 に違反（安全性の問題は精度で埋め合わせできない）
- **C2**: 3run の合計が 5問以上ばらつく（測定が安定せず判断材料にならない）
- **C3**: 1問あたりの応答が中央値 60秒を超える

### 判定に使わないもの

- **統計的有意性は採否に使わない。** n=30 では検出力がほとんど無く、
  p 値を持ち出すと「有意差なし＝同等」という誤読を生む（前回 95%CI を撤回した理由と同じ）
- JQaRA 等の公開ベンチ。**両候補とも日本語スコアが存在しない**

## 5. 事前に表明しておく予想（外れたら正直に書く）

- 候補Aは合計で **2〜4問落ちる**と予想する（12B → 8B、かつプロンプトが gemma4 向け）
- P2（白書外 5/5）は**維持できると予想する**。これは能力よりプロンプト遵守の問題のため
- VRAM は 5.9〜6.1GB と予想（重み5.35GB + オーバーヘッド）

## 6. 記録するもの

- run ごとの生スコアとカテゴリ別内訳（a〜e の5カテゴリすべて。**抜粋しない**）
- `ollama ps` の VRAM 実測（両条件）
- 1問あたり所要（run 別の生値を必ず併記。プール中央値だけを書かない）
- 逸脱があれば全件記録する

## 8. 逸脱の記録（測定開始前・2026-08-04）

**P5（VRAM 6.5GB 以下）を満たさないことが、精度測定の前に判明した。**

同一条件（ctx 8192）での実測:

| モデル | VRAM | + bge-m3(0.6GB) |
|---|---|---|
| `gemma4:12b`（対照） | 8.4 GB | 9.0 GB |
| `granite4.1:8b`（候補A） | **6.7 GB** | **7.3 GB** |

P5 の 6.5GB に対し **0.2GB 超過**。ctx 4096 なら 5.9GB（合計 6.5GB）で収まる。

**判断: P5 を満たさないまま精度測定へ進む（ユーザー選択、2026-08-04）。**

- P5 は実機情報が無いために置いた保守的な仮値であり、**実機の実効 VRAM が判明した
  時点で最終判断する**。基準を緩めたのではなく、判定を保留する。
- したがって **本測定だけでは採用を決定できない。** 精度が合格でも、
  実機で 7.3GB が載らなければ不採用になりうる。
- ctx 4096 への引き下げ（5.9GB）は代替案として残す。ただし文脈が切れて精度が
  落ちる可能性があり、その代償は本測定では測らない（測るなら別条件が要る）。

**P1〜P4 の判定基準は変更しない。**
