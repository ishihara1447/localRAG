### 3-2. 1run の手順（`out/reranker-ab-2026-08-04/` に全ログ）

1. オーバーレイを指定して `up -d anythingllm`。**コンテナIDが変わったことを確認**（リランカーは静的シングルトンで起動時に1度だけロードされるため、切替には再作成が必須）。6run すべてで `recreated=yes`
2. healthcheck が `healthy` になるまで待機
3. `docker exec anythingllm env` で環境変数を採取・保存
4. **ウォームアップ1問**（専用 `sessionId=warmup-<run>`、採点対象外）。リランカーを実ロードさせ、§5 の確認を可能にするため。両条件に同一適用

7. 本番30問を実行。`HAKUSHO_SLUG=ttft-hakusho HAKUSHO_RUN=<run> HAKUSHO_OUT=<JSON>`
8. `ollama ps` を採取（測定後）
9. コンテナログ全体を保存（run ごとに再作成しているのでログが run 単位で切れている）

### 3-3. `sessionId`

`scripts/hakusho-eval.py` は設問ごとに一意な `sessionId`（`hakusho-<run>-<番号>`）を振る。
`HAKUSHO_RUN` に `A1`〜`B3` を与えたので、**6run×30問の180セッションがすべて独立**している。
振らないとチャット履歴が交絡する（`docs/EVAL_HARNESS_FIXES_2026-07-26.md` の実証済み事故）。

**ワークスペースを書き換える環境変数（`TOPN` / `CHAT_MODEL` / `PROMPT_FILE`）は意図的に指定しなかった。**
`hakusho-eval.py` はこれらを設定すると workspace を更新するが復元しない既知の問題があるため。
結果、測定前後のワークスペース設定スナップショットの**差分はゼロ**だった（§9）。

## 7. 採否の判定と根拠

### ゲート判定（事前登録どおりの順序）

| # | ゲート | 基準 | 実測 | 判定 |
|---|---|---|---|---|
| **G1** | ハルシネーション | B の d) が3run すべて 5/5 | 5/5, 5/5, 5/5 | **PASS** |
| **G2** | 定義説明 | mean(B の c) ≥ mean(A の c) − 0.67 = **4.33** | **6.00** | **PASS**（下回るどころか +1.00 上回る） |
| **G3** | 総合 | Δ ≥ −1.0 → 採用可 | **Δ = +0.00** | **採用可** |

### 判定: **採用（新リランカー `hotchpotch/japanese-reranker-xsmall-v2` を採用してよい）**

根拠:

1. **同一条件の A/B で合計スコアが完全に同点**（27/30 対 27/30、各3run 完全一致）。「精度が落ちる」という懸念は、少なくとも本評価セット・本構成では確認されなかった
2. **リランカーの効きが最も出る c) 定義説明で新が上回った**（5/6 → 6/6）。しかもそれは
   チャンク境界をまたぐ定義の後半を新モデルだけが拾えたという、**検索側の実質的な差**である（§4-3）
3. **d) 白書外が両条件 5/5 でハルシネーションゼロ。** 採用不可の条件に触れていない
4. **新モデルで落ちた唯一の設問 Q04 は、証拠が文脈1位にあるのに LLM が拒否した生成側の失敗**であり、リランカーの検索性能の劣位を示すものではない
5. 副次的に、リランクが約8.8倍速く、1問あたりの応答が約2.5倍速い

### 🔴 ただし「差が無い」とは言えない

- 30問中**一致28問・不一致2問**（A正B誤1、A誤B正1）。この不一致数から求めた
  **真の差の95%信頼区間は およそ −2.8 〜 +2.8 点/30**（SE=1.41点）。
  **つまり新が3点近く劣っている可能性も、3点近く優れている可能性も、本測定では否定できない。**
- 参考の McNemar 正確検定（両側）は **p = 1.0000** だが、これは事前登録どおり**判定には使っていない**。
  **p が有意でないことは「差が無いこと」の証明ではない。** n=30・不一致2問では検出力が著しく低い
- 各条件内の3run が完全一致したことは「**この構成での測定が決定的である**」ことを示すに過ぎず、
  「**評価セットを替えても同じ結論になる**」ことは意味しない。ばらつきの主因は run ではなく**設問の選び方**である
- カテゴリ別の差（a −1 / c +1）は 8問・6問という規模で、1問が 12〜17pt に相当する。**方向性の観察にとどめ、断定しない**

## 8. 実測したこと / 推定にとどまること

### 実測したこと

- 同一コンテナ・同一ワークスペース・同一コーパス・同一プロンプトでの新旧交互 A/B（各3run、計6run、180設問）
- 6run すべてで、期待どおりのモデルが読まれたことのログ確認とレイテンシ指紋による裏づけ
- 6run すべての測定前後で `ollama ps` が `100% GPU`
- 解決後の compose 設定の全文 diff が1行だけであること
- 差が出た2設問について、`sources`（検索結果の生データ）まで遡った原因の切り分け
- 現行ベースライン 28/30 が本環境では旧モデルでも再現せず、差分が Q09 の1問であること

### 推定にとどまること / 未検証

- 🔴 **配布物（image 1.1.0）での挙動は未検証。** 測定に使った `localrag-anythingllm:1.0.7` には
  **`LANCE_HYBRID_RERANK`（チャンク単位リランク）の実装が入っていない**ことを実測で確認した
  （`/app/server/utils/vectorDbProviders/lance/index.js` に該当コード0件。env には `LANCE_HYBRID_RERANK=true` が
  入っているが**読まれない**）。また `rerankedSimilarityResponse` は `vectorSearchMode === "rerank"` のときだけ呼ばれ、
  本ワークスペースは `"default"` である。
  **したがって本 A/B が測ったのは「文抽出クッション経路のみを通したリランカーの差」である。**
  チャンク単位リランクが有効な 1.1.0 ではリランカーの寄与が大きくなるため、**差の大きさは変わりうる**
- **n=30 の評価セット1本のみ。** 166問セットや複雑20問セットでは確認していない。
  §7 のとおり真の差は ±2.8点の幅で不定
- **導入先 CPU での挙動は未検証。** 新モデルの同梱 ONNX は `model_qint8_avx2.onnx` をリネームしたもので、
  **AVX2 前提の量子化**である（旧 bge は命令セット非依存の dynamic int8）。本測定機は AVX2 を持つ。
  非対応 CPU で静かに遅くなる／精度が落ちる可能性は**未検証のまま残る**
- **Windows 版での動作は未検証。** 本測定は Linux/Docker 構成での結果であり、**Windows 配布物にそのまま転用できない**。
  なお `windows-native/export-windows.ps1` は本測定の時点で**すでに新モデルへ更新されていた**
  （作業ツリー上の未コミット変更。`$RerankerModelName = "hotchpotch/japanese-reranker-xsmall-v2"`）。
  **`docs/RERANKER_SWAP_2026-08-04.md` §6-2 の「Windows 版は旧リランカーのまま」という記述は古い。**
  ただし更新されたのはビルドスクリプトであって、**Windows でビルドした配布物での精度・速度は測っていない**
- Q04 を「生成側の過剰拒否」と切り分けたのは、正解チャンクが文脈1位に存在するという**実測**に基づく。
  ただし「文脈の構成（A は6チャンク、B は8チャンク）のどの違いが拒否を招いたか」までは**特定していない**
- 埋め込み `bge-m3`（BAAI・中国系）は今回の対象外で、**非中国系化は部分達成**のまま

### 本測定で判明した副次的な事実（リランカーとは無関係）

- **Q09（防衛関係費の歳出額）は現在、両モデルとも誤答する。** 正解の数字は検索結果に含まれており、
  同じ節の「契約ベース」の額と取り違えている。**生成側の課題**であり、現行ベースライン 28/30 と本環境 27/30 の差の正体である

## 9. 逸脱の記録

**測定プロトコルからの逸脱により無効化・再実行した run は1件もない（6run すべて有効・すべて報告）。**
以下は事前登録票に書いていなかった事項、および測定中に起きた外部事象である。

### (D1) 測定中に `runtime/docker-compose.yml` が外部から編集された 🔴

測定の実行中（A1 開始後）、**私以外の主体により** `runtime/docker-compose.yml` 本体に
`RERANKER_MODEL_PREF=hotchpotch/japanese-reranker-xsmall-v2` が追記された（コメント7行＋env 1行）。
**私はこのファイルを編集していない**（制約どおり）。

**測定への影響: なし。検証済み。**

- 両条件のオーバーレイが `RERANKER_MODEL_PREF` を**明示的に上書き**しており、compose のマージで後段のオーバーレイが勝つ
- 編集後に取得した**解決後 compose 設定の全文 diff が1行だけ**であることを確認済み（§3-1）
- A1 を含む全6run の**コンテナ内 env とログの読込モデルが期待どおり**（§5）
- 追加された行以外の差分は**コメントのみ**で、挙動に影響しない

**ただし、測定中に測定対象の設定ファイルが変わったこと自体は記録に残す価値がある。**
今回はオーバーレイが明示指定していたため無害だったが、オーバーレイが暗黙の既定に依存していたら**気付かず条件が壊れていた**。

### (D2) ウォームアップ1問を追加した（事前登録票に未記載）

各 run で本番30問の前に、専用 `sessionId=warmup-<run>` で1問を投げた。**採点対象外**。

- **理由**: リランカーは遅延ロードのため、実際に1回動かさないと「どのモデルが読まれたか」をログで確認できない。
  §5 の V2/V3 検証を成立させるために必要だった
- **両条件に完全に同一適用**しており、A/B の比較を歪めない
- 専用 `sessionId` なので30問のセッションとは独立で、履歴の交絡も生じない

### (D3) 測定の対象範囲が想定より狭かった（事前登録後に判明）

`LANCE_HYBRID_RERANK=true` を「共通条件」として票に書いたが、**image 1.0.7 にはその実装が無い**ことを測定中に実測で確認した。
リランカーが効く経路は**文抽出クッションのみ**だった。**票の記述は変更していない**（結果を見てからの変更はしない方針のため）。
影響は §8 に記載した。**A/B の対称性は保たれている**（両条件とも同じ経路を通る）ため、比較の妥当性そのものは損なわれない。

### (D4) 生データから API キーを削除した

ドライバが run ごとに生成した API キーを `out/.../raw/<run>.key.txt` に保存していたが、
**`out/` は `.gitignore` されていない**ためコミットされうる。測定完了後に全削除した。
測定結果には影響しない。

### (D5) 事後の状態確認（後始末）

- **ワークスペース設定は測定前後で差分ゼロ**（`workspace-snapshot-before.json` / `-after.json` を全キー比較）。

  `docker exec` と読込ログの両方で確認済み
- **他プロジェクトのコンテナ（`oracle-*`, `newscellar-*`, `data-generator`, `flow-pilot-*`）には一切触れていない。**
  測定後も稼働時間が連続していること（8〜12日）を確認済み。`rag-ollama` も再作成していない（`--force-recreate` を使わず、
  env 変更による差分再作成に任せた）
