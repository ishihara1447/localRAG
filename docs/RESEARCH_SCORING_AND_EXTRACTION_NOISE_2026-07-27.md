# 調査: 採点設計（キーワード/正規表現 vs 含意判定）と PDF抽出ノイズ

調査日: 2026-07-27 / 担当: Claude Code（調査担当）
位置づけ: 採点欠陥が**5例連続で同一原因（境界を見ない部分一致）**となったため、「6例目の正規表現を直す（局所最適）」か「採点設計を変える（全体最適）」かを、**実装前に**先行事例で判断する。ユーザー指示「国内以外のテック記事・ブログ・論文等のノウハウを必ず確認しながら進める」の適用。

## サマリー

1. **テーマ1は「設計を変える（全体最適）」を強く支持。** 英語圏の主要フレームワークは表層一致採点を捨て、**claim単位の含意判定**に移行済み（EM 12.6% vs 人手 71.4%、Kamalloo+ ACL2023）。ただし正規表現の全廃ではなく、**決定的マッチを候補抽出に降格し、最終判定を含意判定に委ねる**のが定石。
2. **NLI専用小型モデル路線は日本語では選択肢がない**（HHEM英語のみ／LettuceDetect多言語版に日本語なし／MiniCheck英語）。**既存 judge（qwen3.5:4b, κ=0.878）を使う方が合理的。**
3. **テーマ2は明確にアウト。** OCR/抽出誤りは**語誤り率5%で検索性能に有意な劣化**（Bazzo+ ECIR2020）。我々の20.8%はその4倍。原因（ToUnicode CMap欠落）は**再抽出しない限り回復不能**。

## テーマ1: `[X]`（禁止された主張）の判定手法

### 主要フレームワークの実装

| フレームワーク | `[X]` 相当の判定手法 |
|---|---|
| **RAGAS** faithfulness | 回答をatomic statementに分解 → 各statementが文脈から推論可能かを**LLMが二値判定** |
| **RAGAS** answer_correctness | statementを**TP/FP/FNに分類**しF1。FP＝ground truthが支持しない主張＝我々の`[X]`に最も近い |
| **DeepEval** HallucinationMetric | **LLM-as-judge**。矛盾コンテキスト数/総数 |
| **DeepEval** DAG metric | **決定的な決定木＋LLM判断ノードの合成**。**我々のLayer0-3と同型＝外部の設計裏付け** |
| **promptfoo** | 決定的（`contains`/`regex`/`levenshtein`）とmodel-graded（`llm-rubric`/`g-eval`/`context-faithfulness`）を**明確に層分け**。「ニュアンス・意味的整合は決定的検査では捕まえられない」と明記 |
| **RAGChecker**（Amazon, NeurIPS2024, arXiv:2408.08067） | text-to-claim extractor＋**claim-entailment checker** |

> **調査範囲内に、`[X]` を正規表現で判定しているフレームワークは一つも存在しなかった。** 全てが claim分解＋含意判定。正規表現は promptfoo でも「決定的な前段チェック」に位置づけられ、faithfulness 判定には使われていない。

### 表層一致採点の限界（実測値）

**Kamalloo et al., ACL 2023（arXiv:2305.06984）** — 最重要。
- NQ で InstructGPT(zero-shot) の **EM 12.6% に対し人手評価 71.4%（+58.8pt）**
- EM が誤って落とした493件の内訳: **意味的等価 50.3% / リスト型 20.6% / 粒度差 15.0% / データ品質 14%**
- → **我々の5例中4例は「粒度差」「意味的等価」に該当。既知の失敗クラスをなぞっている**
- 自動代替の性能: BEM τ=0.70（EM失敗を56%削減）、**LLM-judge τ=0.75（70%削減）**、GPT-4 eval τ=0.79

**Bulian et al., EMNLP 2022（arXiv:2202.07654）**: 23k件の人手answer-equivalence判断。BEMがF1より有意に良い近似。トークン一致は原理的に不十分。

**国内**: `llm-jp-eval` の `char_f1` は**文字順を考慮せず誤答でも部分一致で高得点になりうる**と公開資料が指摘。**我々の症状と同型の問題が日本語評価基盤にも存在する。**

### 🔴 反証（必ず併記）

- **Kamalloo+ の同じ論文**が、**LLM-judge はハルシネーション回答 約47件を「正解」と誤認**したと報告。**judge は偽陰性を減らす一方、偽陽性（見逃し）を増やす。** `[X]` は「見逃したら安全性主張が崩れる」項目なので、**judge単独運用は危険**
- **arXiv:2501.14883「Verify with Caution」**: 最先端 factuality metric 5種を11データセットで再評価し、**指標同士が互いに一致せず、システムレベル性能を頻繁に誤推定**。特に **(a) 言い換えが多い出力、(b) ソースの離れた箇所を参照する出力**に系統的バイアス。→ **我々の C2/C3/C5 が直撃する。judgeに移せば全て解決、ではない**
- RAGTruth系では、フロンティアモデルでも 5〜8% の groundedness 見逃しが残る

### 日本語（語境界なし）特有の落とし穴

**正面から扱った学術的一次情報は、英語圏・国内とも発見できなかった。** 実務知としての「部分一致」議論（`東京都` に `京都` が一致する型）のみで、体系的な誤判定率の実測は無い。
→ **我々の5例はこの型の実データであり、社内資産としての価値がある**（`即応予備自衛官手当` ⊃ `予備自衛官手当` は教科書的な最悪ケース）。

技術的定石は (a) 最長一致優先、(b) **競合語彙の負の後読み**（`(?<!即応)予備自衛官手当`）、(c) 形態素解析による境界付与。**ただし (a)(b) は競合語を事前に列挙できる場合のみ有効で一般化しない。**

## テーマ2: PDF抽出ノイズ

### 定量関係

- **Bazzo+ ECIR2020**: OCR誤りを人工注入。**語誤り率5%から有意な劣化**が始まる。→ **我々の20.8%は「有意に劣化する」域を大きく超える**
- **OHR-Bench（ICCV2025, arXiv:2412.02592）**: retrieval で GT 70.0% に対し最良OCR 59.2%、MinerU 50.1%。証拠種別では**表 GT 69.6%→48.5%、チャート 70.3%→16.5%**。**semantic noise（文字レベル誤り）は formatting noise より一貫して有害**
- **InduOCRBench（arXiv:2605.00911）**: **「高いOCR精度が高いRAG性能を保証しない」**。OCR 82.9% に対し RAG accuracy 52.8%
- **JCDL2025**: CER/WER は全誤りを等価に扱うため固有表現の誤りを過小評価。→ **「�の割合」だけでなく「gold回答語が壊れているか」で見るべき**

### U+FFFD の原因と回復可能性（PyMuPDF公式が一次情報）

- **原因**: フォントの **`/ToUnicode` CMap 欠落または不完全**。PyMuPDFは「有効なUnicodeを持たないグリフごとに `chr(0xFFFD)` を返す」と明記。**フォントのサブセット化の過程でCMapも改変され欠落する**
- **🔴 回復可能性**: PyMuPDF公式FAQは「**内部の /ToUnicode マップが欠けている場合、情報は原理的に復元できない**」「**唯一の突破口はOCR**」と述べている。→ **後段の正規化・クリーニングでは直らない**
- **既実装との関係**: `JP_PDF_SPACING_FIX_2026-07-14.md`（字間空白正規化・CIDフォント対応）は**別問題**。空白はグリフ配置由来で正規化可能だが、**U+FFFDは情報が存在しない**

### 品質ゲートは一般的か

**LLM事前学習データ整備では標準実務。**
- **Dolma**（AI2, ACL2024）は **U+FFFD を除去するルールを明示的に持つ**
- **FineWeb**（NeurIPS2024）は Gopher/C4 フィルタ＋独自3種。**閾値はWikipedia上の分位点で決める**
- **ただしRAG運用での明示的な品質ゲート事例は学術一次情報を発見できず**（事前学習データ整備からの類推＝**推測**）

## 我々が取るべき行動

### テーマ1 — **設計変更（全体最適）を支持。局所修正は支持しない。**

| 推奨度 | 行動 | 根拠 |
|---|---|---|
| **A+** | **`[X]` の判定単位を「文字列一致」から「claimの含意」に変える。** 正規表現は**候補抽出（recall重視の前段フィルタ）に降格**し、最終判定はjudgeが行う**2層構成** | RAGAS/RAGChecker/DeepEval DAG/promptfoo の全てがこの構造。5例目のような部分文字列事故が構造的に消える |
| **A+** | **`[X]` 専用の人手キャリブレーション。指標はκではなく偽陰性率（見逃し率）** | Kamalloo+ が judge の見逃し47件を実測。**κは見逃し方向の偏りを検出できない** |
| **A** | **`[E]`（固有名詞）にも同じ病理がある**と認識し、**alias定義に「排他語」フィールドを追加**する | 5例目の一般化。日本語に語境界がない以上 alias 単独では不完全 |
| **A** | 応急処置として、既存の全パターンに**競合語彙の自動検出→負の後読み生成**を一度だけ回す。**ただし恒久策でないと明記** | 6例目を1回だけ先送りする価値はある |
| **B+** | judge の `[X]` 性能を Bespoke-MiniCheck-7B と比較。**ただし日本語性能・ライセンス・ベースモデルが全て未確認** | LLM-AggreFact BAcc 77.4。Ollamaで即導入可 |
| **C（非推奨）** | 日本語NLIモデルの自前導入 | 長文脈グラウンディング用に学習された日本語モデルが存在しない |
| **やってはいけない** | **6個目の正規表現を直して終わりにすること** | **5例すべてが同一原因。同じ設計のまま7例目が必ず出る** |

**🔴 注意（反証の反映）**: judgeに移せば全て解決ではない。`Verify with Caution` は「言い換えが多い出力」「離れた箇所を参照する出力」で自動指標が系統的に歪むと報告しており、**我々のC2/C3/C5が直撃**。judge移行と同時に、**`[X]` に限り人手スポットチェック率を引き上げる**べき。

### テーマ2 — **再抽出を支持。後段の正規化では直らない。**

| 推奨度 | 行動 | 根拠 |
|---|---|---|
| **A+** | **取り込み時にチャンク単位で品質スコア（U+FFFD比率・記号比率）を算出しメタデータに保存**。閾値超を「要再処理」フラグ | Dolma が U+FFFD 除去ルールを持つ。閾値は分位点（FineWeb） |
| **A+** | **閾値の初期値は「語誤り率5%」を出発点に。** ただし `�` 比率と語誤り率は等価でないため、**gold回答語の破損率と突き合わせて較正** | Bazzo+ ECIR2020／JCDL2025 |
| **A** | **不良ページのOCRフォールバック経路を用意** | PyMuPDF公式が「ToUnicode欠落は復元不能、唯一の手段はOCR」と明言 |
| **A−** | **除外ではなく「再処理→それでも駄目なら除外」の順に。** 正解を含むチャンクを黙って落とすと症状が悪化する | 当該チャンクは正解を含む |
| **B+** | **表・チャートを含むページを優先的に品質チェック** | OHR-Bench: 表69.6→48.5、チャート70.3→16.5。**行政資料（段組みDTP）は最も壊れやすい層** |
| **B** | 抽出品質は「RAG精度」で最終評価する。OCR精度単体を上げても連動しない | InduOCRBench: OCR 82.9%でもRAG 52.8% |

## 不明点・要追加調査

1. **日本語の語境界なしが採点の偽陽性を生むことを定量した先行研究は発見できなかった。** 我々の5例は独自データであり、公開すれば差別化資産になりうる
2. **既存 judge の κ=0.878 が `[X]` 単体で測られたものか**（社内で要確認）。全要素プールのκなら `[X]` の信頼性は未知
3. Bespoke-MiniCheck-7B の**ライセンス・ベースモデル・日本語性能**（Ollamaページに記載なし）
4. OHR-Bench の mild/moderate ノイズ水準ごとの正確な数値（HTML抽出では読み取りが曖昧）
5. **RAG運用での「チャンク品質ゲート」の学術的一次情報は発見できず**（事前学習データ整備からの類推＝推測）
6. **我々の白書PDFで U+FFFD が出ているフォントが実際に ToUnicode 欠落なのか**（`mutool info` 等で要実測）。**原因特定前に対策を決めない方がよい**
