## 1. 結論

**24問すべてが8秒以内に収まった。要件を満たしている。**

| | 旧構成（2026-08-04） | **新構成（本測定）** |
|---|---:|---:|
| TTFT 中央値 | 6.99 s | **2.00 s** |
| TTFT p90 | 11.56 s | **2.37 s** |
| TTFT 最大 | 14.26 s | **2.65 s** |
| **8秒以内** | **14/24（58%）** | **24/24（100%）** |

**最大値が要件を満たしている点が重要である。** 旧構成は「中央値では満たすが
p90 では満たさない」状態で、24問中10問が要件を外していた。新構成は最悪ケースでも
2.65秒で、8秒に対して約3倍の余裕がある。

| LLM | `gemma4:12b`（7.38GB） | **`granite4.1:8b`（5.35GB）** |

**2つを同時に変えているため、改善の内訳は本測定では切り分けられない。**

リランカーが TTFT 中央値の 60.1%（4,202ms）を占めており、
リランク所要が実測で約1/9になった（`out/reranker-ab-2026-08-04/`）ことから、
**寄与の大半はリランカー側と考えられる**（推定であり、切り分け測定はしていない）。

## 4. 測定条件

- 経路: 製品の stream-chat（SSE）。最初の非空 textResponse までをクライアント側で計測
- 設問: `fixtures/complex/hakusho-complex-qa.json` から等間隔に24問（2026-08-04 と同一）
- 文書: `R07zenpen.pdf`（令和7年版 防衛白書、544ページ）
- ワークスペース: `ttft-hakusho`
- `openAiTemp=0` / `chatMode=query` / topN=8
- 測定機: WSL2 + RTX 5070 Ti **16GB**

## 5. ★本測定で言えないこと

- **8GB 機での TTFT。** 本測定は 16GB 機である。8GB では GPU メモリに余裕が無く、
  一部が CPU へ退避されれば**遅くなる可能性がある**。実機未検証
- **旧構成との比較は同一セッションではない。** 旧は 2026-08-04 の測定で、
  日をまたいでいる（同じ24問・同じスクリプト・同じワークスペース・同じ topN だが、
  同時刻に交互実行したわけではない）。したがって「6.99秒 → 2.00秒」は
  **厳密な A/B ではなく、条件を揃えた別日の比較**である
- **改善の内訳。** LLM とリランカーを同時に変えているため切り分けられない
- **配布物そのものでの測定ではない。** 開発環境（Docker）での測定であり、
  Windows ネイティブ配布物（v1.2.8）を導入した状態では測っていない
