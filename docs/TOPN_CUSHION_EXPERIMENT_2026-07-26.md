## 0. 結論（先に書く）

### 仮説は **支持されなかった**。

> 仮説: 「topN を上げても精度が上がらなかったのはクッションが上限を握っていたためであり、`topN` と `SENTENCE_CUSHION_TOPK` を**同時に**上げれば LLM に届く情報量が増えて精度が上がる」

| 層 | 結果 |
|---|---|
| **検索（retrieval）** | **仮説どおり効いた。** クッションが上限だったことは実証された。`SENTENCE_CUSHION_TOPK=16` にすると Coverage@16 = 0.849→0.868、Coverage@32 = 0.832→**0.896**、All-Hit@32 = 0.700→0.750。**@16→@32 で Coverage が下がる非単調性も消滅**した |
| **生成（generation）** | **改善しなかった。むしろ悪化した。** 要素カバー率は Base 0.582 → 条件B(topN16/cushion16) 0.557 → 条件C(topN32/cushion32) **0.354**。条件C は **S07 判定則の3条件すべてを満たす「有意な差」**（McNemar p=0.0003 / CI非重複 / 3run方向一致）で、方向は**悪化**である |
| **原因** | **トークン予算の超過による切り捨て（cannonball）**。条件C では **20問すべて**でコンテキストが約9,000〜12,500トークンから **約930トークンへ切り詰められた**（コンテナログ実測）。同時にシステムプロンプトも 977→316 トークンへ切られている |

**「検索で正解を取れる量を増やしても、LLMに渡す前の予算で切り捨てられるなら意味がない」** — これが本実験で得られた最も重要な事実である。

### ただし、副産物として**製品既定を変える価値のある発見が1つあった**

**`SENTENCE_CUSHION_TOPK=16`（topN は8のまま）＝ 条件A** は、
- 複雑20問の要素カバー率を **変えない**（0.582 → 0.582、McNemar b=3 c=3 p=1.000）
- 一方で **防衛白書30問の製品ベースラインを 28/30 → 29/30 に上げた**（各3run完全一致で決定的）
- トークン予算超過は**起きない**（コンテキスト最大4,531トークン、cannonball 0件）

ただしこの +1 は**見かけほど良くない**（§6-2 で詳述）。推奨は §9 に書く。

#### 採点系を2つ併記する理由（★重要な但し書き）

`_eval_common.py` には**桁境界チェック付きの `contains()` / `find_bounded()` が既に実装済み**である。
しかし `complex-eval.py` の `judge_element()` は依然として素の `normalize(a) in na`（部分一致）を使っており、
**桁境界の修正が complex-eval に配線されていない**。実験終了時点でもこの状態のままだった。

そこで本書は**2つの採点系の両方で数値を出す**。

- **`frozen`** … 現行 `scripts/complex-eval.py` と同一挙動（桁境界チェックなし）
- **`frozen_fixed`** … スクラッチパッド内のコピーに対してのみ `judge_element` を `_eval_common.contains_marked()` へ差し替えたもの（`scripts/` は変更していない）

**A/B の判定（McNemar・CI・方向一致）は2つの採点系で完全に同じ結論になった**ので、
本書の結論は採点系の選択に依存しない。以降、本文の代表値は `frozen_fixed` を使う
（Base の 0.582 は `QUALITY_ROADMAP` §2.5.3 の訂正後の値と一致する）。

### 2-1. ページ方式 Coverage@8 は**4条件すべてで全問完全に同一**だった

20問すべてについて、`cushion=8/16/32/OFF` の Coverage@8 が1問も違わない。
つまり **topN=8 の時点ではクッションは gold ページを1つも落としていない**。
`SENTENCE_CUSHION_TOPK` を単独で上げても（条件A）、ページ方式の検索指標は**まったく動かない**。

これは §2.5.4 発見1 の「クッションが上限を握っている」という記述を**部分的に訂正する**。
クッションが上限として効くのは **topN ≥ 16 の領域**であって、製品既定の topN=8 では効いていない。

### 2-2. クッションが実際に壊していたのは k≥16 の領域だった

`cushion=8` のときだけ現れていた**非単調性（k を増やすと Coverage が下がる）が、`cushion=16` で完全に消えた**。

| 設問 | cushion=8 の @16→@32 | cushion=16 の @16→@32 | OFF の @16→@32 |
|---|---|---|---|
| Q03 | 0.83 → **0.67**（下落） | 1.00 → 1.00 | 1.00 → 1.00 |
| Q10 | 0.60 → **0.20**（大幅下落） | 0.80 → 0.80 | 0.80 → 0.80 |
| Q16 | 0.67 → **0.33**（下落） | 0.67 → 0.67 | 0.67 → 0.67 |

そして `cushion=16` の @16/@32 は **cushion OFF（＝理論上の上限）とほぼ一致**する
（@32 Coverage 0.896 = OFF の 0.896）。**クッション予算を16にすれば、検索の取りこぼしは上限まで回復する。**

### 2-3. M1 の「索引・チャンク分割の問題（5問）」は**3問がクッションの副作用だった**

`complex-eval` の自動分類が条件によってこう変わった。

| 分類 | cushion=8（M1の結論） | cushion=16 / 32 / OFF |
|---|---|---|
| @8 で全 gold 取得済み | 11問 | 11問 |
| k を増やせば取れる（ランキング） | 4問 Q01/Q05/Q14/Q19 | **7問** Q01/Q03/Q05/Q10/Q14/Q16/Q19 |
| **k を増やしても取れない（索引・チャンク分割）** | **5問** Q02/Q03/Q04/Q10/Q16 | **2問** Q02/Q04 |

**Q03・Q10・Q16 は索引の問題ではなく、クッション予算が gold を追い出していただけだった。**
`QUALITY_ROADMAP` §2.5.3 の「5問（25%）が Phase E の投資判断の根拠」という記述は、
**2問（10%）に下方修正される**（ただし §7 の但し書きを読むこと）。

### 2-4. アンカー方式は条件Aの効果を捉えている（ページ方式は捉えられない）

ページ方式は「取れたチャンクの出所ページ」で判定するため、**チャンク内で何文残ったか**に鈍い。
アンカー方式（gold 本文の文字列が取得チャンク本文に含まれるか）は、まさにそれを測る。

アンカーCoverage@8: **0.581（既定8）→ 0.642（16 / 32）→ 0.708（OFF）**。
設問別に見ると条件Aで改善したのは Q05（0.33→0.67）・Q17（0.67→1.00）・Q18（0.00→0.50）の3問。
**同じチャンクからでも、より多くの gold 本文が LLM に届くようになっている。**

## 3. 🔴 トークン予算の観測結果（切り捨ては起きたか）

### 3-1. 予算の実体（コードから確認、変更はしていない）

RAGコンテキストは `ollama/index.js #appendContext()` により**システムメッセージ側**に載る
（`systemPrompt` + `"\nContext:\n" + [CONTEXT ...]` の連結）。したがって効く配分は
`limits.user`（0.7＝5,734）ではなく **`limits.system` = 8192 × 0.15 = 1,228.8** である。

`helpers/chat/index.js` の `messageArrayCompressor()`:

1. `statsFrom(messages) + 600 < 8192`（＝総計 7,592 未満）なら**何もしない**
2. 超えたら system を `Context:` で割り、プロンプト側を **1,228.8 × 0.25 = 307**、
   コンテキスト側を **1,228.8 × 0.75 = 921.6** トークンへ `cannonball()`（中央を抜く切り詰め）
3. さらに ollama へは `num_ctx = 8192` が渡るので、超過分は Ollama 側でも落ちる

つまり **7,592 トークンを1トークンでも超えると、コンテキストが約922トークンへ崖のように落ちる。**

### 3-2. 条件別の実測

コンテキスト・トークン数は各条件 run1 の `sources[].text` から
AnythingLLM と同じ **cl100k_base**（`js-tiktoken` が gemma4:12b を解決できずフォールバックする encoding）で再構成して数えた。
cannonball はコンテナログの `Cannonball results X -> Y tokens.` を実測。

| 条件 | コンテキスト・トークン min/mean/max | cannonball 発生 | 影響設問 |
|---|---|---|---|
| **Base** topN8/cushion8 | 1,999 / **2,634** / 3,494 | **0件** | — |
| **A** topN8/cushion16 | 3,156 / **3,713** / 4,531 | **0件**（再測定1runでログ実測） | — |
| **B** topN16/cushion16 | 3,976 / **5,148** / 7,184 | **1run あたり2問**（3runで計12行） | **Q13・Q16** |
| **C** topN32/cushion32 | 7,901 / **9,668** / 12,010 | **1run あたり20問すべて**（1runで40行） | **全20問** |
| **D** topN8/cushionOFF | 3,986 / **4,647** / 5,099 | **0件** | — |

**条件B のログ実測（原文）**

```

Cannonball results  9523 -> 929 tokens.
Cannonball results  9400 -> 931 tokens.
Cannonball results 12495 -> 930 tokens.    ← 計20件（全問でコンテキストが切られた）
```

### 3-3. 何が起きたのかの解釈

条件C では、**LLM に届いたコンテキストは約930トークン**である。
これは Base の 2,634 トークンより**少ない**。
つまり条件C は「情報を増やした条件」ではなく、**情報を増やそうとして減らしてしまった条件**である。

さらに悪いことに、`cannonball()` は**中央を抜く**切り詰めなので、
977→316 に切られたシステムプロンプトは
「ルール3（言い換えを同一視せよ）〜ルール6（捏造禁止）」のあたりが**欠落**する。
**ハルシネーション抑止の指示そのものが削られている。**
本実験では条件C のハルシネーションは 0/60 のままだったが、これは運が良かっただけとみなすべきである。

## 7. 本実験の限界（誇張しないための注記）

1. **`vector-search` API は `performSimilaritySearch` を通る**ため、本書の retrieval 数値は
   「素の検索性能」ではなく「**実際に LLM に届くコンテキストの gold 被覆率**」である。
   これは製品の挙動を測るという意味では正しいが、アルゴリズム単体の比較には使えない。
2. **条件D（クッションOFF）だけはページ推定の条件が違う。** クッションONでは
   `PageIndex.locate()` が非連続な文集合から多数決でページを当てるのに対し、
   OFF では連続したチャンク本文をそのまま照合できる。OFF が有利に出る方向のバイアスがありうる。
3. **20問では検出力が足りない**（`PHASE_A_IMPLEMENTATION` S07 で実測済み）。
   条件A/B/D が「誤差範囲」なのは**差が無いことの証明ではない**。
   条件C だけが有意になったのは、差が 0.582→0.354 と極端に大きかったためである。
4. **§2-3 の「索引問題は5問→2問」は、topN を 16〜32 に上げた場合の話**である。
   製品既定の topN=8 のままなら Coverage@8 は 0.783 で変わらず、
   Phase E（チャンク構造化）の必要性そのものは消えていない。
5. 文書は防衛白書1本（DTP制作の行政資料）のみ。
   `CLAUDE.md` にある**もう一方の想定文書（Word/Acrobat 由来のヘルプPDF）では傾向が違いうる**。

## 9. 推奨（製品既定値を変えるべきか）

### 9-1. `topN` は **8 のまま据え置く**

topN を 16 / 32 に上げる条件（B / C）は、retrieval が上がっても generation が上がらないか有意に悪化した。
**`OLLAMA_MODEL_TOKEN_LIMIT=8192` という予算のもとでは、topN を上げる余地は無い。**

topN を上げたいなら、先に必要なのは以下のいずれかであり、順序を逆にしてはいけない。

- コンテキスト予算の拡大（`OLLAMA_MODEL_TOKEN_LIMIT` の引き上げ。**ただし VRAM を要検証**。
  `num_ctx` はそのまま Ollama に渡るため、`docker-compose.yml` のコメントにある
  「KVキャッシュが膨らみ 16GB GPU に載らずCPUへ転落する」問題と同じ土俵になる）
- `messageArrayCompressor` の配分見直し（コンテキストが `limits.system = 全体の15%` しか
  持てず、超えると922トークンへ落ちる設計そのものが**本製品の用途に合っていない**）

**後者は「予算超過時にコンテキストが1/3以下になり、しかもシステムプロンプトの
ハルシネーション抑止ルールが中央から削られる」という設計上の欠陥であり、
Phase F の前に独立した是正項目として立てる価値がある。**

### 9-2. `SENTENCE_CUSHION_TOPK` は **当面 既定8 のまま**を推奨。ただし条件付きで16の余地あり

| 観点 | 8（現行） | 16 |
|---|---|---|
| 複雑20問 要素カバー率 | 0.582 | 0.582（**変わらない**、p=1.000） |
| 複雑20問 完全正答 | 6/20 | 5/20（**わずかに悪化**） |
| 白書30問 | 28/30 | 29/30（ただし §6-3 のとおり**中身は拒否のまま**） |
| Coverage@8 | 0.783 | 0.783（**同一**） |
| アンカーCoverage@8 | 0.581 | 0.642（**改善**） |
| トークン予算 | 平均2,634 | 平均3,713（**超過なし**） |
| ハルシネーション | 0/60 | 0/60 |
| 応答時間 | 8.2s | 7.8s（**差なし**） |

**16 にする実利は「アンカー被覆が上がる」ことだけで、生成の質は動いていない。**
一方でリスクは小さい（予算超過なし・ハルシネーション増なし・遅延増なし）。

したがって推奨は次のとおり。

- **今すぐ既定を変えることは推奨しない。** 20問では検出力が足りず、
  「変えても変わらなかった」以上のことが言えない。設定を1つ増やす保守コストに見合わない
- **ただし `topN` を将来上げるなら `SENTENCE_CUSHION_TOPK` を同時に上げるのは必須**である
  （§2-2 のとおり、topN=16/32 では cushion=8 が実際に gold を追い出している）。
  `QUALITY_ROADMAP` §2.5.4 の「同時に動かせ」という指示は**そのまま有効**
- **評価セットが30〜40問に拡張された後**に、条件A（cushion=16 単独）を再判定する価値がある。
  現時点で最も見込みのある単独変更はこれである

### 9-3. **再embed は不要**（明記）

`SENTENCE_CUSHION_TOPK` も `topN` も **retrieval 後の後処理／取得件数**にしか影響しない。
embedding モデル（`bge-m3`）・チャンク分割（`EMBEDDING_MODEL_MAX_CHUNK_LENGTH=500`）は不変であり、
**どの値に変えても既存文書の再embedは一切不要**である（環境変数変更＋コンテナ再作成のみ）。

### 9-4. ロードマップへの反映事項

1. **§2.5.4 発見1 を訂正する。** クッションの上限が効くのは topN≥16 の領域であり、
   製品既定の topN=8 では gold ページを落としていない（§2-1）
2. **§2.5.3 の「kを増やしても取れない5問」を訂正する。** cushion を上げると2問（Q02/Q04）になる。
   Q03/Q10/Q16 は索引の問題ではなくクッションの副作用だった（§2-3）
3. **新規リスク項目を追加する。** 「コンテキスト予算超過時の cannonball が
   システムプロンプトのハルシネーション抑止ルールを削る」（§3-3）
4. **Phase F（生成側）の重みが上がった。** 検索は cushion=16 + topN=32 で Coverage 0.896 まで
   到達できるのに、生成はそれを使えない。**ボトルネックは検索ではなく、
   コンテキスト予算と gemma4 の抽出能力の側にある**
