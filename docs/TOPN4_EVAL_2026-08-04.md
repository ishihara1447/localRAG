## 1. 結論

1. **`topN=4` の生成側の劣化は 3.74pt**（決定的要素カバー率 **0.630 → 0.593**、166問・650要素・各条件3run）。ペア差の95%CIは **[+0.10pt, +7.43pt]** で0を含まない。**「差が無い」ではなく、小さいが実在する劣化**である。
2. **S07（旧20問）の 7.2pt の約半分**にとどまり、**C5 が壊滅する（0.500→0.100）という前例は再現しなかった**（C5 は 0.395→0.372 の −2.3pt）。最も落ちたのは **C1 集約・構成（−9.8pt）**。
3. **ハルシネーションは増えず（2問→2問、内訳も同一）、C6 unanswerable はむしろ +3.0pt 改善**した。安全性の指標は悪化していない。
4. **ただし事前登録の安全条件 S2（過剰拒否）に抵触した**（10問→21問、+11問。閾値は +5問未満）。追加調査の結果、増加分の大半は「答えられない設問で明示的に棄権するようになった」失敗モードの変化であり、**回答不能になった設問の正味増加は +3問**だが、Q071 のような**真の過剰拒否も実在する**。
5. 🔴 **本タスクの前提「検索側は影響がほぼ無い」は、現在の稼働構成では成立しない。** 本環境で測り直した `anchor_coverage` は **@4 0.631 / @8 0.673（−4.2pt）**。前提となった @4 0.710 / @8 0.712 は**ハイブリッドリランクが有効だった環境の値**であり、その実装は稼働イメージ 1.0.7 に入っていない（§3-2 / §4-6）。**生成側の 3.74pt は、検索側 4.2pt の劣化を引き継いだものと読むのが自然**である。
6. **判定: 事前登録 §2-8 の「保留（追加調査）」**。劣化幅 3.74pt 自体は「条件付き採用」の帯（2.0〜5.0pt）に入るが、S2 に抵触するため機械的には保留となる。**採否はユーザー判断**であり、本測定は「TTFT 要件を確実に満たす代わりに約3.7pt を払う」という取引を数値で確定させた。**なおリランクをイメージに焼き込めば、この代償は大きく縮む可能性がある**（リランク有効時は @4≈@8 だった。ただし別環境の値であり本測定では未検証）。

### 2-4. 統計処理（★測定前に固定。結果を見てから足さない）

1. **McNemar 検定（要素単位・n=650）**
   - **主**: 対応する run 同士のペア 3組（A_run1 vs B_run1 / A_run2 vs B_run2 / A_run3 vs B_run3）でそれぞれ実施。**3組すべてで p<0.05 か**を見る
   - **併記**: ハーネス `--phase report --compare` の既定集約（要素ごとに3run中1回でも当たれば hit = `any()`）
   - 実装は `scripts/complex-eval.py` の `mcnemar()`（両側・厳密二項）を再利用する
2. **設問単位クラスタブートストラップによる「ペア差」の95%CI**（★これが劣化幅の主たる区間推定）
   - リサンプル単位 = **設問（166）**。復元抽出で166問を取り、10,000回、**seed=20260804 固定**
   - 各設問 q について、条件 X の3run合計ヒット数 `hit_{X,q}` と必須要素数×3 の `req3_q` を持つ
   - 標本 S に対し `δ(S) = Σ_{q∈S} hit_{A,q} / Σ_{q∈S} req3_q − Σ_{q∈S} hit_{B,q} / Σ_{q∈S} req3_q`
   - 2.5 / 97.5 パーセンタイルを95%CIとする
   - **要素独立を仮定しないため、ペア差ではこちらを正とする**（要素は設問内にネストしている）
3. **各条件単独のCI**: ハーネス既定の `cluster_bootstrap()`（設問単位・1,000回・seed=20260726）をそのまま使う。判定則 (a) の入力
4. **完全正答率**: Wilson CI（ハーネス既定）＋設問単位 McNemar
5. カテゴリ別: 点推定と n を必ず併記。**カテゴリ単独では採否を決めない**（`BASELINE_166Q_2026-07-28.md` §5-4 の禁止事項）

### 4-6. ★補助: 本環境での retrieval — **「検索側は影響がほぼ無い」は本環境では成立しない**

`--phase retrieval` を本環境で1run 実施した（166問 × k=4/8/16/32 = 664回の `vector-search`、
所要 99分、LLM 不使用）。retrieval は `BASELINE_166Q_2026-07-28.md` §2-8 で
**2run 完全一致（決定的）**と実証済みなので1runでよい。

**アンカー方式（主指標・n=165問。アンカーを持たない Q19 を除外）**

| k | **本測定（リランクなし）** | 参考: ベースライン166（リランク**有効**） |
|---:|---:|---:|
| **4** | **0.631** | 0.710 |
| **8** | **0.673** | 0.712 |
| 16 | 0.699 | 0.707 |
| 32 | 0.699 | 0.717 |
| **@8 − @4** | **+4.2pt** | **+0.2pt** |

アンカー単位（micro / 分母584）: **@4 371/584 = 0.635 ／ @8 397/584 = 0.680**。
`returned` 件数: @4 は中央値4・最大4 ／ @8 は中央値6・最大8。

> 🔴 **これが本測定で最も重要な発見のひとつである。**
>
> 本タスクの前提として与えられた「**検索側は影響がほぼ無い**（@4 0.710 / @8 0.712）」は、
> **ハイブリッドリランク（候補K=32 → クロスエンコーダ → topN）が有効だった環境の実測値**である。
> **リランクが効いていない現在の稼働構成では、`topN` を 8→4 にすると
> 検索側だけで 4.2pt 落ちる。**
>
> 機構は素直に説明できる。リランクがある場合、RRF が作った候補32件を
> クロスエンコーダが並べ替えるので、**上位4件は「32件から選び抜かれた4件」**であり
> 上位8件とほとんど品質が変わらない。リランクが無い場合、**RRF の順位がそのまま切り捨てに使われる**ので、
> 4件に絞ると rank 5〜8 にあった正解チャンクが素直に失われる。
>
> **したがって「検索は影響が無いのに生成だけ落ちる」のではなく、
> 生成側の 3.74pt は、検索側の 4.2pt の劣化をほぼそのまま引き継いだもの**と読むのが自然である。
> （ただし**因果を証明したわけではない**。両者が同程度なのは整合的だというだけである）

**カテゴリ別 `anchor_coverage`（本環境。診断であって証明ではない）**

| カテゴリ | n | @4 | @8 | 差（@8−@4） | 参考: 生成側の差（§4-2） |
|---|---:|---:|---:|---:|---:|
| C1 集約・構成 | 24 | 0.608 | 0.672 | **+6.39pt** | +9.80pt |
| C2 マルチホップ | 49 | 0.633 | 0.706 | **+7.31pt** | +4.74pt |
| C3 比較 | 32 | 0.766 | 0.781 | +1.56pt | +0.97pt |
| C4 要約 | 30 | 0.608 | 0.625 | +1.67pt | +0.28pt |
| C5 推論・含意 | 17 | 0.510 | 0.549 | +3.92pt | +2.33pt |
| C6 unanswerable | 13 | 0.551 | 0.551 | **±0.00pt** | −3.03pt（生成はBが良い） |

**検索側で落ちるカテゴリと、生成側で落ちるカテゴリの順位はおおむね一致している**
（C1・C2 が大きく、C3・C4 が小さく、C6 は検索で不変）。
これも「生成側の劣化は検索側から来ている」という読みと整合する。

§4-5 の生成側 −4.6pt と同じ原因（リランク喪失＋再チャンク）を見ていると考えられるが、
**内訳は分離していない**。

### 5-1. ★設問単位クラスタブートストラップによるペア差の95%CI（主たる区間推定）

650要素は166設問に**ネスト**しており、要素独立を仮定した二項CIはペア差では危険である
（`BASELINE_166Q_2026-07-28.md` §5-3 が「デザインエフェクト 0.64」を実測している）。
そこで**リサンプル単位を設問**にした。

```
リサンプル単位 = 設問（166問を復元抽出）
反復           = 10,000回
seed           = 20260804（事前登録で固定）
統計量 δ(S)    = Σ_{q∈S} hit_A,q / Σ_{q∈S} req3_q  −  Σ_{q∈S} hit_B,q / Σ_{q∈S} req3_q
                 （hit は3run合計、req3 は必須要素数×3。A と B で同じ設問標本を使う＝ペア）
```

| | 値 |
|---|---:|
| **劣化（A−B）点推定** | **+3.74pt** |
| **95%CI** | **[+0.10pt, +7.43pt]** |
| CI が 0 を含むか | **含まない** |
| `P(δ > 0)`（ブートストラップ標本のうち A が優位な割合） | **0.9779** |

> **CI の下限が +0.10pt と 0 のすぐ上にある。**
> したがって「劣化が実在する」とは言えるが、**「劣化幅が 3.74pt である」と断定してはいけない。**
> 真の劣化はほぼ 0 に近い可能性も、7pt を超える可能性も、この測定では排除できていない。
> **点推定を単独で引用しないこと。**

### 5-2. McNemar 検定（要素単位・n=650）

**主（事前登録 §2-4-1）— 対応する run 同士のペア3組**:

| ペア | b（Aのみ正解） | c（Bのみ正解） | **p（両側・厳密二項）** |
|---|---:|---:|---:|
| A_run1 vs B_run1 | 56 | 29 | **0.00451** |
| A_run2 vs B_run2 | 60 | 37 | **0.02499** |
| A_run3 vs B_run3 | 60 | 37 | **0.02499** |
| — | — | — | **3組すべてで p<0.05 → 成立** |

**併記（ハーネス既定の `any()` 集約）**: b=62 / c=23 / **p = 2.77×10⁻⁵**（n=650要素）

**設問単位（完全正答）の McNemar**: run1 b=14 c=7 p=0.189 ／ run2・run3 b=14 c=9 p=0.405。
**設問単位では有意にならない**（完全正答は全要素の充足を要するため分解能が粗く、
不一致ペアが 21〜23 しかない）。**要素単位と設問単位で結論が違うことを隠さずに書いておく。**

不一致ペア率は κ = ψ/δ ≒ (85/650)/(3.74pt) ≒ 3.5 で、`BASELINE_166Q_2026-07-28.md` §5-2 の
想定（κ=1.8）より**両方向の入れ替わりが多い**。b と c の両方が大きい
（56 vs 29 など）ことは、**`topN` を減らすと単に減点されるのではなく、
取れる要素と落ちる要素が入れ替わる**ことを意味する。

### 5-3. 判定則 S07 (a)(b)(c)（プロトコル §3-1）の機械適用

| | 条件 | 結果 |

| (a) | 95%CI が重ならない | ❌ **False** — A[0.5982–0.6628] と B[0.5597–0.6250] は重なる |

**(a) が欠けるので、判定則の文言どおりなら「差は誤差範囲」と書くことになる。**
しかしこれは**判定則 (a) の既知の弱点**である。

> `BASELINE_166Q_2026-07-28.md` §5-3 は測定前に次を実測・警告していた:
> 「判定則 (a) は**独立2標本のCIの重なり**を見ているが、A/B は**同一設問のペア設計**である。
> ペア設計では差の分布に直接CIを付けるほうが検出力が高い。1run 同士なら δ > 約9.8pt が必要」
>
> 本測定の 3.74pt はこの 9.8pt を大きく下回るため、**(a) は原理的に成立しえなかった**。

> **測る前に書いてあり、そのとおりになった**。

**したがって本文書は次の書き分けをする**:

- 判定則の文言に従った機械的な結論: **「(a) を満たさないので判定則上は差なし」**
- ペア設計に適した統計（クラスタブートストラップのペア差CI＋対応runペアの McNemar）に基づく結論:
  **「劣化は 0 と区別できる。点推定 3.74pt、95%CI [+0.10, +7.43]pt」**

**この2つは矛盾していない。** (a) は「独立2標本として見ても差が明白か」を問うており、
本件はそこまで大きくないというだけである。
🔴 **プロトコル §3-1 の判定則そのものは本測定で変更していない。**
変更するならプロトコル本体を改訂してからである（同 §5-3 の指摘のとおり）。

**要点**:

1. **`topN=4` は要件を「満たす／満たさない」の境界を越えさせる唯一の実証済み手段である**
   （`TTFT_BREAKDOWN_2026-08-04.md`。モデル交換では届かない。⑦ LLM は TTFT の32%しかない）
2. **その代償は約 3.7pt であり、5pt の不採用ラインを下回っている**
3. **安全性（ハルシネーション・C6）は悪化していない**
4. **最も落ちるのは C1 集約・構成（−9.8pt）** なので、
   導入先の想定質問が「白書全体の構成を集約する」型に偏るなら、**この判断は変わりうる**
5. **本測定はリランクなしの image 1.0.7 での結果である**（§3-2）。
   §4-6 の実測で、**検索側の `topN` 感度がリランクの有無で大きく違う**ことが分かった
   （リランクなし: @8−@4 = **+4.2pt** ／ リランク有効時のベースライン: **+0.2pt**）。
   したがって `docs/HYBRID_RERANK_2026-07-27.md` の実装をイメージに焼き込めば、
   **`topN=4` の代償は大きく縮む可能性がある**。
   🔴 ただし**本測定はそれを測っていない**（別ワークスペース・別索引の値どうしの比較にすぎない）。
   **期待値として採用判断に織り込んではならない。測るなら別途 A/B が要る**
6. **`topN` を 4 と 8 の二択にする必然性は無い。** §4-6 の retrieval は
   `topN` に対して滑らかに動いており（@4 0.631 / @8 0.673 / @16 0.699）、
   `TTFT_BREAKDOWN_2026-08-04.md` の⑤クッションも topN にほぼ比例する（4件 1.5秒 / 8件 4.2秒）。
   **`topN=5` や `6` なら 8秒要件を保ったまま劣化を減らせる可能性がある**が、**測っていない**

### 7-4. 併せて報告すべき構成上の不整合（本測定の副産物）

**`runtime/docker-compose.yml` は `LANCE_HYBRID_RERANK=true` を渡しているが、
稼働イメージ `localrag-anythingllm:1.0.7` にその実装が入っていないため、効いていない。**
`docs/HYBRID_RERANK_2026-07-27.md` は「検索層の主指標が
`anchor_coverage@8` 0.646 → 0.723 に改善した」と実測しているが、
**その改善は現在の配布物では得られていない**。
§4-5 の「同じ `topN=8` でベースラインから −4.6pt」は、この喪失と再チャンクの合算である
（内訳は分離していない）。**これは `topN` の判断とは独立に扱うべき事実である。**

### 逸脱 3 — 解析スクリプトの表示バグを、結果を見た後に修正した
- 何が起きたか: `out/topn4/analyze.py` で、判定則 (b) を表示する行が
  変数 `p` の上書き（設問単位 McNemar のループが同名変数を再代入）により、

  **正しい値（p=2.77e-05）は修正前の出力にも別行として印字されており**、
  修正は表示の取り違えを直しただけで、**判定基準・統計手法・データは一切変更していない**
- **結果を見た後の逸脱か**: **はい。** ただし
  (i) 変更したのは**自作の集計スクリプトの変数名のみ**で、
  (ii) **凍結対象（`scripts/` `fixtures/`）には触れていない**（sha256 で確認済み）、

  プロトコル §9 が言う「採点基準を触った」には当たらないと判断する。
  それでも**逸脱として記録を残す**
- MFT への回帰テスト追加: 不要（採点器の欠陥ではなく、集計スクリプトの表示バグ）
