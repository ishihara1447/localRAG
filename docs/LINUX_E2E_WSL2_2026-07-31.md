# Linux 配布物 v1.1.0 の E2E 検証記録（WSL2・2026-07-31）

## 1. 何を確かめたか

**配布物 `ote-rag-linux-x64-v1.1.0.tar.gz` を、顧客と同じ経路で通しで実行した。**

これまで検証はすべてスタブ（偽の `docker` コマンド）に対するもので、実際の
インストール・起動・RAG 応答・アンインストールは**一度も実行していなかった**。
特に 2026-07-30 に修正した「アンインストーラが顧客文書を消す10経路」は、
実データに対して守られることを確認できていなかった。

## 2. 検証環境と、その限界

| 項目 | 値 |
|---|---|
| OS | WSL2 / Ubuntu 22.04.5 |
| Docker | 29.4.2 ／ compose v5.1.3 |
| GPU | RTX 5070 Ti 16303MiB ／ nvidia-container-toolkit 1.19.0 |

| systemd | `--no-systemd`（実システムに触れない） |

**RHEL 9 実機ではないため、次は検証できていない**:

- **SELinux Enforcing 下の動作**（WSL2 に SELinux が無い）。`:z` ラベルと
  GPU デバイスアクセスの可否は未確認のまま

  WSL2 の systemd は挙動が異なる）
- **firewalld との相互作用**

これら3点は初回導入が事実上の初検証になる。

## 4. 見つかった事項

### 4-1. WSL2 では `nvidia-smi` が見つからず step 1 で停止する（製品の欠陥ではない）

WSL2 は `nvidia-smi` を `/usr/lib/wsl/lib/` に置く（Windows 側ドライバの
パススルー）。一方 `sudo` は `secure_path` で PATH を制限するため root では
見つからず、`install.sh` が step 1 で停止した。

**RHEL 9 では `/usr/bin/nvidia-smi` にあるため発生しない。**
検証を進めるためラッパー側で PATH を補った（`install.sh` は無改変）。

**停止したこと自体は正しい挙動である。** GPU を確認できないまま導入を完了させ、
後から「異常に遅い」と気づく方がはるかに悪い。podman では GPU 指定が無言で
無視されて CPU 動作に転落する既知問題があり、それと対照的に本製品は
検出して止まることが実証された。

### 4-2. `ote-rag-app` の停止が exit 137（SIGKILL）— 要検討

`docker compose stop` で `ote-rag-app` が **exit 137** になった。正常停止なら
0 か 143 のはずである。

- `docker-compose.yml` に `stop_grace_period` / `stop_signal` の設定は**無い**
  （既定 10 秒）
- コンテナの `StopSignal` / `StopTimeout` も未設定
- 停止直前のログに異常はなく、正常動作中に強制終了された形

**実害は確認していない**（データは保持され、再起動後も正しく回答した）。
ただし書き込みの最中に SIGKILL されるとデータ破損の余地があるため、
`stop_grace_period: 30s` 程度の設定を検討する価値がある。

**これは今回の修正対象外の箇所で、E2E を回さなければ気づけなかった。**

## 5. この検証で埋まったこと / まだ埋まっていないこと

**埋まった**: 導入から RAG 応答、アンインストールまでの通し動作。特に
「顧客文書が実データで守られること」は、スタブでは確認できない性質のものだった。

**埋まっていない**: SELinux Enforcing・systemd 自動起動・firewalld。
これらは RHEL 9 実機でしか確認できず、初回導入が初検証になる。
`RELEASE_NOTES.md` および `INSTALL_GUIDE.md` にその旨は明記済み。
