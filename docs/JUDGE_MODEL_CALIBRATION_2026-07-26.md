## 1. 🔴 配布物への非混入（最優先の設計）

judge は中国系モデル（Qwen）である。ユーザーからは
**「配布物に含まれないのであれば、検証用として中国系LLMを使ってよい」**
という**評価用途に限定した解除**を得ている。したがって混入させないことが実装の第一要件になる。

### 1-1. 物理的に分離した（設定上の約束ではなく、置き場所を分けた）

| | 製品 | judge（評価専用） |
|---|---|---|
| Ollama | コンテナ **`rag-ollama`**（`runtime/docker-compose.yml`） | コンテナ **`ote-judge-ollama`**（compose外・`docker run` で起動） |
| ネットワーク | `rag-internal`（ホストにポートを出していない） | **`127.0.0.1:11435`** のみ |
| モデルストア | **`runtime/ollama-models/`**（＝**配布パッケージに同梱されるディレクトリ**） | **`~/.ollama`**（ホームディレクトリ。リポジトリの外） |
| 中身（実測） | `gemma4`, `bge-m3` の2つだけ | `qwen3:8b`, `qwen3.5:4b` |

`runtime/ollama-models/models/manifests/registry.ollama.ai/library/` の実測内容は
**作業前も作業後も `bge-m3` と `gemma4` の2つだけ**である。judge モデルはここに1バイトも置いていない。

> **なぜコンテナを分けたか（副次的な理由）**
> `rag-ollama` は DNS が壊れており（`registry.ollama.ai` の名前解決が `127.0.0.11:53` で失敗。
> `docs/HANDOFF.md` [B3] のWSL2 DNS問題と同種）、そもそも `docker exec rag-ollama ollama pull` が通らない。
> ホストの `ollama` CLI（DNS 正常）で `~/.ollama` に取得し、それを GPU 付きの別コンテナにマウントして使う構成にした。
> 結果として「製品のモデルストアを触らずに judge を動かす」という要件が構造的に満たされる。

### 1-2. 変更していないファイル（混入経路の点検結果）

以下は**一切変更していない**。judge モデル名の記載も追加していない（`grep` で確認済み）。

- `docs/MODEL_CARDS.md` / `NOTICE` / `LICENSES/` / `THIRD_PARTY_NOTICES`
- `windows-native/` 配下すべて（設定・マニフェスト・envテンプレート）
- `scripts/export.sh` / `scripts/install.*` / `scripts/start.*` などの配布・運用スクリプト
- **`runtime/docker-compose.yml`**（judge 用サービスを足していない。`docker run` の手順を本書に書くだけにした）
- `anything-llm/` 配下すべて（読み取りのみ）

### 1-3. judge 環境の起動・停止手順（開発機でのみ実行する）

```bash
# 1) モデルの取得（ホストの ollama CLI。~/.ollama に入る＝リポジトリ外）
ollama pull qwen3.5:4b

# 2) 評価専用 Ollama をGPU付きで起動（製品の compose には入れない）
docker run -d --name ote-judge-ollama --gpus all -p 127.0.0.1:11435:11434 \
  -e OLLAMA_KEEP_ALIVE=30m -e OLLAMA_NUM_PARALLEL=1 \
  -v "$HOME/.ollama:/root/.ollama" ollama/ollama:latest

# 3) 使い終わったら止めて消す（モデル実体は ~/.ollama に残る）
docker rm -f ote-judge-ollama
```

**評価が終わったらコンテナを消すこと。** 常駐させると VRAM を食い、製品側の推論に影響する（§4-3）。

### 2-1. 制約

1. **被評価モデル `gemma4:12b` と別系統**であること（self-preference bias の回避が S08 の存在理由。
   同系統では意味がない ＝ Gemma 系は全滅）
2. 日本語の判定能力が高いこと
3. **VRAM 16GB（RTX 5070 Ti、実測 16,303 MiB）に載る**こと
4. 中国系可（評価専用に限る）

### 2-3. 選定理由（数字で）

- **`qwen3.5:4b` は Nejumi Leaderboard 4 の10B以下クラスで 0.7352 と最高**であり、
  **`qwen3:14b`（0.7233）を上回る**【出典: Qualiteg 2026-07-10 版】。
  judge は生成ではなく含意判定なので、パラメータ数より指示追従と日本語理解が効く。
- **実測 VRAM 3.4GB**。`gemma4:12b`（8.4GB）+ `bge-m3`（0.6GB）が載ったままでも
  合計 12.4GB で収まり、**製品側をアンロードせずに judge を回せる**。
  `qwen3:8b`（6.3GB）でも合計 15.3GB で載りはするが、実測で 15,939 MiB / 16,303 MiB と
  **限界まで使い切る**（本作業中に実際にこの状態になった）。運用上の余裕がまるで違う。
- 本書 §4 の実測で、**擬似正解に対する κ が qwen3:8b(0.744) を大きく上回る 0.878** だった。
  サイズが小さいほうが精度が高いという結果であり、**選定は指標ではなく実測で決めている**。

### 2-4. `qwen3:8b` 再取得の経緯（記録）

`qwen3:8b` は 2026-07-14 まで**製品のLLM候補**だったが、非中国系方針により不採用となり
（`docs/MODEL_SELECTION_NON_CHINESE_2026-07-14.md`。生成性能でも 22/30・捏造4件で
gemma4:12b の 25/30・捏造0 に劣ると実測されている）、07-17 のクリーンアップでモデル実体も削除済みだった。
本作業では**評価用途に限り再取得**したが、**取得先は `~/.ollama`（リポジトリ外）**であり、
製品モデルストア `runtime/ollama-models/` には戻していない。

> なお「生成では捏造が多い」ことと「judge として使えるか」は別問題である。
> judge の仕事は **reference-guided な YES/NO 判定**であり失敗モードが違う（設計書 §6-3）。
> 実際 §4 の実測でも、qwen3:8b の失敗は捏造ではなく**過度に寛容な YES**だった。

### 3-2. 設計（設計書 §6-2 Layer2 の要求をそのまま実装）

- **Instance-Specific Rubric**: judge に渡すのは
  **(a) 判定対象の要素1つ（`claim`）、(b) 被評価回答の全文、(c) 原典の抜粋（`judge_reference`）** の3点だけ。
  「5点満点で評価して」のような汎用ルーブリックは使わない。総合点・順位付けも出させない。
- **出力は3値**（`OK` / `PARTIAL` / `NG`）の JSON 固定（`format:"json"` で強制）。
  既定では **PARTIAL を不充足に倒す**（保守側。`--partial-is-hit` で変更可）。
- **`evidence` の実在検証**: `OK`/`PARTIAL` のとき、evidence が**正規化後の回答本文に部分文字列として実在しない**判定は
  **無効化して人手キューに回す**（judge 自身のハルシネーション検出。設計書 §6-2）。
- **temperature=0 / seed固定 / top_k=1 / top_p=1**。
- **`think:false`**（qwen3系の思考モードを止める。古い Ollama で 400 が返る場合は自動で think 抜き再試行）。

### 3-3. judge が落ちても評価は止まらない（S08 の必須要件）

`judge_element_llm()` は**例外を外に出さない**。次のすべてを `verdict=None`（未判定）にして続行する。

| status | 意味 |
|---|---|
| `error` | 接続不能・タイムアウト・HTTPエラー（judge コンテナが落ちていても評価は完走する） |
| `bad_json` | JSON として読めない |
| `bad_verdict` | OK/PARTIAL/NG 以外を返した |
| `evidence_missing` | evidence が回答本文に実在しない（人手キュー行き） |

そして **`[N]`/`[E]`/`[X]` の決定的採点は judge の有無から完全に独立している**。
`--judge-model` を渡さなければ judge は1回も呼ばれない。

**非破壊性の実測**: S06 で保存済みの `s06_gen_run1.json` を judge 無しで採点し直し、
既存の `s06_judged_run1.json` と**要素単位の verdict/evidence まで含めて不一致 0**、
プール比率も **48/79 = 0.608** で従来値と一致した。

```
S08導入後の決定的採点の不一致: 0
```

## 4. キャリブレーション（本題）

### 4-1. 人手ラベルを使わない「擬似正解キャリブレーション」

S08 の採用下限は κ ≥ 0.7 だが、本来これは人手ラベル50〜100要素を要し、
**ユーザーの手作業コストが発生する**。これを最小化するために次を実施した。

> **S06 で `[N]`/`[E]` の必須要素 79個の正誤が決定的に確定している。
> この79要素を judge にも判定させ、決定的採点との一致度（κ）を測る。**

これにより**人手ラベル0件で judge の信頼性を推定できる**。
（限界は §5 に必ず書く。完全な代替ではない。）

### 4-2. 実測結果（`s06_gen_run1.json` / 79要素 / seed=20260726）

| judge | prompt | 判定できた要素 | 一致率 Po | **κ（生）** | 95%CI | 偽陰性 | 偽陽性 | 決定性 |
|---|---|---:|---:|---:|---|---:|---:|---:|
| `qwen3:8b` | v1 | 74/79 | 0.878 | **0.744** | 0.581–0.888 | 0.047 | **0.226** | **20/20** |
| **`qwen3.5:4b`** | **v1（採用）** | 66/79 | 0.939 | **0.878** | 0.754–0.970 | 0.083 | **0.033** | **20/20** |
| `qwen3:8b` | v2 | 71/79 | 0.887 | 0.773 | 0.616–0.914 | 0.125 | 0.097 | **19/20**（★） |
| `qwen3.5:4b` | v2 | 61/79 | 0.885 | 0.773 | 0.609–0.929 | **0.219** | **0.000** | **20/20** |

- **偽陽性率**（決定的にはNOなのに judge がYES）が両者の差を作っている。
  qwen3:8b は 22.6%、qwen3.5:4b は 3.3%。**judge の失敗は「甘さ」に出る**という定型どおりの結果である。
- `qwen3.5:4b`(v1) の不一致は**わずか4件**で、内訳は
  **偽陽性1件**（Q05/e5「3月末」で「3月24日」を可とした）、
  **決定的採点側の誤り2件**（§4-3。judge のほうが正しい）、
  **真の偽陰性1件**（Q20/e2「2025年度から整備着手という記述はある旨」を NG とした）である。
  つまり**実質的な judge の誤りは 66件中2件**にとどまる。
- **決定性**: `qwen3.5:4b` は v1・v2 とも **20/20 で完全一致**。
  一方 **`qwen3:8b` は v2 で 19/20（★）** と1件ぶれた（v1 では 20/20）。
  同一 seed・temperature=0 でも**GPU非決定性で判定が動きうる**ことの実測例であり、
  設計書 §6-4-5 の「一致しないなら判定の信頼性以前の問題」に照らすと、
  **この点でも `qwen3.5:4b` を採る根拠になる**。
  なお計測中は別作業の `gemma4:12b` が同一GPUに載っており（合計15.9GB/16.3GB）、
  バッチング状態が run 間で違った可能性がある。**judge の決定性チェックは毎回出力に残す実装にしてある。**

### 4-3. ★副産物: 擬似正解（決定的採点）側に2件の誤りを発見した

judge が「決定的採点はYESだがNG」と言った要素を**原文照合したところ、judge のほうが正しかった**。

| 設問/要素 | 決定的採点 | 実際 | 原因 |
|---|---|---|---|
| Q06/e3「予備自衛官にも勤続報奨金**7万円**」 | YES | **回答は勤続報奨金に言及していない＝NO** | 正規化後 `70000円` が **`約270000円` の内部**に部分一致した |
| Q11/e2「訓練招集手当 **17,100**〜」 | YES | **回答にその数値は無い＝NO** | 正規化後 `17100` が **`約1710000円` の内部**に部分一致した |

**桁境界を跨いだ数値一致**である。79要素を機械的に走査したところ、
**該当は正確にこの2件のみ**（`alias` の先頭/末尾が数字で、その直前/直後も数字であるケース）。

含意（記録として重要）:

### 4-4. プロンプト v2（v1 の癖を塞いだ版）

v1 の不一致を**全件目視**し、`qwen3:8b`（偽陽性7件）に次の系統的な癖を確認した。

| # | 癖 | 実例 | qwen3.5:4b でも出たか |
|---|---|---|---|
| 1 | **不記載表明（「記載がありません」）を OK にする** | Q15「2024年度の出来事5件」への拒否回答を `日米豪比による海上協同活動` の要素にOK判定。Q19 も同様 | **出ていない** |
| 2 | **近い数値で代用する** | 「2025年3月**末**」で「2025年3月**24日**」をOK（Q05/e5） | **出た**（qwen3.5:4b の偽陽性はこの1件のみ） |
| 3 | **「AとB」の片方だけでOKにする** | Q11「予備自12,300円 vs 即応予備18,500円」で12,300円だけを見てOK | 出ていない |

**`qwen3.5:4b` の偽陽性は 30件中1件（癖2）だけ**であり、
評価を壊す度合いが最も大きい癖1（unanswerable の誤判定）が出ていない点が決定的だった。

癖1 は **unanswerable（C6）の評価を壊す最悪の誤り**であるため、
プロンプトに**この3点を明示ルールとして追加**した版（v2）を作り、両モデルで測り直した。

> ⚠ **v2 は擬似正解79要素の誤りを見て書いたため、同じ79要素で測った κ には過学習方向のバイアスがある。**
> にもかかわらず、**v2 は κ を下げた**。

**実測（`qwen3.5:4b`）: v1 κ=0.878 → v2 κ=0.773。** 内訳を見ると原因は明確で、

| | 偽陽性率 | 偽陰性率 | 未判定 |
|---|---:|---:|---:|
| v1 | 0.033 | 0.083 | 13/79 |
| v2 | **0.000** | **0.219** | 18/79 |

**v2 は厳しくしすぎて偽陰性が 8.3% → 21.9% に増えた。** 偽陽性は 0 になったが、
κ は両方向の誤りを見るため差し引きで悪化する。

**結論: 採用モデル `qwen3.5:4b` では v1 を使う**（`--judge-prompt` の既定を `v1` にした）。
v2 は「甘い judge を締める」ためのオプションとして残す。
**これは「プロンプトを厳しくすれば judge は良くなる」という直感が実測で否定された例**である。

## 5. この方法の限界（必ず読むこと）

### 5-1. 擬似正解 κ は「[P] に対する judge 性能」の直接の証拠ではない

決定的に判定できる要素（`[N]`/`[E]`）は、**「その文字列が回答に出ていれば正解」という判定が容易な部類に偏っている**。
一方 judge が本番で担当する `[P]` は、

- 否定を含む命題（「打上げ年度の記載は**ない**旨」）
- 程度・条件つきの命題（「ロシアは中国との戦略的連携と**相まって**という条件付き」）
- 範囲の区別（「653はホットライン3種の合計であり、総計1,422とは範囲が異なる**旨の区別**」）

といった、**判定が本質的に難しいもの**である。したがって擬似正解 κ は
**judge 性能の上限側の推定**として読むべきであり、**人手ラベルの完全な代替にはならない**。

### 5-2. 単一 run・単一設問セットである

- 対象は `s06_gen_run1.json`（topN=8, temperature=0）の1 run。
  topN=8 の6 run は回答がバイト単位で一致しているため（S07 の実測）、run を増やしても情報は増えない。
- **回答の分布が変われば judge の癖も変わりうる**。将来 Phase B 以降で回答傾向が変わったら、
  **キャリブレーションを取り直すこと**（`--phase calibrate` を再実行するだけでよい）。

### 5-3. κ の CI が広い

n=66〜74 では 95%CI がおおむね ±0.12 幅ある。`qwen3.5:4b` の v1 の CI 下限は **0.754** で
採用下限 0.7 を上回っているが、`qwen3:8b`（CI下限 0.581）は**下限が 0.7 を割っている**。
**CI 下限で判断するなら qwen3:8b は不採用**である。

### 5-4. judge が判定を放棄する率（未判定率）

`evidence_missing` により、v1 では qwen3:8b が 5/79、qwen3.5:4b が 13/79 を未判定にした。
これは**安全側の設計どおりの挙動**（根拠を回答から引用できない判定は信用しない）だが、
未判定が多いほど `[P]` の実効サンプルが減る。`[P]` 26要素に対する未判定は
qwen3:8b 6件 / qwen3.5:4b **2件**であり、**本番用途（[P]）では qwen3.5:4b のほうが未判定も少ない**。

## 6. ユーザーにお願いしたい人手ラベル（最小化した結果）

### 6-1. 何個やってほしいか

> **26要素**。ただし**読む回答は15本だけ**（1本の回答に複数の要素がぶら下がるため。実測値）。
> 所要は目安 **20〜30分**。

これは設計書 §6-4 が求める「50〜100要素」を**下回っている**。その代わりに、

1. **判定が容易な79要素は judge に自動採点させ、決定的採点との κ で代替した**（§4）
2. 人手には **judge が実際に担当する `[P]` だけ**をやってもらう（＝1件あたりの情報量が最大）

という構成にしてある。26件は `[P]` の**全件**であり、抽出ではないのでサンプリング誤差が入らない。

### 6-2. どこにあるか

**リポジトリ内に置いてある**（scratchpad は消えるため）。

```
docs/JUDGE_CALIBRATION_HUMAN_SHEET_2026-07-26.md          ← これ1つに書けばよい
docs/JUDGE_CALIBRATION_HUMAN_SHEET_2026-07-26.labels.json ← JSONで入れたい場合はこちらでも可
```

シートは**設問単位にまとめてある**（同じ回答を要素の数だけ読み返さなくて済む）。各要素に

- 判定したい内容（採点基準）
- 原典の根拠
- **judge（`qwen3.5:4b` / プロンプト v1 ＝採用構成）が実際に出した判定と evidence**

が並んでいる。**MDの `- label:` の行に `YES` / `NO` と書き足すだけでよい**
（`○` `×` `はい` `いいえ` も受け付ける）。迷うものは空欄のままでよい。

### 6-3. 記入後にやること

```bash
# judge コンテナは作業後に削除してあるので、まず起動し直す（§1-3）
docker run -d --name ote-judge-ollama --gpus all -p 127.0.0.1:11435:11434 \
  -e OLLAMA_KEEP_ALIVE=30m -e OLLAMA_NUM_PARALLEL=1 \
  -v "$HOME/.ollama:/root/.ollama" ollama/ollama:latest

uv run scripts/complex-eval.py --phase calibrate --judge-model qwen3.5:4b \
    --judge-unload <s06_gen_run1.json> \
    --human-labels docs/JUDGE_CALIBRATION_HUMAN_SHEET_2026-07-26.md

docker rm -f ote-judge-ollama
```

（`--human-labels` は **記入済みMDシートでもJSONでも受け付ける**。パーサは実装済み・動作確認済み）

**judge vs 人手の κ**（本命）が出る。判定則は次のとおり**事前に固定する**。

| 結果 | 判断 |
|---|---|
| κ ≥ 0.7 | **judge を採用**。`[P]` を含む「全要素カバー率」を副指標として報告に載せる（主指標は決定的要素のまま） |
| κ < 0.7 | **judge を採用しない**。`[P]` の評価は諦め、決定的要素のみで運用する（設計書 §6-3-1 の設計どおり動く） |

> **無理に採用しないこと。** `[P]` を諦めても S04〜S07 は成立するように作ってある。
> 「judge を使いたいから閾値を下げる」のは、内部監査が指摘した「生スコアの手動補正」と同じ種類の誤りである。
