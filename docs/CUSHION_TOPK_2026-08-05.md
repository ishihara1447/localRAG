## 2. なぜこれを変えたのか（原因の特定まで）

### 発端: 検索指標が k に対して非単調だった

```
anchor_coverage@4 0.6866 / @8 0.7284 / @16 0.7105 / @32 0.7084
165問中20問で @32 < @8
```

**候補を増やして情報が減ることは原理的にあり得ない。**

### 原因

`sentenceCushion.js` の `topKSentences()` が**チャンク数に関わらず上位8文で固定**。

```js
ranked.slice(0, topKSentences())   // 全チャンクの文をまとめて8文に絞る
```

チャンクが増えるほど1チャンクあたりに残る文が減り、必要な記述が押し出される。

### 排除した原因（推測で手を出さずに済んだもの）

| 候補 | 検証 |
|---|---|
| パース不良 | ❌ 取りこぼした162アンカーすべてが文書全文に存在 |
| マルチホップの難しさ | ❌ ページの散らばりと無相関（0p 0.743 / 201p以上 0.729） |
| 数値・表の抽出 | ❌ 取りこぼしの46%は「中程度の句」、純粋な数値は2% |
| 類似度閾値 | ❌ 0.25→0 でも返却件数が変わらない |
| 候補プールの上限 | △ `min(50, max(20, topN*4))` は @8→@16 の16問を説明するが、プールが同じ @16→@32 の5問は説明できない |

### 既存の実測記録との整合

`server.env.template` に残っていた記述——

> 「K=50 は retrieval では最高だが hakusho-eval が 29/30 → 27/30 に退行した」

——**この退行の機序が本調査で説明できた。**

**安全性の劣化ではない。** 「答えられない」と正しく言ったうえで、周辺説明が減っただけ。

## 6. ★この変更で言えないこと・残る懸念

- 🔴 **TTFT の余裕が約3倍から約1.2倍に減った。** 導入先の **VRAM 8GB 機では未検証**であり、
  開発機より遅ければ8秒を超えうる。TTFT が問題になる環境では 8 に戻すこと
- 🔴 **非単調性の機序を説明できていない。** 16 で悪化し 24 で改善する理由は不明で、
  **24 が最適という保証は無い**。32 以上は測っていない
- **C2 が −1.6pt 低下**した機序も不明
- **配布物での挙動は未測定。** 開発環境（Docker、イメージ 1.1.0）での測定
- **防衛白書1本での測定。** 他の文書での効果は不明
- 166問は **1run** のみ（30問セットは3run）。事前登録では弱点発見用と位置づけていたが、
  効果測定にも使った。**この点は逸脱**であり、3run で確認していない
