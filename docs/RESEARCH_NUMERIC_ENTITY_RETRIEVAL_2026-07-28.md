# 調査: 数値・固有表現に対するRAG検索の弱さと既知の解法

調査日: 2026-07-28
対象: OTE-RAG（bge-m3 + 日本語bi-gram BM25 + RRF + bge-reranker-v2-m3、実効チャンク500文字）
実施: researcherサブエージェント（Write権限が無かったため本ファイルはClaude Codeが保存）

## サマリー

1. 「埋め込みは数値を保持できない」は2019年から一貫して再現されている既知の欠陥。2026年の最新実測でも主要13モデルの平均正答率は **54%（ほぼチャンスレベル）**、特に**カンマ区切り数値と高精度小数が最悪**。当製品の失敗例（`34万4,000円`、`2兆5,245億円`）は**この既知の最悪ケースに完全一致**する。
2. ただし症状は埋め込みだけでなく、**日本語bi-gram BM25が数値文字列でIDFを失うこと**、**500文字チャンクが表を破壊すること**の複合と考えるのが定説に近い。表+テキスト混在の数値QAベンチ（T²-RAGBench）では最良のRAG手法でも数値一致率 **41.3%**、**オラクル文脈でも 72.3%** しか出ない。
3. 最優先は**再embed不要で実装量の小さい3手**（親ページ展開／数値正規化専用スパースフィールド／RRF→凸結合＋数値クエリ時のsparse重み上げ）。**HyDEやクエリ分解は、まさに当該タスクで悪化した実測報告がある**ため後回しが妥当。

## 0. 最重要の所見: 「正解ページは取得できている」

これは失敗が文書レベルではなく以下のいずれかで起きていることを意味する。

- (a) ページ内でgold文を含まないチャンクだけが上位に来ている（粒度）
- (b) rerankerがページ内の別チャンクを優先している（順序）
- (c) gold文は文脈に入っているが生成側が数値を拾えていない（生成）

**「オラクル文脈を与えても数値質問は解けない」という報告が複数ある。**

| 報告 | 内容 | 出典 |
|---|---|---|
| T²-RAGBench | **オラクル文脈での Number Match 72.3%**。最良RAG（Hybrid BM25）41.3%、Base RAG 37.2% | arXiv:2506.12071 |
| FinanceBench上のRAG改善実験 | Base RAG 0.204 → クエリ拡張 0.24 → リランキング 0.256、**オラクル 0.573** | arXiv:2404.07221 |

**含意**: 検索を完璧にしても数値QAの上限は概ね **60〜75%**。166問の失敗を全部「検索の問題」に帰属させると誤診する。

## A. 数値・固有表現に対する検索の弱さ

### A-1. Revealing the Numeracy Gap（EACL 2026 Findings, arXiv:2509.05691）

EmbedNum-1K（金融文脈1,000件）で **13モデル**を評価。

| 指標 | 値 |
|---|---|
| 全モデル平均正答率 | **54%**（"slightly better than chance"） |
| 数値フォーマット別の振れ幅 | **50%〜74%** |
| 小数(0.x)形式 | 62% |
| 4桁整数 | ほぼチャンスレベル |
| **最も苦手な形式** | **カンマ区切り数値（例 3,035）と高精度小数** |

**当製品への含意（重要）**: 論文が最悪と報告した形式が「カンマ区切り数値」。失敗例 `34万4,000円` `2兆5,245億円` `計121件、約234億円` はすべてカンマ区切り＋漢数字スケール混在。**偶然ではなく既知の最悪ケースを踏んでいる。**

説明機構は**トークナイズ**。語彙外の数値は複数トークンに分割され、その分割が意味的に不安定なため埋め込み空間で数値の同一性が保たれない。

**注意（未検証）**: **bge-m3 と multilingual-e5 はこの13モデルに含まれていない。** 両者はXLM-RoBERTa系トークナイザで数値の分割挙動が異なる可能性がある。**bge-m3固有の数値耐性の実測は見つからなかった。**

### A-2. Numbers Matter!（Findings of EMNLP 2024, arXiv:2407.10283）

FinQuant / MedQuant（`=`, `>`, `<` の数値条件クエリ）、NDCG@10:

| モデル | FinQuant | MedQuant |
|---|---|---|
| BM25 | **0.09** | **0.07** |
| ColBERT | 0.27 | 0.24 |
| SPLADE | 0.19 | 0.20 |
| **QColBERT（数量分離型）** | **0.56** | **0.37** |
| **QSPLADE（数量分離型）** | **0.53** | **0.38** |
| ColBERT_ft（統合型） | 0.44 | 0.36 |

**重要な知見**: **「分離(disjoint)」型が「統合(joint)」型を一貫して上回る**（P@10で10ポイント超）。**テキストスコアと数量スコアを別々に計算して後で合成するほうが効く。**

**留保**: このベンチは**範囲条件**クエリが主眼。当製品は**完全一致寄り**なので BM25=0.09 をそのまま当てはめるのは誤り。ただし「標準的な検索器は数量を単なる語として扱っており、それが破綻の原因」という診断は共通。

### A-3. 粒度のジレンマ（Findings of EMNLP 2025）

CapRetrieval。埋め込みは「文書全体の意味との整合」と「細粒度の顕著性の捕捉」を両立できない。**モデルサイズや学習データに関係なく細粒度マッチで一貫して低性能**（0.1Bのファインチューンが7B SOTAを上回った報告あり）。

→ **「bge-m3をより強い埋め込みに差し替える」というアプローチの期待値は低い。**

### A-4. 古典的先行研究

- Wallace et al. (arXiv:1909.07940): 標準的埋め込みは **1,000程度までの大きさ**しか正確に符号化できない。**兆・億のオーダーは範囲外。**
- arXiv:2402.14903: **推論時にカンマで数値を区切ると右から左のトークナイズが強制され性能が大きく改善**。トークナイズ方式が数値表現の質を左右する直接証拠。
- FoNE / Number Token Loss / DEL: 「数値を1トークンで表現」する方向。**すべて再学習が必要**で当製品には非現実的。

## A-2. BM25の日本語トークナイズと数値

### bi-gram分割が数値文字列を壊す機構（**推論**、一次文献の裏付けなし）

`34万4,000円` を文字bi-gramに分割すると:
`34 / 4万 / 万4 / 4, / ,0 / 00 / 00 / 0円`

`34`, `00`, `0円` 等は、数表だらけの白書コーパスでは**DFが極端に高くIDFがほぼ0**。BM25スコアが実質消滅し、無数の他の数値文字列ともマッチして識別力を失う。

対して `わが国を取り巻く安全保障環境` のbi-gram（`安全`, `全保`, `保障`…）は低DFでIDFが効く。**「見出し語は取れて数値は取れない」はこの非対称性で説明できる。**

間接証拠: N-gram方式は「再現率が高いがノイズが多い」、形態素解析は「適合率が高いが辞書依存」（ZOZO TECH BLOG）。※**ZOZO記事に数字・正規化の具体的記述は見つからなかった。**

### 確立した数値正規化の実装（これは「既に解かれている」）

**(1) Lucene / Elasticsearch `JapaneseNumberFilter`（`kuromoji_number`）**

| 入力 | 出力 |
|---|---|
| `〇〇七` | `7` |
| `三千2百２十三` | `3223` |
| `兆六百万五千一` | `1000006005001` |
| `３．２千` | `3200` |
| `１．２万３４５．６７` | `12345.67` |
| `4,647.100` | `4647.1` |

**必ず踏むべき落とし穴**:
- `discardPunctuation` を **false にしないと壊れる**（`３．２千` が `3` と `2000` に分裂）
- **文脈盲目**: 人名「京一」を巨大な数値として誤正規化しうる
- **大字（壱、弐）、会計数字、分数は非対応**
- **既知のバグ的挙動**: `15,7` が `157` になる
- **クエリ側にも同じ正規化を適用しない限りマッチしない**

**(2) Sudachi の `JoinNumericPlugin` / `normalized_form`**
- `JoinNumericPlugin`: `一二三` → `123`、**カンマ区切り数値の結合**
- `normalized_form`: 送り仮名・表記ゆれ・異体字・誤記の正規化
- `DefaultInputTextPlugin` が小文字化 → **Unicode NFKC**（全角半角統一）
- 分割モードA/B/C。**固有名詞・複合語をまとめたいならモードC**

**(3) 実務上の最小構成（提案）**

インデックス側とクエリ側の**両方**に:
1. NFKC正規化
2. 桁区切りカンマ除去（`4,000` → `4000`）
3. 漢数字スケール展開（`2兆5245億` → `2524500000000`）
4. 単位を別トークンとして保持（`円`, `件`, `億円`, `人`, `年度`）
5. **元の表層形も同時に残す**

3と5を**両方**入れるのが定石（どちらかだけだと質問側の表記が想定と違ったときに落ちる）。

### 日本語SPLADE

`hotchpotch/japanese-splade-base-v1` は JQaRA で **nDCG@10 = 0.6441**。同ベンチの BM25 は 0.458、bge-m3+sparse 0.5088、bge-m3+dense 0.539、bge-m3+all 0.576。

**ただし数値には期待しないほうがよい（不利な情報）**: 学習済みスパース検索の弱点として **「稀なエンティティ、シリアル番号、固有名詞に依存するクエリを解決できない」「製品SKUや型番など完全一致が弱点」「クエリと文書の双方が語彙拡張されるため共通語が1つもないのにマッチする（ノイズ）」** との指摘が複数の技術記事で共通（Qdrant 等）。**SPLADEはサブワード語彙を使うため桁の多い数値はやはり分割される。** JQaRAの+0.19は主に一般語彙の改善であり、**数値質問に効く保証はない。**

> ⚠️ **他調査との不一致**: `RESEARCH_GRANULARITY_MISMATCH_2026-07-28.md` は日本語SPLADEを P4 として推奨している（JQaRA +13.5pt）。本調査は「数値には効かない可能性」を指摘。**両者は矛盾しない**（一般語彙には効くが数値には効かない）が、**当製品の失敗の中心が数値である以上、SPLADE導入の期待値は割り引くべき**。

## A-3. ハイブリッド検索と融合関数

### RRFのパラメータ感度と凸結合の優位（直接的な論文証拠）

**An Analysis of Fusion Functions for Hybrid Retrieval**（arXiv:2210.11934 / TOIS）:
- **「既存研究に反して、RRFはそのパラメータに敏感である」**
- 凸結合（CC）の学習は**スコア正規化の選び方にほぼ非依存**
- **「CCはドメイン内・ドメイン外の双方でRRFを上回る」**
- CCはサンプル効率が良く**少数の学習例で調整できる**

**機構の説明（推論を含む）**: RRFは**スコアではなく順位のみ**を使う。「BM25が完全一致で圧倒的に高いスコアを出した」という情報が**順位に潰されて失われる**。

BM25 1位 / dense 50位 → `1/61 + 1/110 ≈ 0.0255`
dense 1位 / BM25 20位 → `1/61 + 1/80 ≈ 0.0289` ← **後者が勝つ**

**数値の完全一致という「強い証拠」が順位変換で希釈される構造は明確に存在する。当製品の症状と整合する最有力仮説の一つ。**

### ハイブリッドの重みの実測値（arXiv:2407.01219, EMNLP 2024）

- スパース／デンス混合の**最適 α = 0.3**（両ベンチマークで最良）

| 手法 | DL19 mAP | DL20 mAP | 遅延 |
|---|---|---|---|
| 元クエリのみ | 30.13 | 28.56 | — |
| Hybrid Search | 47.14 | 47.72 | **3.20秒** |
| Hybrid + HyDE | **52.13** | **53.13** | **11.16秒** |

著者の結論: HyDEはmAP +4〜5ptだが**+7〜14秒/クエリ**の遅延で実用的でない。

- チャンクサイズ実測: **512トークンが最良**（faithfulness 97.59%）、256（97.22%）、1024（94.26%）
- リランカー: monoT5 31.78 / 4.5秒、TILDEv2 27.83 / **0.02秒**

### 数値混在文書ではBM25がdenseに勝つ

- arXiv:2604.01733: **「BM25が金融文書上でSOTAのdense retrievalを上回る」**。2段階ハイブリッド＋リランキングで Recall@5 = 0.816
- T²-RAGBench: **Hybrid BM25 が最良**（MRR@3 37.8%）

**含意**: 数値・表が多い文書では**スパース側の比重を上げるのが定石**。

## B. 表・数表からの検索

### B-1. 表+テキスト混在の数値QAは未解決領域

**T²-RAGBench**（arXiv:2506.12071、23,088トリプル）:

| 手法 | MRR@3 | Number Match |
|---|---|---|
| Oracle Context | — | **72.3%**（上限） |
| **Hybrid BM25** | **37.8%** | **41.3%** |
| Base RAG | 36.9% | 37.2% |
| **HyDE** | **32.0%** | — |
| **Reranker** | **30.3%** | — |
| 検索なし | — | 3.9% |

論文の失敗原因分析（重要）:
1. **わずか3,000文書でもMRR@3が50%を割る**
2. 表データの構造的複雑さを埋め込みモデルが捉えられない
3. **「表中の数値は意味的文脈を欠く」ためdense検索が効きにくい**
4. **HyDEはベースより悪化**
5. **要約系の手法は推論に必要な数値情報を失う**

- **TAT-QA**: モデル 58.0% F1 vs **人間 90.8% F1**（33pt差）
- **MULTITAT**（arXiv:2502.17253）: 10言語拡張で**非英語は英語比で平均19.4%の性能低下**。日本語RAGには追加のハンディ
- **FinLongDocQA**: **129kトークンを超えると文脈位置特定に失敗**

### B-2. TableRAG（NeurIPS 2024, arXiv:2410.04739）

| 手法 | ArcadeQA | BirdQA |
|---|---|---|
| **TableRAG** | **49.2%** | **45.5%** |
| ReadSchema | 43.1% | 40.3% |
| RowColRetrieval | 37.7% | 39.6% |
| **ReadTable（表全部投入）** | **4.6%** | **9.1%** |

**「表を丸ごとチャンクに入れる」が最悪の戦略**であることが明確。ただしTableRAGは「巨大な単一テーブル」前提で、**白書のように小さい表が散在する文書に直接は適用できない**。転用するなら「表ごとにスキーマを抽出して別インデックス化する」部分。

**TableRAG (HeteQA版, arXiv:2506.10380)**: 「表を平坦化してチャンク化する戦略は本質的な表構造を破壊し情報損失を招く」と明言。SQL生成・実行を組み込む。**具体的数値は未取得。**

### B-3. 表のシリアライズ形式（WSDM 2024, arXiv:2305.13062）

- **HTML が「NL+Sep」形式を 6.76% 上回る**
- 自己拡張プロンプト併用: TabFact +2.31%、HybridQA +2.13%、ToTTo +5.68%

→ 表をMarkdownで持っているなら**HTMLに変えるだけで数%改善する可能性**（低コスト）。ただし主因の解決にはならない。

### B-4. 段組みPDFでの表の破壊（OmniDocBench, arXiv:2412.07626）

表認識 TEDS:

| ツール | TEDS |
|---|---|
| RapidTable | 82.5% |
| StructEqTable | 75.8% |
| PaddleOCR | 73.6% |
| Qwen2-VL-7B | 71.0% |

最新SOTA: PaddleOCR-VL-1.5 が v1.5 で **94.5%**、MinerU2.5-Pro が v1.6 で **95.69**。

**段組みに関する明記**: 「すべてのモデルで、**多段組みと複雑レイアウトで明確な精度低下**が観測される」「InternVL2 と Qwen2-VL は**財務報告書のような特定のPDF種別で多段組みテキストを結合してしまう傾向**」「**回転した表はほぼ全モデルが構造認識に失敗**」。

**言語**: 「英語より中国語の認識精度が低い」。**日本語の結果は含まれていない。**

**→ 低コストな検出方法**: 失敗した gold 文字列を抽出済みテキストに単純 grep する。**数分で切り分けができ、最初にやるべきこと。**

> ✅ **2026-07-28 実施済み。結果は本文書の想定と異なり、156件中156件（100%）がパース済みテキストに存在した。さらにチャンク境界で分断されていたのは3件（1.9%）のみ。パース品質は当文書では犯人ではない。**

## C. 実務的な回避策

### C-1. Query rewriting / decomposition — 数値質問には効かないという報告が優勢

**不利な報告（重要）**:

| 報告 | 内容 | 出典 |
|---|---|---|
| T²-RAGBench | **HyDE が Base RAG より悪化**（32.0 vs 36.9） | 2506.12071 |
| T²-RAGBench | **リランカーも Base より悪化**（30.3 vs 36.9） | 同上 |
| T²-RAGBench | **要約系手法は推論に必要な数値情報を失う** | 同上 |
| RAG Best Practices | HyDE +4〜5pt だが**遅延 +7〜14秒/クエリ** | 2407.01219 |
| Gemma 1B/4B | HyDEは**応答時間25〜40%増**かつ幻覚率が無視できない。**オンデバイス用途ではRAGがHyDEを上回る** | 2506.21568 |
| Agent-Orchestrated Adaptive RAG | **クエリ分解はマルチホップベンチでランキング精度を悪化させた** | 2606.05658 |
| Dissecting Agentic RAG | クエリ分解とリランキングは**有意だが小さい**。固定ハイブリッドが適応ルーティングを上回った | 2606.21553 |

**有利な報告**: FinanceBench上の改善実験で Base 0.204 → HyDE 0.24 → リランキング 0.256（オラクル 0.573）（2404.07221）、ARAGOG（2404.01037）。

**総合判断**: 当製品の条件に最も近い T²-RAGBench で**HyDEが明確に悪化**しているため、**HyDE系は優先度を下げるべき**。

> ⚠️ **要注意**: T²-RAGBench では **reranker も Base より悪化**している（30.3 vs 36.9）。当製品は 2026-07-27 に `LANCE_HYBRID_RERANK` を有効化して集計で +0.077 を得たが、**数値質問に限定した層別検証はしていない**。数値質問でリランカーが有害になっていないかを確認すべき。

### C-2. メタデータ・構造化抽出との併用 — 最も有望な方向

| 手法 | 効果 | 出典 |
|---|---|---|
| **SRAG**: 抽出したエンティティを関係表に整理しSQLで推論 | **精度 +29.6%** | 2503.01346 |
| **MimirRAG**: メタデータ統合＋**表対応チャンキング**＋エージェント的WF | **FinanceBench 89.3%** | 2605.25030 |
| **Numbers Matter の disjoint 法** | テキストと数量を**別々にスコアリングして合成**、P@10で10pt超 | 2407.10283 |

**「RAGより構造化抽出が適する」という主張は明確に存在する。**

### C-3. Contextual Retrieval（Anthropic 2024-09）

| 構成 | top-20失敗率 | 削減 |
|---|---|---|
| ベースライン | 5.7% | — |
| Contextual Embeddings | 3.7% | **-35%** |
| + Contextual BM25 | 2.9% | **-49%** |
| + リランキング | 1.9% | **-67%** |

コスト: **文書100万トークンあたり $1.02**（一度きり、プロンプトキャッシュ利用）

**再embedの要否（当製品に重要）**:
- Contextual **Embeddings** は**全チャンク再embed必須**
- Contextual **BM25** は**再embed不要**（スパースインデックス再構築のみ）

→ **「Contextual BM25 だけ先に入れる」部分適用が可能**で、当製品の制約に適合する。ただし**BM25単独の寄与は公開値から分離できない**（35%→49%の差分をBM25寄与と読むのは**推論**）。

**当製品との相性（仮説）**: 表由来チャンクは「`計121件、約234億円について認定`」のように**単体では何の話か分からない**。「第III部 第2章 防衛生産・技術基盤 / 表: 装備品等の認定実績」を前置すればdenseもBM25も効きやすくなる。**表チャンクに限定すれば再embed対象を数%に絞れる可能性**（推測）。

### C-4. Late Chunking

bge-m3 は8192トークン対応で適用可能だが**全チャンク再embedが必要**。改善幅はabstractに明記されておらず**未取得**。

> ⚠️ `RESEARCH_GRANULARITY_MISMATCH_2026-07-28.md` が **bge-m3 はCLSプーリングのため適用不可**（BGE-M3で nDCG@5 0.246→0.070）という決定的な反証を掴んでいる。**そちらを採用する。**

## D. 「効果がなかった／悪化した」報告のまとめ

1. **HyDE は表+数値ドメインで悪化**: T²-RAGBench 36.9 → 32.0
2. **リランカーも同ベンチで悪化**: 36.9 → 30.3 ← **当製品の層別検証が必要**
3. **要約・圧縮系は数値を失う**
4. **クエリ分解がランキング精度を悪化**（2606.05658）
5. **クロスエンコーダの寄与は「有意だが小さい」**、固定ハイブリッドが適応ルーティングを上回った（2606.21553）
6. **HyDEの遅延コスト**: +7〜14秒/クエリ、応答時間25〜40%増
7. **RRFはパラメータに敏感で凸結合に劣る**（2210.11934）— 「RRFは頑健」という通説への反証
8. **埋め込みの大型化では細粒度検索は解決しない**（粒度のジレンマ）
9. **表を丸ごと投入する戦略は壊滅的**: 4.6% / 9.1%
10. **LLM-as-a-judge は表認識の最適化信号として信頼できない**（2607.13347）

## E. 日本語での検証事例

**正直な報告: 日本語で「数値検索の失敗」を定量的に扱った一次文献は見つからなかった。**

| 事例 | 内容 |
|---|---|
| JQaRA | BM25 0.458 / bge-m3+dense 0.539 / bge-m3+all 0.576 / japanese-splade 0.6441 / JaColBERTv2.5 0.642 / ruri-reranker-large 0.7712。**JAQKETベースのクイズ的QAで数値抽出に特化していない** |

| Lucene JapaneseNumberFilter | 漢数字・スケール語・カンマ区切りの正規化仕様（前掲） |
| Sudachi | JoinNumericPlugin、NFKC、分割モードA/B/C |
| MULTITAT | **非英語で平均19.4%の性能低下** |
| OmniDocBench | **日本語の評価結果は含まれない** |

**含意**: 「日本語の数表PDFに対する数値QA」は**公開ベンチマークが存在しない空白領域**。リスクであると同時に**差別化の機会**（自社評価セット166問自体が資産）。

## F. 再embed要否のマトリクス

| 手法 | 再embed | 実装量 | 期待効果 |
|---|---|---|---|
| チャンク→親ページ展開 | **不要** | 極小 | 大（自社実測が根拠。ただし推論） |
| 数値正規化した専用スパースフィールド | **不要**（BM25再構築のみ） | 小 | 中〜大（実装済み仕様あり。数値は推測） |
| bi-gram → Sudachi C ＋数値保護の併用 | **不要** | 小〜中 | 中（数値効果は未実測） |
| RRF → 凸結合＋数値クエリ時のsparse重み上げ | **不要** | 小 | 中（2210.11934、α=0.3） |
| 表由来チャンクのみHTML形式に | 表チャンクのみ | 小 | 小〜中（+6.76%） |
| 数量メタデータの別インデックス | **不要**（追加索引） | 中 | 中〜大（+13〜34pt、**範囲条件クエリでの値**） |
| PDF再パース | 表チャンクのみ | 中〜大 | **grep検証の結果次第** |
| Contextual BM25（スパース側のみ） | **不要** | 中 | 中（内訳不明） |
| Contextual Embeddings | **必要（全チャンク）** | 中 | 中（-35%） |
| Late Chunking | **必要** | 中 | **他調査が適用不可と判定** |
| 埋め込みモデル差し替え | **必要（全チャンク）** | 中 | 中（JQaRA +0.09〜0.10）だが**数値への効果は保証なし** |
| 表→SQL化 + Text-to-SQL | 不要（別系統） | **大** | 大（+29.6%）だが**製品スコープが変わる** |
| HyDE / クエリ分解 | 不要 | 小 | **負またはゼロの可能性が高い** |

## G. 適用優先順位

### 順位0（着手前・数時間）: 診断を確定させる

**0-a. gold文字列の grep 検証** — ✅ **2026-07-28 実施済み。156/156件が存在（100%）。パースは犯人ではない。**

**0-b. オラクル文脈での上限測定と層別リコール**
- 費用: 半日、再embed不要
- 内容: 数値質問／非数値質問で層別した chunk-level Recall@k、**リランカー適用前後の順位変化**
- 期待効果: 検索改善の天井が分かる。**リランカーが数値質問で逆効果になっていないかを検出できる**
- 根拠: T²-RAGBench オラクル 72.3% / 最良RAG 41.3%、**リランカーが Base より悪化（30.3 vs 36.9）**

### 順位1: チャンク→親ページ／隣接チャンク展開 — 費用: 極小 / 効果: 大

- **再embed不要**。1日以内
- **「正解ページ自体は取得できている」という自社実測がそのまま効果の根拠**
- リスク: 文脈が長くなり Lost in the Middle（2307.03172）で生成側が落ちる。**必ずA/Bで測る**
- 「要約・圧縮は数値を失う」ので**削るより足す方向が正しい**

### 順位2: 数値正規化を両側に適用したスパースフィールド追加 — 費用: 小 / 効果: 中〜大

- **再embed不要**（BM25再構築のみ）。1週間以内
- NFKC → カンマ除去 → 漢数字・スケール展開 → 単位分離 → **表層形も併存**
- 既製部品: Lucene `JapaneseNumberFilter`、Sudachi `JoinNumericPlugin`
- **落とし穴**: クエリ側にも同じ正規化が必須、`discardPunctuation=false`、`15,7`→`157` バグ、人名誤正規化、大字・分数は非対応

### 順位3: RRF → 凸結合 ＋ 数値クエリ検出時のスパース重み上げ — 費用: 小 / 効果: 中

- **再embed不要**。2〜3日
- 根拠: 2210.11934、α=0.3（2407.01219）、「BM25が金融文書でSOTA denseを上回る」（2604.01733）
- 順位0-bでリランカーが数値質問で有害と分かったら、**数値質問ではリランカーをバイパスする**分岐も同時に

### 順位4: PDF再パース — ~~費用: 中〜大~~ → **0-aで否定されたため優先度を下げる**

### 順位5: 表チャンクの再設計（HTML保持＋見出し前置） — 費用: 中 / 効果: 中

- 表チャンクのみ再embed（全体の数%と推測）。1〜2週間
- (1) 表は500文字で切らず表単位で保持、(2) HTMLシリアライズ、(3) 表タイトル＋章見出しを前置
- 根拠: シリアライズ形式だけで +6.76%、文脈前置は失敗率 -35〜-49%

### 順位6: 数量メタデータの分離インデックス — 費用: 中 / 効果: 中〜大

- **再embed不要**（追加インデックス）。2〜3週間
- 根拠: **「分離型が統合型を一貫して上回る」**（2407.10283）
- **留保**: +29ptは**範囲条件クエリ**での値で、完全一致寄りの当製品タスクに外挿できない

### 順位7以降（優先度低、または非推奨）

| 施策 | 判断 | 理由 |
|---|---|---|
| Contextual Embeddings（全チャンク） | 保留 | 全再embed必須。順位5の表限定適用で効果の大半が取れる可能性 |
| 埋め込みモデル差し替え | 保留 | 全再embed必須。**数値への効果は保証なし**。粒度のジレンマは解決しない |
| Late Chunking | **非推奨** | 他調査が bge-m3 で適用不可と判定 |
| **HyDE / クエリ書き換え** | **非推奨（当面）** | T²-RAGBenchで悪化。遅延+7〜14秒 |
| **クエリ分解** | **非推奨（当面）** | ランキング悪化の報告、寄与は小 |
| Table-as-Image / VLM検索 | **非推奨** | GPU要件が上がりローカル実行という製品価値を毀損 |
| 表→SQL化 + Text-to-SQL | **別プロダクトとして検討** | 効果は最大級だが製品スコープが変わる |

### 生成側の対策（順位1と同時に、費用極小）

- プロンプト変更のみ。数時間
- (1) 数値は**逐語コピーを強制**し丸めを禁止、(2) 出典チャンクの再掲、(3) 数値が文脈に無ければ「記載なし」
- 根拠: T²-RAGBench のオラクル 72.3%（＝**28%は生成側の失敗**）

## H. 不明点・要追加調査

1. **bge-m3 / multilingual-e5 の数値保持能力の直接実測がない**。XLM-RoBERTa系トークナイザが `34万4,000円` をどう分割するかは**未検証**（ローカルでtokenizerを回せば数分で分かる）
2. **日本語 bi-gram BM25 と形態素解析の、数値クエリ限定の定量比較が存在しない**。IDF崩壊の説明は**推論**。自社166問で「bi-gram BM25 単独 vs Sudachi BM25 単独」を測るのが最も確実
3. **RRFが数値の完全一致を希釈する機構を実証した論文は見つからなかった**
4. Late Chunking の改善幅の一次数値
5. Contextual Retrieval における BM25 単独寄与
6. TableRAG (HeteQA版) の具体的精度
7. FinanceBench 原典の数値は**二次情報で未検証**
8. **OmniDocBench に日本語文書が含まれていない**
9. WebSearch予算切れで未調査: 日本語RAG実務ブログの数値検索失敗事例、`kuromoji_number` の実運用不具合、bge-reranker-v2-m3 の数値クエリ挙動、Docling/MinerU の日本語ベンチ
