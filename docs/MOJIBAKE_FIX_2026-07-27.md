## 1. 何を変えたか

| ファイル | 変更 |
|---|---|
| `anything-llm/collector/processSingleFile/convert/asPDF/PDFLoader/index.js` | `normalizeReplacementChars()` を追加（+44行）。env gate `PDF_MOJIBAKE_TO_ELLIPSIS`（**既定ON**） |
| `runtime/docker-compose.yml` | gate の説明とコメントアウトした巻き戻し用エントリ（**挙動は不変**） |
| `windows-native/config/collector.env.template` | 同上（顧客配布物側の設定先） |

処理の実体は1行である。

```js
const _RE_REPLACEMENT_RUN = /�+/g;
text.replace(_RE_REPLACEMENT_RUN, "…")
```

呼び出し位置（`load()` 内、ページ単位）:

```js
const text = normalizeJapaneseSpacing(
  normalizeReplacementChars(textItems.join(""))
);
```

### 1-1. なぜ `asPDF/index.js` ではなく `asPDF/PDFLoader/index.js` か

3つとも実装上の理由がある。

1. **不具合は pdfjs-dist に固有**である（`docs/EXCLUSION_FIELD_AND_MOJIBAKE_2026-07-27.md` §2-3）。
   その抽出器を呼んでいるのは `PDFLoader` だけなので、修正はそこに閉じるのが正しい。
   `asPDF/index.js` に置くと **OCRフォールバック経路（`OCRLoader`）にも掛かってしまう**。
   OCR は別の壊れ方をするので、同じ規則を当てる根拠がない。
2. **ページ境界マーカー `\f<page>\f` を挿入するのは `asPDF/index.js`**（`pageContent.push(\`\f${pageNumber}\f\`)`）である。
   `PDFLoader` はマーカー挿入より**手前**なので、マーカーと衝突する余地が構造的に無い。
   U+FFFD も U+2026 も `\f` ではないから誤って壊すこともない。
3. 既存の日本語PDF対策 `normalizeJapaneseSpacing()` と**同じ層**であり、
   「pdfjs の抽出テキストを直す」という関心事が1か所にまとまる。

### 1-2. 処理順序（`normalizeJapaneseSpacing` を壊していないこと）

**U+FFFD の畳み込み → 字間空白の正規化** の順にした。

そもそも両者は干渉しない。`normalizeJapaneseSpacing()` が触るのは
「CJK-CJK」「数字-CJK」「CJK-数字」に挟まれた空白だけで、**U+FFFD も U+2026 も
`_CJK` の文字クラスにも数字にも属さない**からである。

これは推論で済ませず**実測で確かめた**（§3-2）。防衛白書PDF 543ページで
「畳んでから正規化」と「正規化してから畳む」の出力は**全ページでバイト一致**する。

## 2. 設計判断（変えてはいけない点）

### 2-1. 「削除」ではなく「`…` への置換」

`QUALITY_ROADMAP_2026-07-26.md` の **S21（印刷目次パーサ、未実装）は、目次ページの判定に
リーダー罫線（`U+FFFD` 連続 / `・{3,}` / `\.{3,}`）を使う設計**である。
単純除去すると判定材料そのものが消えて S21 が成立しない。
`…` への置換なら (a) ノイズが圧縮され、(b) リーダー罫線の signal が残り、
(c) **PyMuPDF が同じページに対して返す正しい表現と一致する**。

**S21 実装時の申し送り（重要）**: 畳み込みにより **`U+FFFD` の連続も `…` の連続も
コーパスに存在しなくなる**。したがって S21 の検出規則は
「`…` が3つ以上連続」ではなく **「`…` の後に行末のページ番号が続く行」** にすること。
本PDFの目次5ページでは、この規則が **293本のリーダー行のうち 289本（98.6%）に一致する**（§3-3 実測）。

### 2-2. 単発の `U+FFFD` も畳む（畳む下限は1）

`�{3,}` のような閾値は置かず、**1文字でも `…` にする**。根拠は3つ。

1. **U+FFFD は定義上「復号できなかった」ことしか意味せず、情報を持たない。**
   残しても復元できず、埋め込みでも BM25 でも純粋なノイズにしかならない。
2. **本PDFの単発10件は、すべて「幅が足りず点1つになったリーダー罫線」だった**（実測で本文を確認）。
   例: `…インドとパキスタンとの対立\x08 � 152`、`トランプ政権後の米国の安全保障戦略の見通し\x08� 59`。
   閾値を置くと、**同じ現象なのに表記が2つ残る**。
3. 閾値を置くと **U+FFFD がコーパスに残り続け**、下流（S21、チャンク品質ゲート、
   将来の正規化）が「`…`」と「`�`」の両方を相手にすることになる。**規則は1つに保つ。**

想定される反論は「本文中で1文字だけ復号に失敗した場合、`…` にすると
"意図的な省略記号" に見えてしまう」というもの。ただしその場合も
**元の情報は既に失われており**、`�`（復号失敗）と `…`（省略）はどちらも
「ここに何かがあった」以上を語らない。**新たな損失は発生しない。**

### 2-3. gate の既定 — **当初ONで実装し、実測を見てOFFに変更した**

**着手時の設計は「既定ON」だった。** 理由は「U+FFFD は情報を持たないので失うものが無い」（§2-2）、
「既定OFFだと顧客配布物では `collector/.env` を書き換えない限り永久に効かない」、
「巻き戻しは env だけで可能」の3点で、`LANCE_HYBRID_RERANK`（レイテンシ1.7倍という明確な代償があった）
とは違い**代償が測定上ゼロ**（抽出時間 14.0s vs 13.8s）だと考えていた。

**この前提は §5 の実測で覆った。** 「代償ゼロ」ではなく、**再チャンク化による位相ずれという代償があった**。
したがって**既定を OFF に変更した**。判断の根拠は §5-5 に書く。

**受け付ける値（既定OFF版）**: `true` / `1` / `on` / `yes`（大文字小文字・前後空白は無視）で**有効**。
未設定・空文字・その他の文字列はすべて無効。
**有効化しても、対象文書を再取り込みするまで既存チャンクは変わらない。**

## 4. 再embed手順（★S26 リハーサル。次回そのまま再現できる粒度）

### 4-0. 前提の確認（着手前に必ず）

```bash
# 1) 稼働コンテナと docker cp 済みファイルの一致（--force-recreate 厳禁）
REPO=/home/ishihara1447/projects/fukugyo/repos/localRAG
for F in server/utils/vectorDbProviders/lance/index.js \
         server/utils/vectorDbProviders/lance/sentenceCushion.js \
         collector/processSingleFile/convert/asPDF/PDFLoader/index.js; do
  H=$(sha256sum "$REPO/anything-llm/$F" | cut -d' ' -f1)
  C=$(docker exec anythingllm sha256sum "/app/$F" | cut -d' ' -f1)
  [ "$H" = "$C" ] && echo "OK $F" || echo "MISMATCH $F"
done
# 2) env（LANCE_HYBRID_RERANK=true 等）
docker exec anythingllm sh -c 'env | grep -E "LANCE_|EMBEDDING_|PDF_MOJIBAKE"'
# 3) ワークスペース設定（topN=8 / temp=0 / chatMode=query）
```

### 4-1. 変更を反映する（`docker cp` + `docker restart`）

`scratchpad/mojibake/deploy.sh`。**collector は起動時に JS を読み込むので `docker cp` だけでは効かない。restart が必須。**

```bash

until [ "$(curl -s -o /dev/null -w '%{http_code}' http://localhost:3001/api/ping)" = "200" ]; do sleep 2; done
```

| 3 | PDFをアップロード（＝**ここで collector が抽出。gate が効くのはこの瞬間**） | `POST /api/v1/document/upload`（multipart, field=`file`） |
| 4 | ワークスペースへ追加（＝埋め込み・LanceDB投入） | `POST /api/v1/workspace/{slug}/update-embeddings` `{"adds":[location],"deletes":[]}` |
| 5 | APIキー削除 | `DELETE /api/system/api-key/{id}` |

### 4-4. 踏んだ落とし穴（次回のために必ず読むこと）

1. **`httpx.Client.delete()` は `json=` を受け付けない。**
   `TypeError: Client.delete() got an unexpected keyword argument 'json'` になる。
   `c.request("DELETE", url, json=...)` を使う。
   このため初回は「ベクタ削除は済んだが文書実体が残る」中途半端な状態で落ちた。
   → **再取り込みスクリプトは、途中から再実行しても収束するように書くこと**（本スクリプトは
   ワークスペース添付が既に外れていても `documents/custom-documents/` に残る実体を探して消す）。
2. **旧文書のJSONを消し忘れると評価ハーネスが壊れる。**
   `scripts/_retrieval.py` の `PageIndex.autodetect()` は
   「改ページマーカーが最も多い文書JSON」を選ぶ。同じPDFの新旧2本が残ると
   **同数で並び、glob 順に依存して旧文書を拾いうる**。今回、以前から残っていた
   孤児 `R07zenpen.pdf-559eabd8-….json`（どのワークスペースにも属さない）も併せて削除した。
3. **`docker compose up -d` / `--force-recreate` を使わない。**
   `lance/index.js` と `lance/sentenceCushion.js` は `docker cp` でしか入っておらず、
   イメージ `localrag-anythingllm:1.0.7` には含まれていない。再作成すると消える。
4. **APIキーの後始末。** 途中で異常終了すると `finally` に到達せず孤児キーが残る
   （今回1件発生し、次の実行の一括削除で回収した）。**キーの値はログに出さない**。

| | ベースライン（2run） | 本変更後（2run） | **巻き戻し後（1run）**<br>＝ベースラインと**バイト一致するコーパス** |

> 結果はベースライン(29/30)ではなく変更後(28/30)と完全に同じ内訳になった。**

> **「同じテキストを入れ直しただけ」で起きている。**

**交絡因子として最も疑わしいのは再取り込みそのもの**である。再取り込みすると
チャンク本文が同一でも **ベクタの UUID が新規採番され、LanceDB のテーブルが作り直される**。
ハイブリッド検索は BM25 のみでヒットしたチャンクを `score=null` のまま扱う（§2.5.14 の「機構上の注意」）ため、
**同点の並び順が ID/行順に依存し、topN=8 の切り口が変わりうる**。
これは推定であり、本作業では**切り分けていない**（切り分けるには「同一コーパスで再取り込みだけを2回繰り返す」対照実験が要る）。

**したがって、生成側の指標は本変更の評価に使えない。** 判定は検索側（§5-1）に依拠する。

### 5-4. なぜ下がったのか — チャンク分割の位相ずれ（実測で特定）

**目次5ページが 3,489字 短くなった結果、そこから下流のチャンク境界が再整列した。**

| 実測 | 値 |
|---|---|
| 作業前チャンク | 1,756 |
| 作業後チャンク | 1,748 |
| **本文が完全に一致するチャンク** | **1,692（96.4%）** |
| 旧にしか無いチャンク / 新にしか無いチャンク | 64 / 56 |
| **変化したチャンクの出所ページ** | **物理ページ 5〜27 のみ**（27で再同期し、以降は完全一致） |

日本語セパレータ指定のテキスト分割器は区切り位置で再同期するため、
**影響は文書全体には及ばず、ページ5〜27 の「位相がずれている区間」で止まる。**

評価20問のうち gold がこの区間に掛かるのは **Q01/Q02/Q05/Q06/Q13/Q14/Q15/Q19 の8問**で、
**@8 で動いたのは Q15（gold = phys 23,24）だけ**だった。Q15 の中身を見ると:

```
ベース: rank3 のチャンク（p23）が 4アンカーを全部含んでいた → 1.00
変更後: rank1 のチャンク（p23）は 2アンカーしか含まない      → 0.50
```

**アンカーそのものは新コーパスにも全て存在する**（`在レバノン共和国邦人等輸送` は4→3チャンク、
`防衛省・自衛隊70周年記念観閲式` は不変）。**取れなくなったのではなく、1つのチャンクに同居しなくなった。**

> **これは本作業の最大の学びである。**
> **抽出を1文字でも変えると、変更箇所より下流のチャンク境界が再整列し、
> 「変更していないページ」の検索結果まで動く。**
> したがって抽出系の改修は「その改修が正しいか」だけでなく
> **「再チャンク化のくじ引きに勝てるか」まで含めて測っている**ことになる。
> n=19/n=30 の評価セットでは、この2つを分離できない。

### 5-5. 既定を OFF にした判断

**2026-07-26 に事前合意した判定則「Phase B以降は retrieval 指標を主・generation 指標を従（退行監視）」に従う。**

- **主指標が下がった**（`anchor_coverage@8` 0.7228 → 0.6965）。
  巻き戻すと **0.7228 に完全復帰**したので、**これは本変更に帰属する実効果である**（§5-1 ③）
- 従指標（`hakusho-eval`）は**判定に使わない**。再取り込みだけで動くことが判明したため（§5-3・§6-1）
- **得られた利益は測定上ゼロ。** Q02 は既に 1.00 で伸びしろが無く、他の18問も1つも改善しなかった

**＝ 「利益ゼロ・主指標に実測の退行あり」なので、既定で入れる理由が無い。**

- 実装は**残す**。S21（印刷目次パーサ）は `…` を必要とし、`�` のままでは §2.5.13 の設計衝突が残るため
- **既定は OFF**。`PDF_MOJIBAKE_TO_ELLIPSIS=true` ＋ 再取り込みで有効化できる
- **再検討のタイミング**: S21 実装時、またはチャンキング（Phase E）改修時。
  どちらも再チャンク化を伴うので、**位相ずれのコストを二重に払わずに済む**

**やってはいけないこと**: 「Q15 が下がっただけだから誤差」として既定ONで押し切ること。
2run で決定的に再現しており、事前に決めた判定則に照らせば退行である。

## 6. 巻き戻し確認（★S26 の要求事項）

**gate を戻して再取り込みするだけで、作業前の状態にバイト単位で戻ることを実測した。**

手順（コード変更なし。所要 **214.2秒**）:

1. `PDF_MOJIBAKE_TO_ELLIPSIS` を無効側にする
   （本作業では既定をOFFに変更したので**設定を消すだけ**。既定ONのままで戻す場合は
   docker なら compose の `environment` に `PDF_MOJIBAKE_TO_ELLIPSIS=false`、

**入力（PDF）と設定が同じなら出力はバイト一致するので、失敗しても必ず戻せる。**
